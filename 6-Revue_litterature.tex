\paragraph{History and background}
Since the early days of linear programming (LP), practitioners have needed to translate
mathematical formulations into data that solvers can process.
At first, this meant encoding each coefficient of the problem matrices by hand, a process
that is both tedious and error-prone~\cite{fourer1978modern}.
\emph{Matrix generators} were introduced in the late 1960s to automate this task: they compute the
coefficients through explicit loops and write them out in solver-readable formats like
MPS~\cite{marceau1971matrix, ibm1976mpsx}.

Despite matrix generators removing most of the manual labor, a gap remained.
Modelers naturally think in terms of sets, indices, and algebraic expressions,
while procedural code constructs the coefficient matrices entry by entry.
This mismatch between how a model is expressed and how it is implemented made them difficult to
verify, modify, and communicate with others \cite{fourer1983modeling}.
\emph{Algebraic modeling languages} such as AMPL \cite{fourer1990ampl},
AIMMS \cite{bisschop2006aimms} and GAMS \cite{brooke1988gams} closed this gap by accepting
problem descriptions that closely follow the math.
For a more complete overview of the early history of modeling languages refer to
\cite{orchard-hays1984history}.

More recently, modeling languages embedded in general-purpose programming languages have
gained popularity, such as Pyomo \cite{bynum2021pyomo, hart2011pyomo} in Python,
JuMP \cite{dunning2017jump} in Julia, and CasADi \cite{andersson2019} in C++.
Other domain-specific modeling languages specialized for convex optimization \cite{boyd2004convex}
are built on \emph{disciplined convex programming} (DCP), a set of composition rules under which
the convexity of a problem can be verified
automatically \cite{grant2004disciplined, grant2006disciplined}.
These DCP-based languages include CVX \cite{cvx} in MATLAB, CVXR \cite{Fu_2020} in R,
CVXPY \cite{diamond2016cvxpy} in Python, and Convex.jl \cite{udell2014convex} in Julia.

\paragraph{Structure of the chapter}
The first two sections focus on CVXPY: it is the most actively maintained DCP implementation,
and the work of this thesis aims to be integrated into it.
\S\ref{sec:canonicalization} covers the \emph{frontend} of canonicalization, which rewrites the
user's functional form into a functional conic form of purely affine and quadratic expressions.
\S\ref{sec:matrix-stuffing} covers its \emph{backend}, \emph{matrix stuffing}, which assembles
the problem data from this functional conic form.

Because the problem data assembled this way is exactly a sparse Jacobian of the canonicalized
form, \S\ref{sec:computing-derivatives} reviews the methods available for computing sparse
derivatives.
\S\ref{sec:coefficient-extraction} then revisits the same task from the side of other modeling
systems: it presents the embedded modeling languages JuMP and CasADi as well as the algebraic
language AMPL as instances of that machinery, and compares how each one extracts the problem
data with the approach taken in CVXPY.
Finally, \S\ref{sec:sparse-matrices} covers the sparse matrix formats used to store the
problem data, along with some useful algorithms for manipulating them.

\section{Canonicalization}
\label{sec:canonicalization}

CVXPY is a DCP-based modeling language embedded in Python \cite{diamond2016cvxpy},
which began in 2013 as an implementation of the modeling principles of CVX \cite{cvx}.
Three fundamental design decisions differed from CVX at the beginning.
The first is modularity: a few core data structures are shared by separate components for
verification, canonicalization, matrix stuffing, and solver interfaces.
The second is the expression tree as the central data structure, which is formed
automatically from user code through Python's operator overloading.
The third is support for parameters: since canonicalization never looks at the values of
constants, much of the compilation work can be reused when a problem is solved repeatedly.

These ideas matured with version 1.0, which redesigned canonicalization as
a general reduction-based rewriting system \cite{agrawal2018rewriting}.
The new design enabled the addition of other disciplined
grammars \cite{agrawal2019dgp, agrawal2020dqcp, cederberg2025disciplined}, and the early
parameter support grew into disciplined parameterized programming (DPP), a restricted grammar
under which canonicalized programs can be updated efficiently \cite{agrawal2019dpp}.

The open source project has since grown through contributions from many other enthusiastic
developers; a recent paper surveys the new canonicalization and modeling features
introduced between versions 1.1 and 1.9 \cite{zhang2026cvxpy}.

\paragraph{Functional form.}
A user most naturally expresses a CVXPY problem in \emph{functional} form,
\BEQ\label{eq:functional-form}
\begin{array}{ll}
\mbox{minimize}   & f_0(x; \theta) \\
\mbox{subject to} & f_i(x; \theta) \leq g_i(x; \theta), \quad i=1,\ldots,m_1,\\
                  & h_i(x; \theta) = j_i(x; \theta), \quad i=1,\ldots,m_2,
\end{array}
\EEQ
where the optimization variables $x_1,\ldots,x_k$ are collected into a single
vector $x \in \reals^n$, and likewise the parameters $\theta_1,\ldots,\theta_l$
into $\theta \in \reals^p$ \cite{boyd2004convex}.
As in \S\ref{sec:Introduction}, \eqref{eq:functional-form} is a problem family when $\theta$ is left
symbolic and a problem instance when $\theta$ is fixed to a numerical value; it generalizes the
parametric form \eqref{e:parametric-family} to the convex/concave inequalities and affine equalities
CVXPY accepts. Internally, CVXPY represents each function in \eqref{eq:functional-form}
as an expression tree.

\paragraph{Disciplined convex programming.}
When $f_0$ and all $f_i$ are convex, all $g_i$ are concave, and all $h_i$ and $j_i$ are
affine, the functional form defines a convex optimization problem.
To certify convexity, CVXPY uses the DCP composition rules to classify
the curvature of each function.
Once all functions are classified, a problem is \emph{DCP-compliant} if the objective and
each constraint have curvatures compatible with a convex problem: a convex objective,
convex $\leq$ concave inequalities, and affine equalities.

Otherwise, if a curvature is incompatible (\emph{e.g.}\ $f_0$ is concave) or cannot be
determined, CVXPY raises an error and terminates.
Because these rules are only sufficient for convexity, a problem that is genuinely convex
but not expressed in a recognized form may still be rejected.

\paragraph{Composition rules.}
The composition $\phi(f_1(x), f_2(x), \dots, f_k(x))$ of an atom $\phi$ with subexpressions $f_i$
is convex when $\phi$ is convex and, for each argument $i \in \{1, \dots, k\}$, one of the
following holds:
\begin{itemize}
    \item $\phi$ is non-decreasing in argument $i$ and $f_i$ is convex, or
    \item $\phi$ is non-increasing in argument $i$ and $f_i$ is concave, or
    \item $f_i$ is affine.
\end{itemize}
The same results hold for concave functions by swapping convex and concave.
Affine expressions require $\phi$ and all of its arguments to be affine \cite{grant2004disciplined}.

\paragraph{Functional conic form.}
Once a problem is verified to be DCP-compliant, the frontend of canonicalization
rewrites its functional form \eqref{eq:functional-form} into an equivalent \emph{functional conic form}
\BEQ\label{eq:conic-form}
\begin{array}{ll}
\mbox{minimize}   & f_0(x; \theta) \\
\mbox{subject to} & \ell_i(x; \theta) \in \mathcal K_i, \quad i = 1,\ldots,m,
\end{array}
\EEQ
where $f_0$ is affine or quadratic, each $\ell_i$ is affine, and each $\mathcal{K}_i$ is one of
the standard convex cones: the zero, nonnegative, second-order, power, exponential, and positive
semidefinite cones.

\paragraph{Reductions.}
This rewriting is carried out as a sequence of \emph{reductions}. Each reduction provides an
\texttt{apply} step that converts a problem into an equivalent one, and a \texttt{retrieve}
step that recovers a solution of the original problem from a solution of the rewritten one
\cite{agrawal2018rewriting}.

A first example is \texttt{FlipObjective}, which turns a maximization problem
into a minimization one by
flipping the sign of the objective; its \texttt{retrieve} step simply flips the sign back.

A second example, \texttt{CvxAttr2Constr}, handles variable attributes, which are properties
declared on a variable that restrict its domain. These include nonnegativity (\texttt{nonneg}),
positive semidefiniteness (\texttt{PSD}), and explicit variable bounds, amongst others.
When the target solver supports an attribute natively, CVXPY leaves it for the solver to enforce;
otherwise the reduction creates a new variable that carries no attributes and adds
explicit constraints that enforce the attribute. Its \texttt{retrieve} step then maps the
reformulated solution back onto the original attributed variable.

\paragraph{Conic reformulation.}
The main reduction, \texttt{Dcp2Cone}, rewrites every nonlinear atom into conic constraints.
The first step of the reduction is to rewrite the problem into \emph{Smith form}, where each
nonlinear atom is replaced by a new variable coupled with an equality constraint; every atom
then acts only on affine arguments \cite{smith1996}.
For a convex atom $\phi$, the Smith form gives an auxiliary variable $t$ with the equality
constraint $\phi(x) = t$. The second step relaxes this equality to the inequality $\phi(x) \le t$.
The DCP rules allow a convex atom only where its value is minimized or upper-bounded, so the solver
always prefers $t$ as small as possible; the relaxation is therefore \emph{lossless}.

The pair $(x, t)$ then lies in the \emph{epigraph} $\{(x, t) : \phi(x) \le t\}$ of $\phi$, so we
often refer to $t$ as an \emph{epigraph variable}.
A concave atom relaxes to $\phi(x) \ge t$ instead, giving a \emph{hypograph variable}.
The final step of the reduction expresses each epigraph (hypograph) inequality as the membership of
an affine function of $(x, t)$ in a convex cone \cite{grant2008graph}.

\paragraph{Example of reformulations.}
A first example is the $\ell_2$ norm atom $\|x\|_2$, whose epigraph $\|x\|_2 \le t$ is exactly the
second-order cone constraint $(t, x) \in \mathcal K_{\mathrm{soc}}$.
A second example is the nondifferentiable absolute value atom $|x|$, whose epigraph $|x| \le t$ can
be written smoothly as the pair of affine inequalities $-t \le x \le t$.
A final example is the sum of the $k$ largest entries of $x$, which expands into a small LP:
the epigraph $\mathrm{sum\_largest}(x, k) \le t$ holds if and only if there exist a scalar
$q$ and a vector $u$ such that
\BEQ\label{eq:sum-largest}
q\mathbf{1} + u \ge x, \qquad u \ge 0, \qquad kq + \mathbf{1}^\top u \le t.
\EEQ
Here $q$ acts as a threshold and each $u_i$ measures how far the entry $x_i$ rises above it, so that
the sum of the $k$ largest entries is bounded by $kq + \mathbf{1}^\top u$ \cite{boyd2004convex}.

\paragraph{Example of canonicalization.}
To show a concrete example of the frontend of canonicalization,
we consider a simple fitting with regularization problem
\BEQ
    \begin{array}{ll}
        \text{minimize} & \|Fx-g\|_2 + \mu \|x\|_2\\
        \text{subject to} & x \succeq 0\\
    \end{array}
      \label{eq:example}
\EEQ
with variable $x \in \reals^n$, fixed problem data $F\in \reals^{m\times n}$, and parameters
$g\in \reals^m$ and $\mu \geq 0$.
The problem formulation in CVXPY code is
\begin{lstlisting}[language=Python]
import cvxpy as cp
import numpy as np
F = np.random.randn(m, n)
x = cp.Variable(n)
g = cp.Parameter(m)
mu = cp.Parameter(nonneg=True)
objective = cp.Minimize(cp.norm(F @ x - g) + mu * cp.norm(x))
prob = cp.Problem(objective, [x >= 0])
\end{lstlisting}
where we also use the numerical computation library \texttt{NumPy} \cite{numpy} for
the data arrays. The expression tree representation of the problem
is shown in \ref{fig:dcp-expression-tree}.

\paragraph{Conic form expression tree.}
After applying the reductions, the problem has been \emph{canonicalized} to
\BEQ\label{eq:graph}
\begin{array}{ll}
  \mbox{minimize}  & t_1 + \mu t_2 \\
  \mbox{subject to}  &
x \in \reals_+^n \\
& (t_1, Fx -g) \in \mathcal K_{\mathrm{soc},m+1} \\
& (t_2, x) \in \mathcal K_{\mathrm{soc},n+1} \\
\end{array}
\EEQ
where $t_1$ and $t_2$ are new epigraph variables, and the cone $\mathcal K$ from
\ref{e:standard-form} is the product $\reals_+^n \times \mathcal K_{\mathrm{soc},m+1}
\times \mathcal K_{\mathrm{soc},n+1}$.
Problem \eqref{eq:graph} is now in the functional conic form introduced above: every constraint
is a cone membership, and the objective and constraint expressions are affine.
Comparing the DCP trees of \ref{fig:dcp-expression-tree} with the conic-form trees of
\ref{fig:conic-form-tree} shows the effect of canonicalization: the nonlinear norm atoms have been
replaced by epigraph variables, leaving affine expression trees in the variables.
The three rows of \eqref{eq:graph} remain three separate cone constraints, each carrying the
affine expressions that must lie in its cone; \ref{fig:conic-form-tree} accordingly shows one
expression tree per constraint, rather than a single combined tree.

\section{Matrix stuffing}
\label{sec:matrix-stuffing}

CVXPY takes the perspective of matrix calculus \cite{magnus2019matrix} for computing the
coefficient matrices of linear expressions; this is where most of the computational burden of
canonicalization lies. The section first develops this view, in which every affine atom becomes a
linear operator and assembling the problem data amounts to composing these operators over the
expression trees. It then examines how CVXPY carries out the composition and how parametrized
data is cached and updated, highlighting along the way important design differences with the
engine of \S\ref{sec:Theme1}.

\paragraph{Matrix calculus.}
Matrix calculus extends differentiation to functions whose arguments and values are vectors and
matrices. Systematic rules for such derivatives go back to Dwyer and Macphail
\cite{dwyer1948symbolic}: the derivative of a matrix-valued expression with respect to a matrix
variable is a four-dimensional object, and several competing conventions arrange its
entries \cite{magnus2019matrix}. The convention of Magnus and Neudecker, which CVXPY and this
thesis follow, removes the ambiguity by vectorization: every expression is identified with
\BEQ\label{eq:vec}
\vect(X) = \begin{bmatrix} x_{11} & \cdots & x_{m1} & x_{12} & \cdots & x_{mn} \end{bmatrix}^T,
\EEQ
the vector that stacks the columns of $X \in \reals^{m \times n}$, and the derivative of one
vectorized expression with respect to another is an ordinary Jacobian matrix. Under this
convention matrix operations become linear operators on the vectorized arguments, and their
Jacobians carry structure: for example
\BEQ\label{eq:vec-kron}
\vect(FX) = (I \otimes F)\,\vect(X),
\EEQ
so the matrix product $FX$ corresponds to the Kronecker-structured, block-diagonal Jacobian
$I \otimes F$. The convention is illustrated in \ref{fig:vec-variable}: as an expression, a
matrix variable is the identity map of its own entries, so its Jacobian is an identity block
whose columns are indexed by the entries of $\vect(X)$, and the Jacobian of the product $FX$ is
block-diagonal with one copy of $F$ per column of $X$.

\paragraph{Composing linear operators.}
After canonicalization every expression is affine, so each node of a conic-form tree can be
written in the vectorized form
\BEQ\label{eq:linop-form}
f(x) = A\,x + b
     = \begin{bmatrix} A & b \end{bmatrix} \begin{bmatrix} x \\ 1 \end{bmatrix},
\EEQ
where $x$ is the stacked vector of all variables, $A$ is the Jacobian of the node, constant
since $f$ is affine, and $b$ is a constant offset. Matrix stuffing computes the augmented matrix
$[A\ b]$ of every node in one bottom-up pass. A variable leaf contributes an identity block in
its own column slot, a constant leaf contributes its value to the offset column, and an interior
atom $g$ with arguments $f_1, \dots, f_k$ is a linear map $\sum_i L_i f_i$ whose constant
Jacobians $L_i$ apply directly to the augmented matrices of its children,
\BEQ\label{eq:linop-chain-rule}
\begin{bmatrix} A & b \end{bmatrix}
  = \sum_{i=1}^{k} L_i \begin{bmatrix} A_i & b_i \end{bmatrix}.
\EEQ
Computing the problem data thus amounts to composing many linear operators over the tree: the
node matrices of the figures in this section are exactly these augmented blocks, and at the root
of the constraint tree the augmented matrix is the problem data $[A\ b]$ itself.

\paragraph{Views and copies.}
The simple operators act as \emph{views}, modifying the augmented matrix of their argument in
place: negation flips the sign of every stored entry, indexing keeps the selected rows, and
reshaping costs nothing at all, since it leaves the vectorization of the expression unchanged.
The operators that create \emph{copies} are chiefly the bivariate atoms that carry data: one
operand of a matrix product, an elementwise multiplication or a division is constant under the
DCP rules, and the atom forms a matrix from that operand, multiplies it with the augmented
matrix of the other, and stores the product as new data. An expository subset is classified in
\ref{tab:views-copies}.

\paragraph{Local versus global derivatives.}
The augmented matrices of \eqref{eq:linop-form} can be laid out in two ways

Python indexing trick to refer to the last column, the offset $b$. The columns of a block index only the entries of its own
variable; only after the walk completes are the blocks shifted to their variables' column offsets
and concatenated into the full matrix $[A\ b]$. The alternative is a \emph{global} derivative, a
single Jacobian per node whose columns span the whole stacked vector $x$ from the outset. The
local layout keeps the blocks small and skips variables absent from a subtree, but every operator
must be dispatched over a dictionary of blocks; the engine of \S\ref{sec:Theme1} takes the global
route.

\paragraph{The \texttt{ignore\_dpp} path.}
Problems that fall outside the DPP grammar, or that opt out of it by solving with
\texttt{ignore\_dpp=True}, take a simpler path. The reduction \texttt{EvalParams} replaces each
parameter leaf by a constant holding its current value, and the parameter-free tree that results
is stuffed as if the problem had no parameters (\ref{fig:param-map-evalparams}). The path is
fully general, since arbitrary functions of parameters reduce to constants, but every change of
$\theta$ repeats the whole symbolic walk even though the sparsity pattern of the problem data
never changes. This is the regime the engine of \S\ref{sec:Theme1} improves.

\paragraph{Code generation.}
A third option is to compile the problem ahead of time. CVXPYgen emits problem-specific C code
that embeds the cached parameter map \eqref{eq:param-maps} of a DPP problem
\cite{schaller2022cvxpygen}, continuing an earlier line of work on code generation for embedded
second-order cone programs \cite{chu2013codegen}. The benchmarks of \S\ref{sec:Theme2} do not
compare against it: code generation is an offline step that fixes the problem structure at
compile time, a different deployment model from a runtime backend that must accept arbitrary
problems.

\paragraph{Implementation details.}
Three implementation details, shared by CVXPY's two backends, the C++ \texttt{cvxcore} and the
\texttt{SciPy} backend, stand out as limitations of the current approach; the engine of
\S\ref{sec:Theme1} does each differently.
\begin{itemize}
\item \emph{External sparse libraries.} Both backends delegate every matrix operation to a
general-purpose sparse library, Eigen \cite{guennebaud2010eigen} for \texttt{cvxcore} and
\texttt{scipy.sparse} \cite{2020SciPy-NMeth} for the \texttt{SciPy} backend. The storage formats and kernels are fixed by the library, leaving no
room to exploit structure known at canonicalization time.
\item \emph{Everything is sparse.} All coefficient data is treated as sparse: dense atom data
is converted to a sparse matrix on entry, and no operator carries a dense or block special
case, so dense blocks pay sparse-format overhead and no BLAS kernel is ever used.
\item \emph{Quadratic objectives are separate.} Each quadratic form is swapped for a dummy
variable, and the surrounding affine expression is stuffed by the same walk. The matrices of
the quadratic forms are then scaled by the resulting coefficients and reassembled into the
global objective matrix $P$.
\end{itemize}

\section{Computing derivatives}
\label{sec:computing-derivatives}

Finding the rate of change, or \emph{derivative}, of a function is a fundamental problem in many
fields of science and engineering.
Although computing derivatives may seem straightforward at first, there are many approaches, each
with its own trade-offs \cite{baydin2017ADsurvey}.
These approaches differ in four basic choices: whether the function is treated as a \emph{scalar}
or \emph{vectorized} expression, whether derivatives are propagated \emph{forward} or in
\emph{reverse}, whether the Jacobian or Hessian is assembled \emph{directly} or accessed through an
\emph{oracle} of matrix--vector products, and whether the resulting matrix is \emph{sparse} or
\emph{dense}.

The problem data for an optimization model is often large and sparse, so we place
particular emphasis on computing sparse derivatives in this section.
The standard approach in the literature is scalar and oracle-based differentiation
\cite{griewank2008evaluating}, where graph coloring is used to recover a sparse matrix in far fewer
oracle evaluations.
This thesis instead proposes to compute these sparse derivatives directly on a vectorized graph
whose sparsity pattern follows from the structure of the operations, so no coloring is needed.

The remainder of the section is structured as follows: we begin with a brief survey of the standard
numerical and symbolic methods, before turning to algorithmic differentiation.
Finally, we gather a range of relevant works, organizing them in a table according to their
particular approach to differentiation.

\paragraph{Numerical differentiation.}
Other than computing derivatives by hand, the simplest method is to use \emph{numerical
differentiation}, which approximates the derivative of a function at a point by evaluating the
function at nearby points using a \emph{finite difference} formula similar to either
\BEQ
f'(x) \approx \frac{f(x + h) - f(x)}{h},
\EEQ
or
\BEQ
f'(x) \approx \frac{f(x + h) - f(x - h)}{2h},
\EEQ
where $h$ is a small step size. Although this approach is straightforward to implement and
can achieve reasonable accuracy, there are important downsides to consider.
First, it requires a linear number of function evaluations with respect to the number of
input variables, which is expensive for high-dimensional functions.
Second, it can easily lead to \emph{truncation errors} (when $h$ is too large) or
\emph{rounding errors} (when $h$ is too small) in the computed derivative if the step size is
not carefully chosen \cite{chakravarti1961truncation}.
Despite these downsides, numerical differentiation is still widely used in practice,
especially for verifying the correctness of derivative computations (also known as a
\emph{derivative checker}) \cite{wolfe1982checking}.

\paragraph{Symbolic differentiation.}
Mathematical expressions can be manipulated automatically using simple derivative rules of
calculus, such as the product and sum rule. This \emph{symbolic} approach to differentiation
is used in computer algebra systems such as Mathematica \cite{mathematica} and Maple
\cite{maple} as well as the SymPy library in Python \cite{sympy2017}.
Unlike its numerical counterpart, symbolic differentiation tools compute derivatives as
closed-form expressions, which can be simplified and evaluated at any arbitrary point.
These closed-form expressions are particularly useful for deriving analytic solutions of
optimization problems, and can be further used in mathematical proofs and analyses.

However, a naive implementation of symbolic differentiation can quickly form exponentially
large symbolic expressions, which is impractical and inefficient for many problems
\cite{griewank2008evaluating}.
Interestingly, when intermediate expressions are stored as \emph{common subexpressions}, and
the expression is represented with a \emph{directed acyclic graph} (DAG) instead of a tree,
symbolic differentiation performs the same set of operations as \emph{reverse mode
differentiation} \cite{Laue2019OnTE}.

\paragraph{Algorithmic differentiation.}
\emph{Algorithmic differentiation} (AD) treats the function as a \emph{computational graph} of
elementary operations, each with a known local derivative rule.
The chain rule is then applied to combine these local derivatives throughout the graph, giving the
derivative of the whole function.
AD is also commonly referred to as \emph{automatic differentiation}; we prefer the term
\emph{algorithmic} to emphasize that AD differentiates the algorithm that computes a function,
rather than a numerical approximation or a symbolic formula \cite{griewank2008evaluating}.
In this broad sense, AD can refer to any method that applies the chain rule over a computational
graph. In the remainder of this section, we introduce the standard scalar and oracle-based 
differentiation methods, then contrast them with vectorized and direct approaches.

\paragraph{Scalar differentiation.}
The earliest and most foundational form of AD operates on a \emph{scalar} computational graph, where
every node is a single elementary operation (an addition, a multiplication, or a univariate
function such as $\sin$ or $\exp$), and every edge carries the corresponding scalar partial
derivative \cite{griewank2008evaluating, Naumann2011}.
Since each elementary operation has a simple and known derivative, the chain rule reduces to
multiplying and summing scalars along the graph.
Early AD tools such as ADOL-C \cite{griewank1996adolc} and CppAD \cite{bell2012cppad} form the
scalar graph by recording a runtime trace of every elementary operation. Such a trace can be enormous:
a single matrix--vector product $Ax$ unrolls into one scalar
multiplication for every entry of $A$, together with the additions that sum them, so it quickly
reaches millions of nodes for a realistic problem.

\paragraph{Modes of differentiation.}
The chain rule can be applied in different orders, all giving the same result. The two best-known are
\emph{forward mode} (or \emph{tangent} mode), which propagates derivatives from the inputs
toward the outputs, and \emph{reverse mode} (or \emph{adjoint} mode), which propagates them from the
outputs back toward the inputs \cite{baydin2017ADsurvey}.
The two modes have asymmetric costs: in forward mode the work scales with the number of inputs, and
in reverse mode with the number of outputs.
Reverse mode is therefore preferred when there are far fewer outputs than inputs,
such as computing the gradient of a scalar function.
Other mixed-ordering modes exist, commonly grouped under the umbrella term \emph{cross-country}
elimination \cite{griewank2008evaluating}. However, finding the best ordering on a general graph is difficult,
so these modes are rarely used in practice \cite{naumann2008optimal}.

\paragraph{First- and second-order derivatives.}
For a vector-valued map $F : \reals^n \to \reals^m$ of an input $x \in \reals^n$, the first-order
derivative is the \emph{Jacobian} $J \in \reals^{m \times n}$ of partial derivatives of the outputs
with respect to the inputs,
\BEQ\label{eq:jacobian}
  J_{ij} = \frac{\partial F_i}{\partial x_j}, \qquad i = 1, \dots, m, \quad j = 1, \dots, n.
\EEQ
For a scalar function $f : \reals^n \to \reals$, the second-order derivative is the \emph{Hessian}
$H \in \reals^{n \times n}$ of second partial derivatives,
\BEQ\label{eq:hessian}
  H_{ij} = \frac{\partial^2 f}{\partial x_i \, \partial x_j}, \qquad i, j = 1, \dots, n.
\EEQ
The Hessian is the Jacobian of the gradient of $f$, and is symmetric whenever $f$ is twice
continuously differentiable. It is therefore obtained by differentiating the gradient, with no method
beyond those used for the Jacobian.

\paragraph{Oracle-based differentiation.}
Instead of $J$ itself, AD returns its action on a vector: the Jacobian-vector product (JVP) $Jv$ in
forward mode, and the vector-Jacobian product (VJP) $J^\top w$ in reverse mode (for the Hessian, the
analogous Hessian-vector product $Hv$ comes from one forward pass over one reverse pass)
\cite{baydin2017ADsurvey}.
These matrix-vector products are obtained without ever forming $J$, each at about the cost of one
function evaluation. Borrowing terminology from numerical linear algebra, we call this the
\emph{matrix-free}, or \emph{oracle}, view of AD.
The oracle is sufficient for many applications; they never form the matrix and use only its action
on vectors, as in backpropagation for training neural networks or Krylov methods for linear systems.

\paragraph{Recovering the Jacobian.}
Recovering $J$ explicitly requires \emph{probing} the oracle with a sequence of seed vectors: the $n$
unit seeds recover it column by column in forward mode, and the $m$ unit seeds recover it row by row
in reverse mode (the Hessian is recovered the same way, though its symmetry permits fewer seeds)
\cite{griewank2008evaluating}.
When the Jacobian has many rows or columns this becomes prohibitively expensive, and reducing the
number of probes is exactly the purpose of the graph-coloring methods described next.
Crucially, coloring operates on the oracle alone, independently of how the underlying graph is built,
so even fully vectorized frameworks rely on it when they need an assembled sparse Jacobian.

\paragraph{Graph coloring.}
The cost of probing drops when several seeds share a single pass. Two columns of $J$ with no nonzero
in a common row are \emph{structurally orthogonal}, so one seed recovers both without their nonzeros
colliding. Finding the fewest such groups is a graph-coloring problem on the column intersection
graph, whose edges join columns that share a row
\cite{curtis1974estimation, coleman1983estimation, gebremedhin2005color}. The Hessian compresses
further: its symmetry admits dedicated star and acyclic colorings that use fewer colors than the
general Jacobian case \cite{Gebremedhin2009SparseHessians}.

\paragraph{Sparse derivatives.}
An oracle-based sparse Jacobian is obtained in three stages: \emph{detect} the sparsity pattern,
\emph{compress} it by coloring, and \emph{propagate} the compressed seeds through the oracle to
recover the nonzero entries \cite{hill2025sparser}. The pattern is computed once and reused, so its
cost is amortized across repeated evaluations of the same function. This pipeline underlies sparse AD
in oracle-based tools such as CasADi \cite{andersson2019}, which we revisit in
\S\ref{sec:coefficient-extraction}.

\paragraph{Vectorized differentiation.}
More recent frameworks coarsen the graph so that each node is a whole vector or matrix operation
rather than a single scalar. The local derivative of such a node is then a matrix, a block of the
Jacobian, and these blocks are combined by the rules of matrix calculus \cite{magnus2019matrix}.
The resulting graph has far fewer nodes than the scalar trace, which lets frameworks such as JAX
\cite{jax2018github} differentiate large programs efficiently. Vectorization alone, however, does not
change the assembly: these frameworks still expose only the oracle, and still rely on coloring when
they need an assembled sparse Jacobian.

\paragraph{Direct differentiation.}
Direct methods go a step further and abandon the oracle altogether. Rather than returning products,
they propagate the local Jacobian blocks themselves through the graph and combine them to form $J$
directly, so neither probing nor coloring is needed. Vectorization is the enabler: it gives each
block algebraic structure, whereas a scalar node carries only a $0/1$ dependency. Recent works apply
this idea in statistics \cite{kwok2025vectorised} and optimal control \cite{zou2025vectorized}.
Direct propagation wins when the local blocks are well structured and intermediate fill-in stays
bounded, while coloring through the oracle can still be cheaper when the intermediates densify.
Which assembly is preferable ultimately follows the solver that consumes the result: the conic
solvers targeted in this thesis require the matrix explicitly as data, which is exactly what the
direct approach produces.

\section{Sparse matrices}
\label{sec:sparse-matrices}

Matrices that contain many number of zero entries are known as \emph{sparse matrices}.
The simplest sparse matrix data structure is the \emph{coordinate} or \emph{triplet}
format. It consists of two integer index arrays \texttt{rows} and \texttt{cols} and a floating point
value array \texttt{vals} of length equal to the number of \emph{nonzero entries} in the matrix.

For example, the matrix
\BEQ\label{eq:sparse-matrix}
  \begin{bmatrix}
  0 & 0 & 3.2 & 0\\
  4.1 & 1.8 & 0 & 2.2\\
  0 & 2.8 & 0 & 3.4\\
  \end{bmatrix}
\EEQ
can be represented in coordinate format as
\begin{lstlisting}[language=C]
int     rows[] = {0,    1,    1,    1,    2,    2};
int     cols[] = {2,    0,    1,    3,    1,    3};
double vals[] = {3.2,  4.1,  1.8,  2.2,  2.8,  3.4};
\end{lstlisting}

where we use zero-based indexing and array declaration notation from the C programming
language \cite{Kernighan1988}.
The coordinate format is the easiest to understand and form, but it is not effective for most
operations on sparse matrices; the \emph{compressed sparse row} or CSR format is commonly
used instead.

\paragraph{Compressed sparse row format.}
The CSR format differs from the coordinate format in that it replaces the \texttt{rows} array with
a row pointer array \texttt{idxptr} of length equal to the number of rows plus one.
The row pointer array indicates the starting index of each row in the \texttt{cols} arrays.
For example, the matrix in \eqref{eq:sparse-matrix}
can be represented in CSR format as
\begin{lstlisting}[language=C]
int  idxptr[] = {0,    1,                4,         6};
int    cols[] = {2,    0,    1,    3,    1,    3};
double vals[] = {3.2,  4.1,  1.8,  2.2,  2.8,  3.4};
\end{lstlisting}
where we deliberately format \texttt{idxptr} to align with the start of each
row in the \texttt{cols} arrays.
% talk about benefits of CSR format. fast row slicing, fast matrix-vector products, etc.
The benefits of the CSR format are more than a reduced size of the \texttt{idxptr} array
compared to the \texttt{rows} array.
In the CSR format, accessing a row takes constant time and is very \emph{cache-friendly}
since the nonzero entries are stored contiguously in memory.
For this reason, the CSR format is the default for \emph{iterative methods}
to solve sparse linear systems \cite{saad2003iterative}.

\paragraph{Compressed sparse column format.}
% talk about CSC as a direct extension of CSR but with column pointers.
However, one downside of the CSR format is that accessing a column is much more difficult;
one would need to look at every row to find the nonzero entries in a column.
An alternative format is the \emph{compressed sparse column} or CSC format, 
which swaps the role of the \texttt{idxptr} array to refer to column indices instead.
In contrast to iterative methods, the CSC format is the preferred format for
\emph{direct methods} to solve sparse linear systems \cite{davis2006direct}.

\paragraph{Other formats.}
The coordinate, CSR and CSC formats are the most widely used sparse matrix formats,
but many others exist for different specialized use cases.
The scientific Python sparse library \texttt{scipy.sparse} \cite{2020SciPy-NMeth}
allows users to form other types of sparse matrices such as the list of lists (LIL) matrix,
the dictionary of keys (DOK) matrix, and the block-sparse row (BSR) matrix.
