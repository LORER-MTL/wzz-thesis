\paragraph{History and background}
Since the early days of linear programming (LP), practitioners have needed to translate
mathematical formulations into data that solvers can process.
At first, this meant encoding each coefficient of the problem matrices by hand, a process
that is both tedious and error-prone~\cite{fourer1978modern}.
\emph{Matrix generators} were introduced in the late 1960s to automate this task: they compute the
coefficients through explicit loops and write them out in solver-readable formats like
MPS~\cite{marceau1971matrix, ibm1976mpsx}.

Despite matrix generators removing most of the manual labor, a gap remained.
Modelers naturally think in terms of sets, indices, and algebraic expressions,
while procedural code constructs the coefficient matrices entry by entry.
This mismatch between how a model is expressed and how it is implemented made them difficult to
verify, modify, and communicate with others \cite{fourer1983modeling}.
\emph{Algebraic modeling languages} such as AMPL \cite{fourer1990ampl},
AIMMS \cite{bisschop2006aimms} and GAMS \cite{brooke1988gams} closed this gap by accepting
problem descriptions that closely follow the math.
For a more complete overview of the early history of modeling languages refer to
\cite{orchard-hays1984history}.

More recently, modeling languages embedded in general-purpose programming languages have
gained popularity, such as Pyomo \cite{bynum2021pyomo, hart2011pyomo} in Python,
JuMP \cite{dunning2017jump} in Julia, and CasADi \cite{andersson2019} in C++.
Other domain-specific modeling languages specialized for convex optimization \cite{boyd2004convex}
are built on \emph{disciplined convex programming} (DCP), a set of composition rules under which
the convexity of a problem can be verified
automatically \cite{grant2004disciplined, grant2006disciplined}.
These DCP-based languages include CVX \cite{cvx} in MATLAB, CVXR \cite{Fu_2020} in R,
CVXPY \cite{diamond2016cvxpy} in Python, and Convex.jl \cite{udell2014convex} in Julia.

\paragraph{Structure of the chapter}
The first two sections focus on CVXPY: it is the most actively maintained DCP implementation,
and the work of this thesis aims to be integrated into it.
\S\ref{sec:canonicalization} covers the \emph{frontend} of canonicalization, which rewrites the
user's functional form into a functional conic form of purely affine and quadratic expressions.
\S\ref{sec:matrix-stuffing} covers its \emph{backend}, \emph{matrix stuffing}, which assembles
the problem data from this functional conic form.

Because the problem data assembled this way is exactly a sparse Jacobian of the canonicalized
form, \S\ref{sec:computing-derivatives} reviews the methods available for computing sparse
derivatives.
\S\ref{sec:coefficient-extraction} then revisits the same task from the side of other modeling
systems: it presents the embedded modeling languages JuMP and CasADi as well as the algebraic
language AMPL as instances of that machinery, and compares how each one extracts the problem
data with the approach taken in CVXPY.
Finally, \S\ref{sec:sparse-matrices} covers the sparse matrix formats used to store the
problem data, along with some useful algorithms for manipulating them.

\section{Canonicalization}
\label{sec:canonicalization}

CVXPY is a DCP-based modeling language embedded in Python \cite{diamond2016cvxpy},
which began in 2013 as an implementation of the modeling principles of CVX \cite{cvx}.
Three fundamental design decisions differed from CVX at the beginning.
The first is modularity: a few core data structures are shared by separate components for
verification, canonicalization, matrix stuffing, and solver interfaces.
The second is the expression tree as the central data structure, which is formed
automatically from user code through Python's operator overloading.
The third is support for parameters: since canonicalization never looks at the values of
constants, much of the compilation work can be reused when a problem is solved repeatedly.

These ideas matured with version 1.0, which redesigned canonicalization as
a general reduction-based rewriting system \cite{agrawal2018rewriting}.
The new design enabled the addition of other disciplined
grammars \cite{agrawal2019dgp, agrawal2020dqcp, cederberg2025disciplined}, and the early
parameter support grew into disciplined parameterized programming (DPP), a restricted grammar
under which canonicalized programs can be updated efficiently \cite{agrawal2019dpp}.

The open source project has since grown through contributions from many other enthusiastic
developers; a recent paper surveys the new canonicalization and modeling features
introduced between versions 1.1 and 1.9 \cite{zhang2026cvxpy}.

\paragraph{Functional form.}
A user most naturally expresses a CVXPY problem in \emph{functional} form,
\begin{equation}\label{eq:functional-form}
\begin{array}{ll}
\mbox{minimize}   & f_0(x; \theta) \\
\mbox{subject to} & f_i(x; \theta) \leq g_i(x; \theta), \quad i=1,\ldots,m_1,\\
                  & h_i(x; \theta) = j_i(x; \theta), \quad i=1,\ldots,m_2,
\end{array}
\end{equation}
where the optimization variables $x_1,\ldots,x_k$ are collected into a single
vector $x \in \reals^n$, and likewise the parameters $\theta_1,\ldots,\theta_l$
into $\theta \in \reals^p$ \cite{boyd2004convex}.
We call \eqref{eq:functional-form} a problem \emph{instance} when $\theta$ is
fixed to a numerical value, and a problem \emph{family} when $\theta$ is left
symbolic. Internally, CVXPY represents each function in \eqref{eq:functional-form}
as an expression tree.

\paragraph{Disciplined convex programming.}
When $f_0$ and all $f_i$ are convex, all $g_i$ are concave, and all $h_i$ and $j_i$ are
affine, the functional form defines a convex optimization problem.
To certify convexity, CVXPY uses the DCP composition rules to classify
the curvature of each function.
Once all functions are classified, a problem is \emph{DCP-compliant} if the objective and
each constraint have curvatures compatible with a convex problem: a convex objective,
convex $\leq$ concave inequalities, and affine equalities.

Otherwise, if a curvature is incompatible (\emph{e.g.}\ $f_0$ is concave) or cannot be
determined, CVXPY raises an error and terminates.
Because these rules are only sufficient for convexity, a problem that is genuinely convex
but not expressed in a recognized form may still be rejected.

\paragraph{Composition rules.}
The composition $\phi(f_1(x), f_2(x), \dots, f_k(x))$ of an atom $\phi$ with subexpressions $f_i$
is convex when $\phi$ is convex and, for each argument $i \in \{1, \dots, k\}$, one of the
following holds:
\begin{itemize}
    \item $\phi$ is non-decreasing in argument $i$ and $f_i$ is convex, or
    \item $\phi$ is non-increasing in argument $i$ and $f_i$ is concave, or
    \item $f_i$ is affine.
\end{itemize}
The same results hold for concave functions by swapping convex and concave.
Affine expressions require $\phi$ and all of its arguments to be affine \cite{grant2004disciplined}.

\paragraph{Functional conic form.}
Once a problem is verified to be DCP-compliant, the frontend of canonicalization
rewrites its functional form \eqref{eq:functional-form} into an equivalent \emph{functional conic form}
\begin{equation}\label{eq:conic-form}
\begin{array}{ll}
\mbox{minimize}   & f_0(x; \theta) \\
\mbox{subject to} & \ell_i(x; \theta) \in \mathcal K_i, \quad i = 1,\ldots,m,
\end{array}
\end{equation}
where $f_0$ is affine or quadratic, each $\ell_i$ is affine, and each $\mathcal{K}_i$ is one of
the standard convex cones: the zero, nonnegative, second-order, power, exponential, and positive
semidefinite cones.

\paragraph{Reductions.}
This rewriting is carried out as a sequence of \emph{reductions}. Each reduction provides an
\texttt{apply} step that converts a problem into an equivalent one, and a \texttt{retrieve}
step that recovers a solution of the original problem from a solution of the rewritten one
\cite{agrawal2018rewriting}.

A first example is \texttt{FlipObjective}, which turns a maximization problem
into a minimization one by
flipping the sign of the objective; its \texttt{retrieve} step simply flips the sign back.

A second example, \texttt{CvxAttr2Constr}, handles variable attributes, which are properties
declared on a variable that restrict its domain. These include nonnegativity (\texttt{nonneg}),
positive semidefiniteness (\texttt{PSD}), and explicit variable bounds, amongst others.
When the target solver supports an attribute natively, CVXPY leaves it for the solver to enforce;
otherwise the reduction creates a new variable that carries no attributes and adds
explicit constraints that enforce the attribute. Its \texttt{retrieve} step then maps the
reformulated solution back onto the original attributed variable.

\paragraph{Conic reformulation.}
The main reduction, \texttt{Dcp2Cone}, rewrites every nonlinear atom into conic constraints.
The first step of the reduction is to rewrite the problem into \emph{Smith form}, where each
nonlinear atom is replaced by a new variable coupled with an equality constraint; every atom
then acts only on affine arguments \cite{smith1996}.
For a convex atom $\phi$, the Smith form gives an auxiliary variable $t$ with the equality
constraint $\phi(x) = t$. The second step relaxes this equality to the inequality $\phi(x) \le t$.
The DCP rules allow a convex atom only where its value is minimized or upper-bounded, so the solver
always prefers $t$ as small as possible; the relaxation is therefore \emph{lossless}.

The pair $(x, t)$ then lies in the \emph{epigraph} $\{(x, t) : \phi(x) \le t\}$ of $\phi$, so we
often refer to $t$ as an \emph{epigraph variable}.
A concave atom relaxes to $\phi(x) \ge t$ instead, giving a \emph{hypograph variable}.
The final step of the reduction expresses each epigraph (hypograph) inequality as the membership of
an affine function of $(x, t)$ in a convex cone \cite{grant2008graph}.

\paragraph{Example of reformulations.}
A first example is the $\ell_2$ norm atom $\|x\|_2$, whose epigraph $\|x\|_2 \le t$ is exactly the
second-order cone constraint $(t, x) \in \mathcal K_{\mathrm{soc}}$.
A second example is the nondifferentiable absolute value atom $|x|$, whose epigraph $|x| \le t$ can
be written smoothly as the pair of affine inequalities $-t \le x \le t$.
A final example is the sum of the $k$ largest entries of $x$, which expands into a small LP:
the epigraph $\mathrm{sum\_largest}(x, k) \le t$ holds if and only if there exist a scalar
$q$ and a vector $u$ such that
\begin{equation}\label{eq:sum-largest}
q\mathbf{1} + u \ge x, \qquad u \ge 0, \qquad kq + \mathbf{1}^\top u \le t.
\end{equation}
Here $q$ acts as a threshold and each $u_i$ measures how far the entry $x_i$ rises above it, so that
the sum of the $k$ largest entries is bounded by $kq + \mathbf{1}^\top u$ \cite{boyd2004convex}.

\paragraph{Example of canonicalization.}
To show a concrete example of the frontend of canonicalization,
we consider a simple fitting with regularization problem
\begin{equation}
    \begin{array}{ll}
        \text{minimize} & \|Fx-g\|_2 + \mu \|x\|_2\\
        \text{subject to} & x \succeq 0\\
    \end{array}
      \label{eq:example}
\end{equation}
with variable $x \in \reals^n$, fixed problem data $F\in \reals^{m\times n}$, and parameters
$g\in \reals^m$ and $\mu \geq 0$.
The problem formulation in CVXPY code is
\begin{lstlisting}[language=Python]
import cvxpy as cp
import numpy as np
F = np.random.randn(m, n)
x = cp.Variable(n)
g = cp.Parameter(m)
mu = cp.Parameter(nonneg=True)
objective = cp.Minimize(cp.norm(F @ x - g) + mu * cp.norm(x))
prob = cp.Problem(objective, [x >= 0])
\end{lstlisting}
where we also use the numerical computation library \texttt{NumPy} \cite{numpy} for
the data arrays. The expression tree representation of the problem
is shown in \ref{fig:dcp-expression-tree}.

\paragraph{Conic form expression tree.}
After applying the reductions, the problem has been \emph{canonicalized} to
\begin{equation}\label{eq:graph}
\begin{array}{ll}
  \mbox{minimize}  & t_1 + \mu t_2 \\
  \mbox{subject to}  &
x \in \reals_+^n \\
& (t_1, Fx -g) \in \mathcal K_{\mathrm{soc},m+1} \\
& (t_2, x) \in \mathcal K_{\mathrm{soc},n+1} \\
\end{array}
\end{equation}
where $t_1$ and $t_2$ are new epigraph variables, and the cone $\mathcal K$ from
\ref{e:standard-form} is the product $\reals_+^n \times \mathcal K_{\mathrm{soc},m+1}
\times \mathcal K_{\mathrm{soc},n+1}$.
Problem \eqref{eq:graph} is now in the functional conic form introduced above: every constraint
is a cone membership, and the objective and constraint expressions are affine.
Comparing the DCP trees of \ref{fig:dcp-expression-tree} with the conic-form trees of
\ref{fig:conic-form-tree} shows the effect of canonicalization: the nonlinear norm atoms have been
replaced by epigraph variables, leaving affine expression trees in the variables.
The three rows of \eqref{eq:graph} remain three separate cone constraints, each carrying the
affine expressions that must lie in its cone; \ref{fig:conic-form-tree} accordingly shows one
expression tree per constraint, rather than a single combined tree.

Whichever path CVXPY takes, matrix stuffing ends in the same place: a set of constant, sparse
problem-data matrices read off from the canonicalized affine form.
These matrices are nothing other than the sparse Jacobian of that form with respect to the
variables, and every modeling language must produce them in one guise or another.
We therefore review in \S\ref{sec:computing-derivatives} how sparse derivatives are computed,
before returning in \S\ref{sec:coefficient-extraction} to how each system carries out this
extraction.

\section{Computing derivatives}
\label{sec:computing-derivatives}

Finding the rate of change, or \emph{derivative}, of a function is a fundamental problem in many
fields of science and engineering.
Although computing derivatives may seem straightforward at first, there are many approaches, each
with its own advantages and trade-offs \cite{baydin2017ADsurvey}.
These approaches differ in four basic choices: whether the function is treated as a \emph{scalar}
or \emph{vectorized} expression, whether derivatives are propagated \emph{forward} or in
\emph{reverse}, whether the Jacobian or Hessian is assembled \emph{directly} or accessed through an
\emph{oracle} of matrix--vector products, and whether the resulting matrix is \emph{sparse} or
\emph{dense}.

The problem data for an optimization model is often large and sparse, so we place
particular emphasis on computing sparse derivatives in this section.
The standard approach in the literature is scalar and oracle-based differentiation
\cite{griewank2008evaluating}, where graph coloring is used to recover a sparse matrix in far fewer
oracle evaluations.
This thesis instead proposes to compute these sparse derivatives directly on a vectorized graph
whose sparsity pattern follows from the structure of the operations, so no coloring is needed.

The remainder of the section is structured as follows: we begin with a brief survey of the standard
numerical and symbolic methods, then cover \emph{algorithmic differentiation} (AD) from the
perspective of these four choices.
Finally, we gather a range of relevant works, organizing them in a table according to their
particular approach to differentiation.

\paragraph{Numerical differentiation.}
Other than computing derivatives by hand, the simplest method is to use \emph{numerical
differentiation}, which approximates the derivative of a function at a point by evaluating the
function at nearby points using a \emph{finite difference} formula similar to either
\begin{equation}
f'(x) \approx \frac{f(x + h) - f(x)}{h},
\end{equation}
or
\begin{equation}
f'(x) \approx \frac{f(x + h) - f(x - h)}{2h},
\end{equation}
where $h$ is a small step size. Although this approach is straightforward to implement and
can achieve reasonable accuracy, there are important downsides to consider.
First, it requires a linear number of function evaluations with respect to the number of
input variables, which is expensive for high-dimensional functions.
Second, it can easily lead to \emph{truncation errors} (when $h$ is too large) or
\emph{rounding errors} (when $h$ is too small) in the computed derivative if the step size is
not carefully chosen \cite{chakravarti1961truncation}.
Despite these downsides, numerical differentiation is still widely used in practice,
especially for verifying the correctness of derivative computations (also known as a
\emph{derivative checker}) \cite{wolfe1982checking}.

\paragraph{Symbolic differentiation.}
Mathematical expressions can be manipulated automatically using simple derivative rules of
calculus, such as the product and sum rule. This \emph{symbolic} approach to differentiation
is used in computer algebra systems such as Mathematica \cite{mathematica} and Maple
\cite{maple} as well as the SymPy library in Python \cite{sympy2017}.
Unlike its numerical counterpart, symbolic differentiation tools compute derivatives as
closed-form expressions, which can be simplified and evaluated at any arbitrary point.
These closed-form expressions are particularly useful for deriving analytic solutions of
optimization problems, and can be further used in mathematical proofs and analyses.

However, a naive implementation of symbolic differentiation can easily lead to exponentially
large symbolic expressions, which is impractical and inefficient for many problems
\cite{griewank2008evaluating}.
Interestingly, when intermediate expressions are stored as \emph{common subexpressions}, and
the expression is represented with a \emph{directed acyclic graph} (DAG) instead of a tree,
symbolic differentiation performs the same set of operations as \emph{reverse mode
differentiation} \cite{Laue2019OnTE}.

\paragraph{Forward mode AD.}
The method of propagating tangents forward through the computational graph is known as
\emph{forward mode} AD.
A single forward pass simultaneously computes the value and derivative of every intermediate
variable with respect to a single input variable, giving the sensitivity of all outputs to
that input.
The cost of a forward pass is a small constant factor of the cost of evaluating the original
function, since each elementary operation is augmented with at most a few additional
arithmetic operations for the derivatives.
However, one downside of forward mode AD is that the number of forward passes scales linearly
with the number of input variables, which is impractical for certain functions (which have
many input variables and very few output variables).

\paragraph{Reverse mode AD.}
In contrast to forward mode, \emph{reverse mode} AD propagates adjoints backward through the
computational graph.
It first requires a forward pass to compute and store the value of every intermediate
variable, and it then performs a reverse pass to compute the sensitivities of a single output
variable with respect to all input variables.
The cost of a reverse pass is also a small constant factor of the cost of evaluating the
original function, but the number of passes required now scales linearly with the number of
output variables rather than the number of input variables.
This makes reverse mode AD particularly efficient for computing gradients of scalar-valued
functions, making it the default method for modern machine learning libraries such as Jax
\cite{jax2018github}, Pytorch \cite{pytorch2019}, and Tensorflow \cite{tensorflow2016}.

\paragraph{From scalar gradients to sparse problem data.}
The methods above were developed for the dominant use of AD: computing a dense gradient of a
scalar-valued function. Extracting optimization problem data instead calls for a large, sparse
Jacobian of a vector-valued function, and reaching it takes two independent shifts in how
derivatives are computed, which we take in turn.

\paragraph{Scalar versus vectorized graphs.}
The first shift concerns whether the computational graph is \emph{scalar} or \emph{vectorized}.
In a \emph{scalar} graph each node is a single scalar operation, so a matrix product $Ax$ with
$A \in \reals^{m \times n}$ expands into roughly $mn$ multiplication and addition nodes, and the local
derivative attached to each edge is a single number.
In a \emph{vectorized} graph the same product is one node, and its local derivative is no longer a
scalar but a \emph{structured linear operator}.
In the matrix differential calculus of Magnus and Neudecker \cite{magnus2019matrix} these operators
take a compact form built from Kronecker products, diagonal matrices, and selection matrices; the
differential of a matrix product $C = AB$, for instance, is
$\mathrm{d}\,\mathrm{vec}\,C = (B^\top \otimes I)\,\mathrm{d}\,\mathrm{vec}\,A
+ (I \otimes A)\,\mathrm{d}\,\mathrm{vec}\,B$.
Differentiation in a vectorized graph is therefore the \emph{composition of linear operators} rather
than the accumulation of scalar chain-rule products, and each local operator carries the
macro-structure of its operation instead of shattering it into individual entries.
This choice governs both the size of the graph---$O(mn)$ scalar nodes against a handful of array
nodes---and the shape of the local derivatives.
Scalar graphs underlie classical AD tools such as ADOL-C \cite{griewank1996adolc} and CppAD
\cite{bell2012cppad}, whereas a recent line of work computes derivatives in vectorized, sparse,
forward-mode form across several domains: optimal control \cite{zou2025vectorized}, statistical
estimation \cite{kwok2025vectorised}, and sparse-tensor differentiable programming
\cite{shaikhha2023sparse}.

\paragraph{Dense versus sparse derivatives.}
The second shift concerns the \emph{data format} in which the derivative is carried.
A dense representation stores every entry of the Jacobian, including the structural zeros; a
\emph{sparse} representation stores and propagates only the nonzeros.
For the matrices that arise in optimization this distinction is decisive: a constraint matrix with
millions of entries may have only a few nonzeros per row, so forming it densely is not merely
wasteful but often infeasible.
Keeping the derivative sparse means representing it in one of the compressed formats discussed in
\S\ref{sec:sparse-matrices} and arranging every elementary operation to act on the nonzeros alone.
The two shifts are independent: a graph may be scalar or vectorized regardless of whether its
derivatives are dense or sparse, and it is their \emph{combination}---a vectorized graph carrying
sparse derivatives---that the data-extraction problem of this thesis calls for.
What remains is the question of \emph{how} the sparse matrix is actually produced, and here the
literature divides into two routes.

\paragraph{Sparse Jacobians by coloring.}
The first route never forms the Jacobian explicitly.
A single AD pass does not return the matrix; what it returns depends on what is propagated through the
graph.
Propagating one seed vector gives a \emph{matrix-free}, or \emph{oracle}, primitive: a forward pass
returns the \emph{Jacobian--vector product} $Jv$ and a reverse pass the \emph{vector--Jacobian
product} $w^\top J$, each a projection of $J$ that costs about one evaluation of the function
\cite{baydin2017ADsurvey}.
To recover the matrix itself one repeats the pass over a basis of seed directions---$n$ of them in
the worst case.
When $J$ is sparse this basis can be compressed: two columns that are never both nonzero in the same
row are \emph{structurally orthogonal} and can be recovered together from a single combined seed, so
minimizing the number of seeds becomes a graph-coloring problem on a graph built from the sparsity
pattern.
This idea was introduced by Curtis, Powell, and Reid \cite{curtis1974estimation} and cast as a
coloring problem by Coleman and Moré \cite{coleman1983estimation}; the survey of Gebremedhin, Manne,
and Pothen \cite{gebremedhin2005color} unifies its many variants.
A further ingredient is \emph{sparsity detection}---recovering the pattern itself when it is not given
in advance---which modern operator-overloading systems perform automatically and which has become the
dominant cost of the pipeline \cite{hill2025sparser}.
Seen this way, coloring is a means of \emph{recovering} a structure that the matrix-free route has
discarded: because the matrix is never formed, its pattern must be rediscovered and then probed
through the oracle.
Vectorization alone does not remove this cost---CasADi's matrix-valued \texttt{MX} graph is
vectorized, yet to extract the sparse matrices $H$ and $A$ it still detects their pattern and colors
it to recover the entries from a few seeded sweeps (\S\ref{sec:coefficient-extraction}).

\paragraph{Direct sparse accumulation.}
The second route keeps the derivative sparse and assembles the matrix directly.
Each elementary operation contributes a local Jacobian, and composing these---in the language of
Griewank and Walther \cite{griewank2008evaluating}, \emph{eliminating} the intermediate vertices of
the graph---yields $J$ itself, with no seed directions.
Assembling the matrix this way does not require storing the Jacobian of every intermediate variable:
in a bottom-up pass each local contribution is folded into its successor and then released, so only
the final matrix and the operands of the step in progress need be held at once.
Forward and reverse mode are simply two orderings in which the vertices are eliminated, and choosing
the order that minimizes the arithmetic is the \emph{optimal Jacobian accumulation} problem, which is
NP-complete on a general graph \cite{naumann2008optimal} and remains so even structurally, under
vertex elimination \cite{bentert2025structural}.
This combinatorial difficulty, however, is specific to dense, scalar graphs: on a vectorized graph
the local Jacobians are structured sparse operators, the graph itself is small, and a single
bottom-up pass forms the matrix directly and cheaply, so neither a seed basis nor a search over
elimination orders is required.
The idea of carrying the derivative as a sparse object is not new: the SparsLinC library of ADIFOR
already propagated derivative objects as sparse vectors with \emph{dynamic sparsity}, exploiting
structure as the computation proceeded rather than recovering it afterwards by coloring
\cite{bischof1996sparse}, and collected matrix-derivative rules give the forward and reverse
sensitivities of products, inverses, and factorizations at the level of whole array operations
\cite{giles2008collected}.
The recent vectorized, forward, sparse methods \cite{zou2025vectorized, kwok2025vectorised,
shaikhha2023sparse} and the coefficient extractor of this thesis belong to this direct lineage; what
they share is an array-level graph with analytically known per-operation sparsity, so that the full
sparse matrix is composed in a single pass without ever forming a seed basis.

\paragraph{Sparse Hessians.}
The same two routes reappear for second derivatives.
The matrix-free route assembles the Hessian as the Jacobian of the gradient and exploits symmetry
through \emph{star} and acyclic colorings, which recover a pair of mirror entries $H_{ij}$ and
$H_{ji}$ from a single seed \cite{Gebremedhin2009SparseHessians}; this is how CasADi forms the
objective Hessian $P$, by a forward-over-reverse sweep over a star-colored seed matrix
(\S\ref{sec:coefficient-extraction}).
The direct route instead builds the sparse Hessian on the graph itself: the edge-pushing algorithm
accumulates it together with its values in a single pass, bypassing detection, coloring, and
compression \cite{gower2012new}; at a coarser grain, AMPL reaches the same end by exploiting the
partial separability of a scalar model \cite{gay1991automatic}.
The coefficient extractor of this thesis follows the direct route for the objective Hessian of a
quadratic program, assembling it as a structured sum of sparse blocks whose pattern is fixed in
advance, with no symmetric coloring required.

\paragraph{Differentiation packages.}
A wide range of AD software exists.
For \texttt{C} and \texttt{C++}, ADOL-C \cite{griewank1996adolc} and CppAD \cite{bell2012cppad}
implement scalar operator overloading, recording an evaluation trace that is then replayed in
either mode.
Source-to-source tools instead transform the program at compile time: Tapenade
\cite{hascoet2013tapenade} for \texttt{Fortran} and \texttt{C}, and Enzyme \cite{moses2020enzyme}
at the level of the \texttt{LLVM} intermediate representation, which lets it differentiate code
written in any compiled language.
In the deep-learning setting, the reverse mode of Jax \cite{jax2018github}, Pytorch
\cite{pytorch2019}, and Tensorflow \cite{tensorflow2016} operates on vectorized graphs but returns
dense gradients; sparse autograd is only beginning to appear there, for instance differentiating
through sparse linear solves \cite{chi2026torchsla}.
The optimization-oriented frameworks AMPL \cite{gay1991automatic} and CasADi \cite{andersson2019}
are examined in detail in \S\ref{sec:coefficient-extraction}.

\paragraph{Summary.}
The methods surveyed here can be characterized by four choices: the \emph{expression type} (scalar or
vectorized), the \emph{mode} (forward, reverse, or both), whether the Jacobian is formed
\emph{directly} or matrix-free through an \emph{oracle}, and the \emph{data format} of the
derivatives (sparse or dense).
Table~\ref{tab:ad-landscape} places the main tools and recent works according to these choices.
The coefficient extractor developed in this thesis occupies the cell of vectorized, forward,
direct, and sparse differentiation, which it shares with the recent works of Zou and
Jiang \cite{zou2025vectorized}, Kwok et al.\ \cite{kwok2025vectorised}, and $\nabla$SD
\cite{shaikhha2023sparse}.
What distinguishes the present work is the program being differentiated: because it is the affine
tree produced by canonicalization, the sparsity pattern is known per atom and the Jacobian recovered
is exactly the constant conic problem data, so graph coloring never enters the picture.
This connection between coefficient extraction and differentiation, obvious in hindsight, is the
starting point for the methodology developed in this thesis.

\section{Coefficient extraction}
\label{sec:coefficient-extraction}

Matrix stuffing is CVXPY's particular answer to a task that every modeling language must
perform: converting a symbolic model into the numerical problem data consumed by a solver.
In this section, we review how three other modeling systems approach this \emph{coefficient
extraction} task and contrast their designs with CVXPY.

\paragraph{\texttt{JuMP}.}

JuMP is an algebraic modeling language embedded in Julia whose development started in 2012 at
the MIT Operations Research Center by Iain Dunning, Joey Huchette, and Miles Lubin, with a
first public release in 2013 \cite{dunning2017jump, lubin2023jump10recent}.
It is now maintained by a team of core contributors, with Oscar Dowson as its most active
maintainer.
Unlike CVXPY, JuMP performs no convexity verification; it belongs to the derivative-based
modeling paradigm, where the user is responsible for the properties of the formulation.
Coefficient extraction in JuMP is \emph{eager}: the \texttt{@constraint} and
\texttt{@objective} macros rewrite the user's code at parse time into loops that build each
affine expression as a sparse list of terms (an ordered dictionary mapping variables to
coefficients).
This macro rewriting avoids the asymptotic blowup of naive operator overloading, where summing
$d$ terms with repeated calls to \texttt{+} copies partial sums of growing size.
As a consequence, the problem data is scalarized one constraint at a time while the model is
being built, whereas CVXPY retains whole expression trees until solve time.

\paragraph{\texttt{MathOptInterface}.}

JuMP communicates with solvers through MathOptInterface (MOI), an abstraction layer whose
standard form is to minimize $f_0(x)$ subject to constraints $f_i(x) \in S_i$, where the
functions $f_i$ and sets $S_i$ are drawn from predefined lists \cite{legat2020mathoptinterface}.
There is deliberately no single canonical form: each solver advertises the function-set pairs
it supports natively, and unsupported constraints are rewritten by \emph{bridges}, local
transformations selected per constraint type by a shortest-path search over a hypergraph of
possible reformulations.
Bridges play the same role as CVXPY's reductions, but they are chosen just-in-time as
constraints are added to the model, rather than applied as a global pass over the whole problem.
The constraint matrix only materializes inside the solver wrapper.
When the model is copied to the solver, MOI assembles the affine terms of all constraints into
a single sparse matrix in compressed sparse column (CSC) format through a two-pass, sort-free
procedure: a first pass counts the nonzeros falling in each column and a prefix sum turns these
counts into the column pointers, sizing the row and value arrays to exactly the number of
nonzeros; a second pass scatters each term into its slot using a per-column cursor.
The column indices are stored either one-based, for an allocation-free view as a native sparse
matrix, or zero-based, so the arrays can be handed directly to a C solver.
This assembly is the same coordinate-to-CSC computation of \S\ref{sec:sparse-matrices}, but it
is carried out for a single fully numeric instance: the standard form $f_i(x) \in S_i$ admits no
symbolic parameters, so re-solving with changed data requires rebuilding the affine terms or
modifying individual coefficients in place and re-copying to the solver.
There is no precompiled map from a parameter vector to the problem data of the kind CVXPY
caches~(\ref{eq:param-maps}); even \texttt{ParametricOptInterface.jl}, which adds parameters to
the JuMP ecosystem, substitutes their fixed values and re-optimizes rather than applying a
reusable sparse parameter-to-data map.

AMPL is one of the original standalone algebraic modeling languages, developed by Robert
Fourer, David Gay, and Brian Kernighan at Bell Laboratories and Northwestern
University \cite{fourer1990ampl} to replace the error-prone matrix generators that
practitioners previously wrote by hand \cite{fourer1983modeling}.
An AMPL model is purely symbolic, with variables and constraints indexed over sets; the AMPL
translator instantiates the model with data, applies a presolve, and writes the problem
instance to a \texttt{.nl} file that is read by the solver \cite{gay2005writing}.
The file splits each constraint into a linear part, stored as sparse coefficient lists along
with the Jacobian sparsity pattern, and a nonlinear part, stored as an expression graph in
Polish prefix notation.
Inside the solver process, the AMPL Solver Library (ASL) reads the file, exposes the linear
coefficients (in CSC format if the solver requests it), and evaluates the nonlinear Jacobian
entries with reverse mode algorithmic differentiation (AD) on the expression
graphs \cite{gay1997hooking, gay1991automatic}.

CasADi is a software framework for nonlinear optimization and optimal control built
around algorithmic differentiation \cite{andersson2019}.
Expressions are stored in two graph types, scalar-valued \texttt{SX} nodes and matrix-valued
\texttt{MX} nodes, and every matrix in the framework is sparse in CSC format.
CasADi can also target nonlinear solvers, to which it hands AD-generated derivative callbacks
rather than any explicit coefficient matrix; the case relevant here, however, is its interface
to conic solvers such as Clarabel.
On that path the \texttt{conic} front-end differentiates the symbolic objective and constraints
to identify the problem data --- the matrices $H$ and $A$ together with their sparsity
patterns --- which it then forwards to the solver.
The sparsity patterns are detected by propagating bitvectors through the graph, and their
numerical values are recovered in a few AD sweeps using the graph coloring techniques covered
in \ref{sec:computing-derivatives}.
Second-order-cone constraints are accepted on this same path through a reformulation helper,
but CasADi stops short of the disciplined-convex canonicalization that lets CVXPY target
general conic solvers automatically.
Crucially, this differentiation step presupposes a problem already cast in the solver's standard
form: AD recovers $H$ and $A$ from a smooth objective and smooth constraints, but it cannot turn
a nonsmooth convex atom --- a norm, a maximum, an eigenvalue --- into the auxiliary variables and
cone constraints that represent it.
Supplying that epigraph reformulation is left to the user, whereas it is precisely the work that
CVXPY's canonicalization performs automatically.

\paragraph{Comparison.}
As established in \S\ref{sec:computing-derivatives}, preparing the problem data amounts to
computing the sparse Jacobian of the constraint functions with respect to the variables; each
of these systems is therefore a particular point in that landscape.
JuMP accumulates it eagerly, one scalarized constraint at a time; AMPL writes it to a file and
defers the nonlinear entries to AD inside the solver; CasADi extracts it from the symbolic
graph by AD; and CVXPY stuffs it from canonicalized affine trees, with the additional map from
parameters to problem data.
Where they differ most sharply is one level up, in the front-end they expose: JuMP, AMPL, and
CasADi are algebraic, requiring the problem to be stated in a form the target solver already
accepts, whereas CVXPY alone infers convexity from a disciplined grammar and reduces it to
conic form on the user's behalf.

\section{Sparse matrices}
\label{sec:sparse-matrices}

Matrices that contain many number of zero entries are known as \emph{sparse matrices}.
The simplest sparse matrix data structure is the \emph{coordinate} or \emph{triplet}
format. It consists of two integer index arrays \texttt{rows} and \texttt{cols} and a floating point
value array \texttt{vals} of length equal to the number of \emph{nonzero entries} in the matrix.

For example, the matrix
\begin{equation}\label{eq:sparse-matrix}
  \begin{bmatrix}
  0 & 0 & 3.2 & 0\\
  4.1 & 1.8 & 0 & 2.2\\
  0 & 2.8 & 0 & 3.4\\
  \end{bmatrix}
\end{equation}
can be represented in coordinate format as
\begin{lstlisting}[language=C]
int     rows[] = {0,    1,    1,    1,    2,    2};
int     cols[] = {2,    0,    1,    3,    1,    3};
double vals[] = {3.2,  4.1,  1.8,  2.2,  2.8,  3.4};
\end{lstlisting}

where we use zero-based indexing and array declaration notation from the C programming
language \cite{Kernighan1988}.
The coordinate format is the easiest to understand and form, but it is not effective for most
operations on sparse matrices; the \emph{compressed sparse row} or CSR format is commonly
used instead.

\paragraph{Compressed sparse row format.}
The CSR format differs from the coordinate format in that it replaces the \texttt{rows} array with
a row pointer array \texttt{idxptr} of length equal to the number of rows plus one.
The row pointer array indicates the starting index of each row in the \texttt{cols} arrays.
For example, the matrix in \eqref{eq:sparse-matrix}
can be represented in CSR format as
\begin{lstlisting}[language=C]
int  idxptr[] = {0,    1,                4,         6};
int    cols[] = {2,    0,    1,    3,    1,    3};
double vals[] = {3.2,  4.1,  1.8,  2.2,  2.8,  3.4};
\end{lstlisting}
where we deliberately format \texttt{idxptr} to align with the start of each
row in the \texttt{cols} arrays.
% talk about benefits of CSR format. fast row slicing, fast matrix-vector products, etc.
The benefits of the CSR format are more than a reduced size of the \texttt{idxptr} array
compared to the \texttt{rows} array.
In the CSR format, accessing a row takes constant time and is very \emph{cache-friendly}
since the nonzero entries are stored contiguously in memory.
For this reason, the CSR format is the default for \emph{iterative methods}
to solve sparse linear systems \cite{saad2003iterative}.

\paragraph{Compressed sparse column format.}
% talk about CSC as a direct extension of CSR but with column pointers.
However, one downside of the CSR format is that accessing a column is much more difficult;
one would need to look at every row to find the nonzero entries in a column.
An alternative format is the \emph{compressed sparse column} or CSC format, 
which swaps the role of the \texttt{idxptr} array to refer to column indices instead.
In contrast to iterative methods, the CSC format is the preferred format for
\emph{direct methods} to solve sparse linear systems \cite{davis2006direct}.

\paragraph{Other formats.}
The coordinate, CSR and CSC formats are the most widely used sparse matrix formats,
but many others exist for different specialized use cases.
The scientific Python sparse library \texttt{scipy.sparse} \cite{2020SciPy-NMeth}
allows users to form other types of sparse matrices such as the list of lists (LIL) matrix,
the dictionary of keys (DOK) matrix, and the block-sparse row (BSR) matrix.

\paragraph{Sparse matrix struct in C.}
A CSR matrix struct in C looks like this.
\begin{lstlisting}[language=C]
typedef struct CSR_Matrix {
    int *p;       /* row pointers, size m+1   */
    int *i;       /* column indices, size nnz */
    double *x;    /* values, size nnz         */
    int m, n, nnz;
} CSR_Matrix;
\end{lstlisting}
