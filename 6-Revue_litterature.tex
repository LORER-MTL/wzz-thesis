Solving an optimization problem on a computer requires translating the mathematical formulation
into a data format that solvers can process. For linear programs, this means constructing the
constraint matrix $A$, the right-hand side vector $b$, and the objective coefficients $c$ that
define the \emph{standard form},
\begin{equation}
\begin{array}{ll}
\mbox{minimize} & c^T x \\
\mbox{subject to} & Ax \leq b, \\
& x \geq 0.
\end{array}
\end{equation}

\paragraph{Manual encoding}
In the early days of linear programming, analysts manually computed and encoded each coefficient
onto punch cards. This process was tedious, error-prone and became impractical as linear
programming found more and more applications in large-scale industrial
problems~\cite{fourer1978modern}.

\paragraph{MPS format}
IBM's Mathematical Programming System (MPS) file format, developed in the 1960s, established a
standardized file format for representing linear programs~\cite{ibm1976mpsx}. The MPS format uses
fixed-width fields designed for 80-column punch cards, with sections for rows, columns, and
coefficients.
William Orchard-Hays~\cite{orchard-hays1984history} provides a comprehensive history of these
early mathematical programming systems, tracing their development from 1952 at RAND Corporation
through their widespread adoption on mainframe computers in the late 1960s.

\paragraph{Matrix generators}
To automate the creation of MPS files, \emph{matrix generators} emerged in the late 1960s; they
are procedural programs that compute the problem coefficients through explicit loops and output
the results in MPS format~\cite{marceau1971matrix}. Commercial systems such as
\texttt{MaGen}~\cite{haverly1977magen}, \texttt{GAMMA}~\cite{sperry1977gamma}, and \texttt{DATAFORM}~\cite{ketron1975dataform}
were among the first matrix generators which were used in various domains.

\section{Algebraic modeling languages}
Modelers naturally think in terms of sets, indices, and algebraic expressions, not in terms of
individual matrix entries. Matrix generators simplified the encoding process but still required
modelers to translate their mathematical formulations into procedural code that explicitly
constructs the coefficient matrices. This suggests that the gap between the modeler's
representation of the problem and the solver's required format remained
unresolved~\cite{fourer1978modern}.

In the late 1970s, \emph{algebraic modeling languages} emerged as formal languages designed to
accept problem descriptions that closely mirror standard mathematical
notation~\cite{fourer1983modeling}. By working directly with the modeler's representation, these
languages simplify verification (the model can be inspected as written), modification (changing
the problem does not require rewriting procedural code), and communication (the formulation serves
as its own documentation).

% take one example and show how it is written in all languages
\subsection{\texttt{GAMS}}
\texttt{GAMS} (General Algebraic Modeling System) was developed in the early 1980s at the World
Bank by Alexander Meeraus, Anthony Brooke, and David Kendrick~\cite{brooke1988gams}. Designed
originally for large-scale economic planning models, \texttt{GAMS} introduced a set-based
algebraic notation that maps naturally to the indexed summations and constraints common in
economics and operations research. It was one of the first systems to cleanly separate model
logic from data, allowing the same formulation to be solved with different datasets.
The following snippet illustrates \texttt{GAMS}'s distinctive
set-based indexing on a transport problem:
{\lstset{language={},basicstyle=\small\ttfamily,columns=flexible,
  breaklines=true,frame=none,xleftmargin=1em,xrightmargin=1em,numbers=none}
\begin{lstlisting}
Sets  i  supply nodes / s1, s2 /
      j  demand nodes / d1, d2, d3 /;
Parameter  supply(i) / s1 50, s2 40 /
           demand(j) / d1 30, d2 25, d3 35 /;
Variable   x(i,j)  shipment quantities;
Equation   sup(i)   enforce supply limits;
sup(i) .. sum(j, x(i,j)) =l= supply(i);
\end{lstlisting}
}

\subsection{\texttt{AMPL}}
\texttt{AMPL} (A Mathematical Programming Language) was created by Robert Fourer, David Gay,
and Brian Kernighan at Bell Labs in the late 1980s~\cite{fourer1990ampl}. Its declarative syntax
was designed to mirror standard mathematical notation as closely as possible, making formulations
directly readable by domain experts. A key design innovation is the strict separation of
\emph{model} (the algebraic structure) from \emph{data} (the numerical values), allowing the
same model file to be instantiated with different datasets. The compiler parses the model into
an expression \ac{DAG} and writes a compact \texttt{.nl} file~\cite{gay2005writing} that
solvers read directly. The following model fragment shows this separation:
{\lstset{language={},basicstyle=\small\ttfamily,columns=flexible,
  breaklines=true,frame=none,xleftmargin=1em,xrightmargin=1em,numbers=none}
\begin{lstlisting}
set PROD;
param demand {PROD} >= 0;
var x {PROD} >= 0;
minimize cost: sum {p in PROD} c[p] * x[p];
subject to meet_demand {p in PROD}: x[p] >= demand[p];
\end{lstlisting}
}

\subsection{\texttt{AIMMS}}
\texttt{AIMMS} (Advanced Interactive Multidimensional Modeling System) was developed by
Johannes Bisschop at Paragon Decision Technology (now AIMMS
B.V.)~\cite{bisschop2006aimms}. It extended the algebraic modeling paradigm pioneered by
\texttt{GAMS} with a graphical integrated development environment, end-user interfaces,
and a model-driven application framework aimed at deploying optimization models as
decision-support applications. The following fragment illustrates \texttt{AIMMS}'s
declaration-based syntax:
{\lstset{language={},basicstyle=\small\ttfamily,columns=flexible,
  breaklines=true,frame=none,xleftmargin=1em,xrightmargin=1em,numbers=none}
\begin{lstlisting}
Set Cities { Index: c }
Parameter Demand { IndexDomain: c }
Variable  Ship   { IndexDomain: (c1,c2), Range: nonnegative }
Constraint MeetDemand {
    IndexDomain: c,
    Definition:  sum(c1, Ship(c1,c)) >= Demand(c)
}
\end{lstlisting}
}

\section{Conic optimization}

\paragraph{Interior-point methods}
The theoretical foundations for conic optimization were laid in the 1980s and 1990s.
Karmarkar's 1984 polynomial-time interior-point algorithm for linear
programming~\cite{karmarkar1984new} demonstrated that \acp{LP} could be solved in
polynomial time by traversing the interior of the feasible region rather than its vertices.
Nesterov and Nemirovski~\cite{nesterov1994interior} generalised interior-point methods to
\emph{self-concordant barrier} functions over convex cones, establishing polynomial complexity
for a broad class of conic programs including \acp{SOCP} and \acp{SDP}. These results made
conic solvers practical: once the problem data is in the right form, the solver provides
worst-case polynomial-time guarantees.

\paragraph{Cone types}
A \emph{conic program} optimises a linear objective over the intersection of an affine subspace
with a convex cone~$\mathcal{K}$~\cite{boyd2004convex}:
\begin{equation}
      \begin{array}{ll}
        \text{minimize} & c^T x\\
        \text{subject to} &  b-Ax \in \mathcal K,\\
      \end{array}
      \label{eq:conic}
\end{equation}
where $\mathcal{K}$ is a closed convex cone. The choice of~$\mathcal{K}$ determines the
problem class:
\begin{itemize}
\item \textbf{Nonnegative orthant} $\reals_+^n = \{x \in \reals^n : x_i \geq 0\}$
  --- recovers linear programming.
\item \textbf{Second-order cone} $\mathcal{Q}^n = \{(t, x) \in \reals \times \reals^{n-1}
  : \|x\|_2 \leq t\}$ --- \acp{SOCP}, which capture quadratic constraints and
  $\ell_2$-norm objectives.
\item \textbf{Positive semidefinite cone} $\symm_+^n = \{X \in \symm^n : X \succeq 0\}$
  --- \acp{SDP}, widely used in control, combinatorial optimisation, and signal processing.
\item \textbf{Exponential and power cones} --- extend the framework to entropy, geometric,
  and $p$-norm problems.
\end{itemize}

\paragraph{Conic form as a universal solver interface}
Modern conic solvers such as \texttt{MOSEK}~\cite{mosekSolver, aps2025mosek} and
\texttt{SCS}~\cite{ocpb:16, odonoghue:21} accept problem data directly in the form
$(A, b, c, \mathcal{K})$. This creates a clean separation of concerns: the \emph{modeling
layer} is responsible for reformulating the user's problem and extracting the coefficient
matrices, while the \emph{solver} handles the numerical optimisation. This thesis focuses
on the modeling-layer side of the interface---specifically, how the sparse matrices $A$, $b$,
and $c$ are extracted from a canonicalized expression tree.

\section{Embedded modeling languages}

In the late 2000s and early 2010s, a new generation of modeling languages emerged that are
\emph{embedded} in general-purpose programming languages, in contrast with standalone systems
like \texttt{AMPL} and \texttt{GAMS}. By living inside a host language, these tools inherit its
full ecosystem: data manipulation libraries, scripting capabilities, testing frameworks, and
package managers. Examples include \texttt{YALMIP}~\cite{lofberg2004yalmip} in MATLAB,
\texttt{Pyomo}~\cite{hart2011pyomo} in Python, \texttt{CasADi}~\cite{andersson2019} in C++,
and \texttt{JuMP}~\cite{dunning2017jump} in Julia. This section presents \texttt{JuMP} in
most detail, as its \texttt{MathOptInterface} abstraction illustrates a particularly
influential design for communicating structured problem data to solvers, then briefly covers
\texttt{YALMIP} and \texttt{CasADi}.

\subsection{\texttt{JuMP} and \texttt{MathOptInterface}}

\texttt{JuMP} is an algebraic modeling language embedded in Julia, originally developed in 2012 by
Iain Dunning, Joey Huchette, and Miles Lubin at the MIT Operations Research
Center~\cite{dunning2017jump, lubin2023jump10recent}. Its abstraction layer, \texttt{MathOptInterface}
(\texttt{MOI})~\cite{legat2020mathoptinterface}, rethinks how a modeling language communicates with solvers,
moving away from the traditional approach of reducing every problem to a single standard form.

\paragraph{Function-set pairs}
\texttt{MOI} represents each constraint as a \emph{function-set pair}: a mathematical function paired with
the set it must belong to. For example, a linear inequality $a^T x \leq b$ is encoded as:
\begin{lstlisting}
MOI.add_constraint(model,
    MOI.ScalarAffineFunction(MOI.ScalarAffineTerm.(a, x), 0.0),
    MOI.LessThan(b))
\end{lstlisting}
while a second-order cone constraint $t \geq \|x\|_2$ with $n$ variables uses:
\begin{lstlisting}
MOI.add_constraint(model,
    MOI.VectorOfVariables([t; x]),
    MOI.SecondOrderCone(n)).
\end{lstlisting}
\texttt{MOI} therefore preserves the semantic type of each constraint, so solvers that
accept specific constraint types can receive them directly without unnecessary reformulations.

\paragraph{Bridges}
When a solver does not natively support a particular function-set pair, \texttt{MOI} applies
a \emph{bridge}, a composable transformation to an equivalent representation the solver accepts.
The bridge system maintains a directed hyper-graph of known transformations and finds the shortest
path to the target solver's supported types, so adding a reformulation once benefits all solvers.

\paragraph{Incremental problem construction}
Some solvers, notably \texttt{MOSEK}~\cite{mosekSolver} and
\texttt{HiGHS}~\cite{huangfu2018highs}, allow constraints to be added one at a time
rather than requiring the entire problem to be submitted at once. \texttt{MOI} supports
this incremental mode natively, so algorithms that iteratively refine a formulation, such
as cutting-plane or branch-and-cut methods, can append a constraint between successive
solves without reconstructing the full problem data.

\paragraph{Extensibility}
\texttt{MOI} makes it straightforward to support new constraint types: a solver declares
which function-set pairs it handles, and new bridges can be registered at any time.
\texttt{Hypatia}~\cite{coey2022solving, coey2022performance}, for example, natively implements over twenty
specialized cones, including the log-determinant cone, the relative-entropy cone, and
several spectral matrix cones, all of which are first-class \texttt{MOI} set types.
\texttt{SCS}~\cite{ocpb:16, odonoghue:21} has similarly begun adding native spectral
matrix cone support~\cite{cederbergspectralmatrixcones}, bypassing the large
semidefinite reformulations that would otherwise be required.

\subsection{\texttt{YALMIP}}

\texttt{YALMIP}~\cite{lofberg2004yalmip} is an optimization modeling toolbox for MATLAB,
developed by Johan Löfberg starting in 2004. It overloads MATLAB's arithmetic operators on
\emph{sdpvar} decision-variable objects, building an internal expression graph as the user writes
natural mathematical expressions. When the user calls \texttt{optimize()}, \texttt{YALMIP}
analyses the expression graph to automatically detect the problem class---\ac{LP}, \ac{QP},
\ac{SOCP}, \ac{SDP}, or mixed-integer variant---and dispatches to an appropriate solver.
Unlike DCP-based tools, it does not enforce convexity rules at construction time, applying
broader reformulation strategies at the cost of weaker compile-time guarantees.
{\lstset{language=Matlab,basicstyle=\small\ttfamily,columns=flexible,
  breaklines=true,frame=none,xleftmargin=1em,xrightmargin=1em,numbers=none}
\begin{lstlisting}
x = sdpvar(n, 1);
F = [A*x <= b, x'*x <= 1];
optimize(F, norm(x, 1));
\end{lstlisting}
}

\subsection{\texttt{CasADi}}

\texttt{CasADi}~\cite{andersson2019} is an open-source framework for nonlinear optimisation and
optimal control, developed by Joel Andersson, Joris Gillis, and Moritz Diehl. Written in C++
with Python and MATLAB interfaces, it builds a symbolic \ac{DAG} of the problem expressions
and uses \ac{AD} to compute exact derivatives. Its primary targets are \ac{NLP} solvers such
as \texttt{IPOPT}~\cite{wachter2006ipopt}, making it the tool of choice for model-predictive
control and trajectory optimisation. For affine expressions the Jacobian
$\partial f / \partial x = A$ is exactly the coefficient matrix, so \texttt{CasADi}'s AD
machinery performs coefficient extraction as a by-product.
{\lstset{language=Python,basicstyle=\small\ttfamily,columns=flexible,
  breaklines=true,frame=none,xleftmargin=1em,xrightmargin=1em,numbers=none}
\begin{lstlisting}
x = ca.SX.sym('x', n)
obj = x.T @ Q @ x
g   = A @ x - b
solver = ca.nlpsol('s', 'ipopt',
                   {'x': x, 'f': obj, 'g': g})
sol = solver(lbg=0)
\end{lstlisting}
}

\section{Disciplined convex programming}

A complementary approach to embedded modeling is \emph{disciplined convex programming}
(DCP)~\cite{grant2004disciplined, grant2006disciplined}, a set of composition rules that can
automatically verify convexity. A DCP language restricts how atoms (elementary functions with
known curvature) may be combined: for example, a convex function of an affine expression is
convex, but a convex function of a convex expression is not necessarily so. By enforcing these
rules at problem construction time, DCP languages guarantee that any accepted formulation is
convex and can be reduced to conic standard form. Implementations include
\texttt{CVX}~\cite{cvx} in MATLAB, \texttt{CVXPY}~\cite{diamond2016cvxpy, agrawal2018rewriting}
in Python, \texttt{CVXR}~\cite{Fu_2020} in R, and
\texttt{Convex.jl}~\cite{udell2014convex} in Julia. This section presents \texttt{CVXPY} in
most detail, as it is the system targeted by the coefficient extraction engine developed in
this thesis, then briefly covers \texttt{CVX} and \texttt{CVXR}.
\texttt{Convex.jl} follows a similar DCP pipeline in Julia and is not discussed further.

\subsection{\texttt{CVXPY}}

\texttt{CVXPY} is a domain-specific language for convex optimization embedded in Python.
It was originally developed by Steven Diamond and Stephen Boyd at Stanford
University~\cite{diamond2016cvxpy}.
Akshay Agrawal later redesigned the
rewriting system in \texttt{CVXPY}~\cite{agrawal2018rewriting},
which enabled support for other disciplined
languages~\cite{agrawal2019dgp, agrawal2020dqcp, agrawal2019dpp}. The
project has since grown through contributions from many other developers
and solver interface maintainers.

\paragraph{Reduction-based rewriting}
\texttt{CVXPY} is built on a system of
\emph{reductions}~\cite{agrawal2018rewriting}. A reduction is a pair of
maps: a \emph{forward} map that transforms a problem into an equivalent one,
and a \emph{backward} map that recovers a solution of the original problem
from a solution of the transformed one. Reductions compose: the output of one
becomes the input of the next, forming a \emph{chain} that converts the
user's formulation into solver-ready data.

The chain is solver-aware, so different solvers trigger different output
formats. Historically, \texttt{CVXPY} distinguished two standard forms. For
solvers that accept quadratic objectives such as \texttt{OSQP} and
\texttt{Gurobi}, the chain produces a quadratic program:
\begin{equation}
\begin{array}{ll}
\text{minimize}   & \tfrac{1}{2}\, x^T P\, x + c^T x \\
\text{subject to} & l \leq Ax \leq u.
\end{array}
\label{eq:cvxpy-qp}
\end{equation}
For purely conic solvers (\eg \texttt{SCS}), the chain instead produces:
\begin{equation}
\begin{array}{ll}
\text{minimize}   & c^T x \\
\text{subject to} & Ax + b \in \mathcal{K}.
\end{array}
\label{eq:cvxpy-conic}
\end{equation}
More recently, a unified interface that combines a quadratic objective with
conic constraints has become the central solver interface in \texttt{CVXPY}:
\begin{equation}
\begin{array}{ll}
\text{minimize}   & \tfrac{1}{2}\, x^T P\, x + c^T x \\
\text{subject to} & Ax + b \in \mathcal{K}.
\end{array}
\label{eq:cvxpy-standard}
\end{equation}
In all cases the final output is a set of sparse coefficient matrices; what
changes between reduction paths is the \emph{structure} of those matrices.

\paragraph{Common reductions}
The individual reductions that compose a canonicalization chain are well
established in the convex optimization literature.
Chu~et~al.~\cite{chu2013codegen} give a concise exposition; the main steps
are:
\begin{enumerate}
\item \textbf{DCP verification.} Confirm that the objective is convex and the
  constraints are valid by walking the expression tree and applying DCP
  composition rules.
\item \textbf{Smith form.} Replace each subexpression with a new
  auxiliary variable linked to the original expression by an equality
  constraint.
\item \textbf{Relaxed Smith form.} Relax the equalities introduced above to
  inequalities wherever the monotonicity of the objective guarantees that the
  inequality will be tight at optimality.
\item \textbf{Matrix stuffing.} Assemble the resulting affine expressions into
  sparse coefficient matrices before passing them to a solver.
\end{enumerate}
The following chapter examines how these steps---and in particular the final
matrix-stuffing step---are implemented in practice across different systems.

\paragraph{Other reductions}
\texttt{CVXPY} also ships reductions beyond the standard canonicalization
chain. For example, a \emph{flip-objective} reduction converts a maximization
problem into a minimization, and the \texttt{Dgp2Dcp} reduction
rewrites disciplined geometric programs into equivalent disciplined convex
programs~\cite{agrawal2019dgp}.

\subsection{\texttt{CVX}}

\texttt{CVX}~\cite{cvx} is the original implementation of disciplined convex programming,
developed by Michael Grant and Stephen Boyd at Stanford University starting in
2004~\cite{grant2004disciplined}. Embedded in MATLAB, it uses \texttt{cvx\_begin}/\texttt{cvx\_end}
blocks to delimit a problem specification, within which MATLAB expressions are intercepted and
checked against DCP rules. Grant's PhD thesis~\cite{grant2004disciplined} formalised the DCP
ruleset and proved that any DCP-compliant problem can be reduced to conic standard form,
establishing the template that \texttt{CVXPY} and subsequent DCP tools follow. On the solver
side, \texttt{CVX} targets \texttt{SeDuMi} and \texttt{SDPT3} by default, producing the
\ac{SDP} data structures these solvers expect.
{\lstset{language=Matlab,basicstyle=\small\ttfamily,columns=flexible,
  breaklines=true,frame=none,xleftmargin=1em,xrightmargin=1em,numbers=none}
\begin{lstlisting}
cvx_begin
    variable x(n)
    minimize( norm(A*x - b) )
    subject to
        x >= 0
cvx_end
\end{lstlisting}
}

\subsection{\texttt{CVXR}}

\texttt{CVXR}~\cite{Fu_2020} brings disciplined convex programming to the R statistical
computing environment. Developed by Anqi Fu, Balasubramanian Narasimhan, and Stephen Boyd,
it uses R's S4 object system to overload arithmetic operators on decision variables, building
an expression tree that is checked against DCP rules. \texttt{CVXR} targets the same solver
backends as \texttt{CVXPY} (including \texttt{SCS} and \texttt{MOSEK}) and follows the same
canonicalization-then-extraction pipeline.
{\lstset{language={},basicstyle=\small\ttfamily,columns=flexible,
  breaklines=true,frame=none,xleftmargin=1em,xrightmargin=1em,numbers=none}
\begin{lstlisting}
x <- Variable(n)
prob <- Problem(Minimize(norm(A %*% x - b)),
                list(x >= 0))
result <- solve(prob)
\end{lstlisting}
}

\section{A Survey of Extraction Methods}
\label{sec:extraction-problem}

Solvers require problem data in a standard form: the constraint matrix~$A$,
right-hand side~$b$, objective coefficients~$c$, and a cone
description~$\mathcal{K}$. Modeling languages let users write natural
mathematical expressions. Something must bridge the gap.

This ``something'' involves two logically distinct operations:
\begin{enumerate}
\item \textbf{Reformulation.} Transform the problem into an equivalent
  standard-form problem by introducing auxiliary variables, epigraph
  constraints, and conic representations. Chapter~\ref{sec:Introduction}
  described how \texttt{CVXPY}'s reduction chain and \texttt{MOI}'s bridge
  system each accomplish this.
\item \textbf{Coefficient extraction.} Extract the numerical coefficient data
  $(A, b, c)$ from the reformulated---now affine---expressions.
\end{enumerate}
The literature has largely treated these as a single pipeline. This section
examines them separately, focusing on the second operation: how different
systems actually compute the sparse matrices that solvers consume.

To make the comparison concrete, we trace a single running example through
each system: the least-squares problem
\begin{equation}
\begin{array}{ll}
\text{minimize} & \|Fx - g\|_2^2,
\end{array}
\label{eq:least-squares}
\end{equation}
with $F \in \reals^{3 \times 2}$ and $g \in \reals^3$.

\subsection{\texttt{JuMP} and \texttt{MathOptInterface}}
\label{sec:jump-trace}

\texttt{JuMP}'s function-in-set architecture, described in
Chapter~\ref{sec:Introduction}, uses operator overloading to eagerly build
coefficient representations. There is no expression tree and no deferred
extraction phase---the coefficients \emph{are} the internal representation.
The following trace shows how this works for the least-squares
problem~\eqref{eq:least-squares}.

\paragraph{Step 1: Macro expansion}
The user writes:
\begin{lstlisting}
using JuMP, MosekTools
F = [1 2; 3 4; 5 6]; g = [1, 2, 3]
model = Model(Mosek.Optimizer)
@variable(model, x[1:2])
@objective(model, Min, sum((F * x - g).^2))
\end{lstlisting}
The \texttt{@objective} macro expands \texttt{sum((F * x - g) .\^{} 2)}
by evaluating each subexpression eagerly. The product \texttt{F * x} dispatches
through Julia's linear algebra: each element $r_i = F_{i1} x_1 + F_{i2} x_2
- g_i$ is built as a \texttt{ScalarAffineFunction} containing the
coefficients~$F_{i1}$, $F_{i2}$ and the constant~$-g_i$ explicitly.

\paragraph{Step 2: Quadratic function construction}
Squaring each residual $r_i^2$ triggers \texttt{JuMP}'s multiplication
dispatch, which collects the quadratic terms into a
\texttt{ScalarQuadraticFunction}:
\[
  r_i^2 = F_{i1}^2 x_1^2 + 2 F_{i1} F_{i2}\, x_1 x_2
  + F_{i2}^2 x_2^2 - 2g_i(F_{i1} x_1 + F_{i2} x_2) + g_i^2.
\]
Summing over $i = 1, 2, 3$ accumulates all quadratic and linear terms into a
single \texttt{ScalarQuadraticFunction} representing $\sum_i r_i^2$.

\paragraph{Step 3: Implicit formation of $F^T\!F$}
The algebra reveals that by expanding the sum of squares,
\texttt{JuMP} has implicitly formed the Gram matrix:
\[
  \|Fx - g\|_2^2 = x^T\! F^T\!F\, x - 2 g^T\!F\, x + g^T\!g.
\]
The quadratic coefficient matrix stored in the
\texttt{ScalarQuadraticFunction} is $Q = F^T\!F$, the linear coefficient
vector is $c = -2F^T\!g$, and the constant is $g^T\!g$. These are the
actual numerical values, not symbolic expressions.

\paragraph{Step 4: Solver handoff}
\texttt{MOSEK} natively supports quadratic objectives, so the
\texttt{MOI} bridge system finds no transformation is needed. The
\texttt{ScalarQuadraticFunction}---containing $Q$, $c$, and the
constant---is forwarded directly to the solver's API.

\paragraph{Consequence}
Compositions are resolved at expression-build time. There is no separate
extraction phase because extraction happens incrementally during
construction. But this means structure is lost: $F^T\!F$ cannot be
``un-formed.'' A conic solver that could accept $\|Fx - g\|_2$ directly as a
second-order cone constraint would need to recover $F$ from $F^T\!F$, which
is not possible in general. When such a reformulation is needed,
\texttt{MOI} activates a bridge, but the bridge operates on the already-formed
quadratic representation rather than the original affine expression.

\subsection{\texttt{CVXPY}}
\label{sec:cvxpy-extraction}

\texttt{CVXPY} takes the opposite approach: it builds an expression tree of
atoms and defers all numerical work until the solver is invoked. The pipeline
has two phases:
\begin{enumerate}
\item DCP-based canonicalization rewrites the tree into conic standard
  form (the reductions framework described in
  Chapter~\ref{sec:Introduction})~\cite{agrawal2018rewriting}.
\item \emph{Matrix stuffing} walks the canonicalized tree and extracts
  $(A, b, c)$ by composing sparse linear maps.
\end{enumerate}
This section focuses on the second phase: how \texttt{CVXPY} actually
computes the coefficient matrices from the canonicalized expression tree.

\paragraph{Expression trees}
After canonicalization, \texttt{CVXPY} guarantees that all constraints and the
objective are affine functions of the decision variable~$x$. Each affine
function is represented as an \emph{expression tree} where every node is a
linear operation (an \emph{atom}), as illustrated in
Figure~\ref{fig:expression-tree}.

    every node/.style={circle, draw, minimum size=18mm, inner sep=0pt}
]

\node {$+$}
  child {
    node {\texttt{sum}}
      child {
          node {$-$}
          child {

When a problem involves matrix variables, \texttt{CVXPY} flattens them into
vectors using column-major (Fortran) ordering: $X \in \reals^{m \times n}$
becomes $(X_{11}, X_{21}, \ldots, X_{m1}, X_{12}, \ldots, X_{mn})^T \in
\reals^{mn}$. This convention determines the column ordering in all
coefficient matrices.

\paragraph{Matrix stuffing via sparse linear map composition}
The extraction phase traverses each expression tree bottom-up. Each leaf node
returns its coefficient matrix (the identity for a variable, a constant
matrix for data), and each internal node composes its children's matrices by
applying its own linear operator. The composition is carried out via sparse
matrix multiplication.

For example, in the expression \texttt{sum(A @ x)}, the traversal first
returns $I$ at the variable node, multiplies by $A$ at the \texttt{mul}
node to get $A$, then multiplies by $\ones^T$ at the \texttt{sum} node to
get $\ones^T A$ (Figure~\ref{fig:sparse-matmul-tree}). Each step performs a
sparse matrix--matrix product and allocates a new result matrix.

\paragraph{Architecture of the extraction backends}
Internally, \texttt{CVXPY} represents the canonicalized tree as a list of
\texttt{LinOp} nodes. The extraction is handled by a
\texttt{PythonCanonBackend} whose \texttt{build\_matrix} method walks each
tree and returns a 2D sparse matrix. The central data structure is a
\texttt{TensorView}: a dictionary mapping each variable to its coefficient
block (a sparse matrix). A recursive function \texttt{process\_constraint}
traverses the tree bottom-up, applying the appropriate linear operator at
each node.

The operations performed during this traversal fall into three categories:
\begin{enumerate}
\item \textbf{Pure index operations} (\texttt{reshape}, \texttt{transpose},
  \texttt{index}, \texttt{promote}, \texttt{broadcast\_to}). These only remap
  row indices---no arithmetic is performed. Essentially free in terms of
  floating-point cost.
\item \textbf{Elementwise operations} (\texttt{neg}, \texttt{mul\_elem},
  \texttt{div}). These scale existing entries via elementwise multiplication.
  The sparsity pattern is unchanged.
\item \textbf{Matrix multiplication operations} (\texttt{mul}, \texttt{rmul},
  \texttt{sum\_entries}, \texttt{conv}, \texttt{kron}). These build an explicit
  operator matrix and apply it via general-purpose
  \texttt{scipy.sparse @ scipy.sparse}. \emph{This is where the cost lives.}
\end{enumerate}

\paragraph{Detailed example: left multiplication}
Consider the node \texttt{C @ X} where $C \in \reals^{m \times n}$ is a
constant and $X \in \reals^{n \times p}$ is the child expression.
The vectorised form is $\vect(CX) = (I_p \otimes C)\,\vect(X)$, so the
backend builds the Kronecker product $I_p \otimes C$ via
\texttt{sp.kron(sp.eye(p), C)}, applies it to the child's coefficient matrix
via sparse matrix multiplication, and converts the result to CSR. This
sequence involves three allocations per node: the Kronecker product, the
matrix product, and the format conversion.

\paragraph{What is already exploited}
\texttt{CVXPY}'s implementation does exploit some structure. Index operations
are handled as pure reindexing without forming operator matrices.
Elementwise operations use \texttt{.multiply()} instead of matrix
multiplication. The Kronecker structure is partially exploited by using
\texttt{sp.kron(sp.eye(n), C)} rather than materialising a dense matrix.

\paragraph{What is not exploited}
Several opportunities for efficiency remain:
\begin{itemize}
\item The Kronecker operator $I_p \otimes C$ is materialised as a general
  sparse matrix, even though its block-diagonal structure means $C$ could be
  applied independently to $p$ blocks.
\item Sparsity patterns are discovered at runtime by \texttt{SciPy}'s sparse
  arithmetic, even though they are fully determinable from the expression
  structure at build time.
\item No pre-allocation of the final output is possible, since each
  intermediate product has an independently computed sparsity pattern.
\item General-purpose sparse matrix multiplication is used regardless of the
  known structure of the operator (diagonal scaling, row selection, Kronecker
  with identity, \etc).
\end{itemize}
\texttt{CVXPY} ships two Python backends (SciPy-based and COO-based) as well
as a legacy C++ backend (\texttt{cvxcore}) that special-cases eighteen
\texttt{LinOp} types. All three share the same compositional architecture.

\paragraph{Key advantage of the deferred approach}
Unlike \texttt{JuMP}'s eager expansion, the deferred approach preserves the
original problem structure through canonicalization. The expression
\texttt{norm(F @ x - g)} never forms $F^T\!F$; the matrix~$F$ appears
directly in the coefficient data. This structural preservation is what
enables conic reformulations that exploit the original factors.

\subsection{\texttt{CasADi}}
\label{sec:casadi-approach}

\texttt{CasADi}~\cite{andersson2019} takes a third approach. It is
fundamentally a nonlinear programming tool: its primary targets are NLP
solvers such as \texttt{IPOPT}~\cite{wachter2006ipopt}, with conic
capabilities (QP, SOCP) available through external backends but not as
a central design focus. Internally, \texttt{CasADi} builds a symbolic
expression DAG and extracts derivative information via algorithmic
differentiation on the graph. For an affine expression $f(x) = Ax + b$,
the Jacobian $\partial f / \partial x = A$ is the coefficient matrix, so
AD-based Jacobian extraction and coefficient extraction are mathematically
identical. Crucially, \texttt{CasADi} propagates sparsity symbolically
through the graph before performing numerical evaluation, making it a
genuine hybrid of symbolic and AD-based approaches.

This is relevant because it explicitly connects expression-graph processing
to Jacobian computation, bridging the modeling and differentiation worlds.
However, since \texttt{CasADi} is designed for general nonlinear problems,
it applies the same AD machinery to affine expressions as to nonlinear
ones---it has no specialised fast path for the purely affine case where the
Jacobian is constant and the coefficients could be read off structurally
rather than computed through differentiation.

\subsection{\texttt{AMPL}}
\label{sec:ampl-approach}

\texttt{AMPL}~\cite{fourer1990ampl} historically pioneered systematic
coefficient extraction. Its internal representation is an expression DAG in
which each node is classified by polynomial degree: constant, linear,
quadratic, or general nonlinear~\cite{gay2005writing}. Linear and quadratic
coefficients are extracted directly from the classified nodes by walking the
DAG, while the nonlinear remainder is retained as an evaluable subgraph for
AD-based derivative computation. This structural decomposition allows
\texttt{AMPL} to hand optimised coefficient data to linear and quadratic
solvers while still supporting fully nonlinear formulations. However,
\texttt{AMPL}'s extraction uses general-purpose operations for the linear
and quadratic coefficients rather than structure-aware CSR transformations,
and its closed-source commercial nature has limited community development of
specialised alternatives.

\section{A Jacobian Interpretation}
\label{sec:jacobian-abstraction}

The previous subsections described four different systems, each with its own
architecture. Despite their differences, a common mathematical structure
underlies them all: extracting the coefficient matrix~$A$ from an affine
expression $f(x) = Ax + b$ is equivalent to computing the Jacobian
$\partial f / \partial x = A$. The Jacobian is constant (independent of~$x$),
so one computation suffices for all~$x$.

\subsection{Properties of the affine Jacobian}
\label{sec:jacobian-special}

Three properties distinguish this Jacobian from general Jacobian computation
in numerical optimisation:
\begin{enumerate}
\item[(a)] \textbf{Constant.} Since $f$ is affine, $\partial f / \partial x =
  A$ is independent of~$x$. One evaluation produces the exact result for all
  inputs.
\item[(b)] \textbf{Structurally determined sparsity.} The sparsity pattern
  of~$A$ is fully determined at expression-build time, before any numerical
  values are known. Each atom's contribution to the sparsity pattern depends
  only on dimensions, index sets, and the topology of the expression tree.
\item[(c)] \textbf{Structured local Jacobians.} The expression is a
  composition of affine operations, each with a known, structured local
  Jacobian. These are not arbitrary sparse matrices: they are typically row
  scalings, permutations, block diagonals, row selections, or Kronecker
  products with the identity.
\end{enumerate}

\subsection{Connections to automatic differentiation}
\label{sec:diff-literature}

The coefficient extraction problem can, in principle, be solved by any method
that computes Jacobians. Existing approaches from the differentiation
literature each address part of the problem but leave efficiency on the
table:

\paragraph{Symbolic differentiation}
For an affine function $f(x) = Ax + b$, symbolic differentiation correctly
yields $\partial f / \partial x = A$. However, computer algebra systems
produce symbolic expressions, not the sparse numerical arrays that solvers
require. The output format does not match the needed representation.

\paragraph{Automatic differentiation}
Forward- and reverse-mode AD compute Jacobian-vector products ($J v$) or
vector-Jacobian products ($v^T J$), not the explicit Jacobian matrix.
Extracting the full sparse matrix requires either $n$ forward passes (one per
column) or $m$ reverse passes (one per row), or sparse compression via graph
colouring~\cite{gebremedhin2005coloring}. This is general-purpose machinery
applied to a special case where the answer is a constant matrix.

\paragraph{Optimal Jacobian accumulation}
Naumann~\cite{naumann2004optimal, naumann2008optimal} studies the problem of
efficiently ordering the multiplication of Jacobian factors in a composition
chain. This is directly relevant: when $f = f_k \circ \cdots \circ f_1$,
the chain rule gives $J = J_k \cdots J_1$, and the multiplication order
affects the total cost. However, the optimal Jacobian accumulation literature
treats each $J_i$ as an arbitrary sparse matrix, without exploiting the
structured forms (diagonal, permutation, block-diagonal) that arise in
affine expression trees.

\medskip
\noindent
None of these methods exploit all three special properties simultaneously:
the constancy of the Jacobian, the a priori knowledge of the sparsity
pattern, and the structured form of each local Jacobian.

\subsection{The sparse composition bottleneck}
\label{sec:composition-problem}

When $f = f_k \circ \cdots \circ f_1$ is a composition of affine maps, the
overall Jacobian is the matrix product $A_k \cdots A_1$ (the chain rule
specialised to constant Jacobians). \texttt{CVXPY} computes this product
during matrix stuffing via repeated sparse matrix--matrix multiplication.
Two costs arise:

\begin{enumerate}
\item \textbf{Intermediate matrix allocation.} Each partial product
  $A_k \cdots A_i$ is materialised as a new sparse matrix. For a tree of
  depth~$d$, up to $d - 1$ intermediate matrices are created and discarded.
\item \textbf{General-purpose sparse matrix multiplication.} Each
  multiplication treats $A_i$ as an arbitrary sparse matrix, invoking
  \texttt{SciPy}'s general \texttt{csr\_matrix @ csr\_matrix} routine. This
  routine must discover the output sparsity pattern at runtime, allocate
  output arrays, and sort indices---overhead that is unnecessary when the
  structure of~$A_i$ is known in advance.
\end{enumerate}

\section{Summary and Research Gap}
\label{sec:research-gap}

No existing implementation exploits all three properties of the affine
Jacobian simultaneously:
\begin{enumerate}
\item[(a)] That local Jacobians are \textbf{structured operations} with
  known forms (row scaling, selection, block-diagonal multiplication,
  Kronecker with identity). Each composition step could be a direct
  transformation of the sparse storage arrays---inserting rows, scaling
  values, selecting entries---rather than a general-purpose sparse matrix
  multiplication.
\item[(b)] That the sparsity pattern of the output is \textbf{determinable
  before numerical evaluation}. The entire output data structure---row
  pointers, column indices, number of nonzeros---can be pre-allocated in a
  single pass over the expression tree, before any floating-point arithmetic
  occurs.
\item[(c)] That \textbf{no intermediate matrices need to be materialised}.
  The composition can be computed as a single pass that writes directly into
  the pre-allocated output arrays, transforming index and value arrays
  in-place rather than creating and discarding temporary matrices at each
  node.
\end{enumerate}
This is the gap that the present work fills. The next chapter presents a
coefficient extraction engine that exploits all three properties: it
performs direct CSR array transformations for each atom, pre-computes
sparsity patterns at build time, and writes results directly into
pre-allocated output arrays without forming intermediate matrices.

\section{Parameters in Optimization Problems}
\label{sec:parameters}

When a problem contains parameters, \texttt{CVXPY}
compiles the structure once---sparsity pattern, cone types, variable
ordering---and stores a mapping from parameter values to numerical coefficients.
Subsequent solves only require evaluating this mapping and calling the solver,
skipping the full canonicalization. The \texttt{cvxpygen}
library~\cite{schaller2022cvxpygen} extends this by generating standalone C code
embedding the compiled structure, enabling deployment without a Python runtime.

This compile-once, evaluate-many paradigm naturally motivates a two-phase
engine design: an initialisation phase that determines the sparsity structure,
and an evaluation phase that fills in numerical values. The next chapter
adopts precisely this separation.
