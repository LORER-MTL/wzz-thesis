Solving an optimization problem on a computer requires translating the mathematical formulation
into a data format that solvers can process. For linear programs, this means constructing the
constraint matrix $A$, the right-hand side vector $b$, and the objective coefficients $c$ that
define the \emph{standard form},
\begin{equation}
\begin{array}{ll}
\mbox{minimize} & c^T x \\
\mbox{subject to} & Ax \leq b, \\
& x \geq 0.
\end{array}
\end{equation}

\paragraph{Manual encoding}
In the early days of linear programming, analysts manually computed and encoded each coefficient
onto punch cards. This process was tedious, error-prone and became impractical as linear
programming found more and more applications in large-scale industrial
problems~\cite{fourer1978modern}.

\paragraph{MPS format}
IBM's Mathematical Programming System (MPS) file format, developed in the 1960s, established a
standardized file format for representing linear programs \cite{ibm1976mpsx}. The MPS format uses
fixed-width fields designed for 80-column punch cards, with sections for rows, columns, and
coefficients.
William Orchard-Hays \cite{orchard-hays1984history} provides a comprehensive history of these
early mathematical programming systems, tracing their development from 1952 at RAND Corporation
through their widespread adoption on mainframe computers in the late 1960s.

\paragraph{Matrix generators}
To automate the creation of MPS files, \emph{matrix generators} emerged in the late 1960s; they
are procedural programs that compute the problem coefficients through explicit loops and output
the results in MPS format~\cite{marceau1971matrix}. Commercial systems such as
\texttt{MaGen} \cite{haverly1977magen}, \texttt{GAMMA} \cite{sperry1977gamma},
and \texttt{DATAFORM} \cite{ketron1975dataform}
were among the first matrix generators which were used in various domains.

\paragraph{A modern approach}
Modelers naturally think in terms of sets, indices, and algebraic expressions, not in terms of
individual matrix entries. Matrix generators simplified the encoding process but still required
modelers to translate their mathematical formulations into procedural code that explicitly
constructs the coefficient matrices. This suggests that the gap between the modeler's
representation of the problem and the solver's required format hadn't been resolved
yet \cite{fourer1978modern}.

\paragraph{Algebraic modeling languages}
In the late 1970s, \emph{algebraic modeling languages} emerged as formal languages designed to
accept problem descriptions that closely mirror standard mathematical
notation \cite{fourer1983modeling}. By working directly with the modeler's representation, these
languages simplify verification, modification, and communication.
In the late 1980s and early 1990s, commercial algebraic modeling
systems such as GAMS \cite{brooke1988gams}, AIMMS \cite{bisschop2006aimms} and
AMPL \cite{fourer1990ampl} became widely adopted in both academia and industry (and they are still
widely used today).

\paragraph{Embedded modeling languages}
In the late 2000s and early 2010s, modeling languages emerged that are embedded in general-purpose
programming languages (in contrast with standalone systems like AMPL and GAMS). Examples include
YALMIP \cite{lofberg2004yalmip} in MATLAB, Pyomo \cite{hart2011pyomo, bynum2021pyomo} in Python,
JuMP \cite{dunning2017jump} in Julia, and CasADi \cite{andersson2019} in C++.

\paragraph{Disciplined convex programming}
In addition, there are domain specific languages that implement \emph{disciplined convex
programming} (DCP), a set of composition rules that can automatically verify
convexity \cite{grant2004disciplined, grant2006disciplined}.
These include CVX \cite{cvx} in MATLAB, CVXPY \cite{diamond2016cvxpy, agrawal2018rewriting}
in Python, and Convex.jl~\cite{udell2014convex} in Julia.

\paragraph{Structure of the chapter}
The sections on canonicalization and matrix stuffing will be about CVXPY, the Python implementation
of DCP. The reasons are twofold: it is the most updated implementation which still has an active
community and the work of this thesis aims to be integrated in CVXPY.
In section \ref{sec:coefficient-extraction}, we present the embedded modeling language JuMP and one of
the original algebraic languages AMPL. In doing so, we also compare the differences with approaches
taken in CVXPY.
Both modeling languages treat the conic problem data as a form a sparse Jacobian computation so

Finally, all modeling languages use sparse matrix formats to store the problem data matrices, they

\section{Canonicalization}
\label{sec:canonicalization}

\paragraph{CVXPY.}
% TODO let's maybe enhance this intro a bit with more substance from the paper
CVXPY is a domain-specific language for convex optimization embedded in Python,
that was originally developed by Steven Diamond and Stephen Boyd at Stanford
University \cite{diamond2016cvxpy}. Akshay Agrawal later redesigned the
rewriting system in CVXPY \cite{agrawal2018rewriting}, 
which enabled support for other disciplined
languages \cite{agrawal2019dgp, agrawal2020dqcp, agrawal2019dpp}, and the
project has since grown through contributions from many others \cite{cederberg2025disciplined}.

\paragraph{Functional form.}
When a user specifies a CVXPY problem, it is usually in a ``functional'' form
\begin{equation}\label{eq:functional-form}
\begin{array}{ll}
\mbox{minimize} & f_0(x; \theta) \\
\mbox{subject to} & f_i(x; \theta) \leq g_i(x; \theta), \ i=1,\ldots,m_1,\\
& h_i(x; \theta) = j_i(x; \theta), \ i=1,\ldots,m_2,
\end{array}
\end{equation}
with variable $x \in \reals^n$ and parameter vector $\theta\in\reals^p$ \cite{boyd2004convex}.
For a given value of $\theta$ we refer to \eqref{eq:functional-form} as a problem instance,
otherwise for general values of $\theta$ it defines a problem family.
Each function in \eqref{eq:functional-form} is internally represented as an
expression tree.

\paragraph{Disciplined convex programming.}
When all $f_i$ are convex, all $g_i$ are concave and all $h_i$ and $j_i$ are both affine,
the functional form defines a convex optimization problem.
To verify that the problem is convex, CVXPY uses the DCP composition rules to classify
the curvature of functions.
Once all functions are classified, a problem is \emph{DCP-compliant} if its functions
satisfy the curvatures of a convex problem.
Otherwise, if certain curvatures are incorrect (\emph{i.e.} $f_0$ is concave) or unknown,
CVXPY will raise an error and terminate.

\paragraph{Composition rules.}
The expression $h(f_1(x), f_2(x), \dots, f_k(x))$ is convex when $h$ is convex and for each
$i \in \{1, \dots, k\}$ the following holds:
\begin{itemize}
    \item $h$ is non-decreasing in argument $i$ and $f_i$ is convex, or
    \item $h$ is non-increasing in argument $i$ and $f_i$ is concave, or
    \item $f_i$ is affine.
\end{itemize}
The same results hold for concave functions by swapping convex and concave.
Affine expressions require $h$ and all of its arguments to be affine \cite{grant2004disciplined}.

\paragraph{DPP composition rules.}
\emph{Disciplined parameterized programming} (DPP) is an extension of DCP which guarantees
an affine parameter dependence in the problem data. A problem is \emph{DPP-compliant} if it
satisfies the DPP composition rules. The rules essentially disallow products of expressions
involving parameters and can be referred to in \cite{agrawal2019dpp}.

\paragraph{Solver standard form.}
After a problem is verified to be DPP-compliant, CVXPY will convert the functional form 
problem to a target solver's standard form.

% make it specific about CVXPY.
% also list some supported solvers.
CVXPY supports solvers for quadratic programming
% maybe show the standard form for it?
 (such as OSQP and HiGHS), conic programming
(such as ECOS), and conic quadratic programming (such as Mosek and Clarabel).
% although we don't talk about quadratic objectives in this thesis, we want to note
% the following: it is not a major generalization (but algorithmically it can be tremendously
% better). And there are ways to go about supporting this (through computing the hessian),
% and maybe I can start pointing to future work.
The conic quadratic form is the most general of these, but is not a major generalization of the
cone form: any conic quadratic program can be reduced to an equivalent cone program by
linearizing the quadratic objective via the second-order cone, at the cost of one extra
variable and one extra constraint.
We will focus on the conic form throughout the thesis.

\paragraph{Reductions.}
Canonicalization converts a DPP-compliant model into a cone program via a sequence
of reductions \cite{agrawal2018rewriting}.

\paragraph{Maximization problems.}
A first example of a reduction is one which takes a maximization problem
and converts it into a minimization problem by flipping the sign of the objective.
The reverse transformation simply undoes the sign flipping and has no effect on the
actual solution of the problem.
In CVXPY, this reduction is conveniently called \texttt{FlipObjective}.

\paragraph{Variable bounds.}
A second example is variable attributes such as numerical bounds or \texttt{nonneg}.
During canonicalization, CVXPY will also verify if the target solver supports bounds
natively. If it does, CVXPY can pass them directly to solvers, otherwise they will
get converted into explicit constraints.
The reverse transformation for this reduction is to take the dual values corresponding
to the explicit constraints ($x\geq 0$) and setting them to be equal to the variable
bound's dual values.
In CVXPY, this reduction is part of a greater set of general attribute constraints
and is called \texttt{CvxAttr2Constr}.

\paragraph{Epigraph transformation.}
% TODO revisit this and maybe rewrite it entirely.
Each convex atom has a \textit{canonicalization} that replaces it with an
epigraph variable (for concave atoms it is a \emph{hypograph} variable)
and auxiliary constraints of the form $f(x, t, \theta) \in \mathcal K$ where
$t$ is the epigraph variable, $f$ is affine in the variables $(x, t)$ for fixed parameters
$\theta$, and $\mathcal K$ is a convex cone.
This process was presented initially in \cite{grant2008graph}.
One illustrative canonicalization replaces the \texttt{norm2} expressions in the objective with
a new epigraph variable $t_i$ and imposes the epigraph constraint known as a \emph{second-order}
cone constraint
\begin{equation}
(t_i, z_i) \in \mathcal K_{\mathrm{soc}}.
\end{equation}

\paragraph{Example of canonicalization.}
To show a concrete example of canonicalization, we consider a simple fitting with regularization
problem
\begin{equation}
    \begin{array}{ll}
        \text{minimize} & \|Fx-g\|_2 + \mu \|x\|_2\\
        \text{subject to} & x \succeq 0\\
    \end{array}
      \label{eq:example}
\end{equation}
with variable $x \in \reals^n$, fixed problem data $F\in \reals^{m\times n}$, and parameters
$g\in \reals^m$ and $\mu \geq 0$.
The problem formulation in CVXPY code is
\begin{lstlisting}[language=Python]
import cvxpy as cp
import numpy as np
F = np.random.randn(m, n)
x = cp.Variable(n)
g = cp.Parameter(m)
mu = cp.Parameter(nonneg=True)
objective = cp.Minimize(cp.norm(F @ x - g) + mu * cp.norm(x))
prob = cp.Problem(objective, [x >= 0])
\end{lstlisting}
where we also use the numerical computation library \texttt{NumPy} \cite{numpy} for
the data arrays. The expression tree representation of the problem
is shown in \ref{fig:dcp-syntax-tree}.

\paragraph{Conic form expression tree.}
After applying the reductions, the problem has been \emph{canonicalized} to
\begin{equation}\label{eq:graph}
\begin{array}{ll}
  \mbox{minimize}  & t_1 + \mu t_2 \\
  \mbox{subject to}  &
x \in \reals_+^n \\
& (t_1, Fx -g) \in \mathcal K_{\mathrm{soc},m+1} \\ 
& (t_2, x) \in \mathcal K_{\mathrm{soc},n+1} \\ 
\end{array}
\end{equation}
where $t_1$ and $t_2$ are new epigraph variables, and the cone $\mathcal K$ from
\ref{e:standard-form} is the product $\reals_+^n \times \mathcal K_{\mathrm{soc},m+1}
\times \mathcal K_{\mathrm{soc},n+1}$. In the next section, we explain how the
symbolic affine expression trees in \ref{fig:conic-form-tree} get converted into
the parameter maps defined in \ref{eq:param-maps}.

\section{Matrix stuffing}
\label{sec:matrix-stuffing}

In this section, we explain how to form the parameter maps from a set of affine expression
trees. In doing so, we also cover fundamental data structures and design choices
of these backends which can later be contrasted with the method proposed
in \ref{sec:Theme1}. Historically, the implementations of matrix stuffing
have been referred to as \emph{canonicalization backends},
and there has been many versions over the years.
We will focus on \texttt{cvxcore}, one of the original implementations in \texttt{C++},
and \texttt{SciPy}, an improved Python version which relies on the sparse matrix
library with the same name.

\paragraph{\texttt{Tensor} object.}
In physics, tensors are defined as [...].
In the canonicalization backends, this abstraction is also relevant but can
be made more precise. We consider a \texttt{Tensor} as a three-dimensional
array which represents a sparse linear mapping from a parameter vector
to the constraint matrix (as shown in \ref{eq:param-maps}).
The three indices of a \texttt{Tensor} are rows for constraints,
columns for variables, and parameter offsets for parameters.

\paragraph{Recursive walk.}
Fundamentally, matrix stuffing is relatively simple;
it requires a single depth-first walk of a set of affine expression trees,
where each tree represents a potentially vector-valued constraint.
Since the process is recursive, every node of an expression tree
will have an equivalent \texttt{Tensor}, and the final output
(the \texttt{Tensor} at the root node)
will give the constraint parameter map $\mathcal R$.
% TODO revisit how to write and explain this, or remove this sentence entirely.

\paragraph{Local vs. Global problem data.}
All modeling languages for optimization must at least do one thing correctly:
abstract away the task of placing \emph{local} tensors (or its equivalent)
at the expression level (where typically a single variable appears)
towards a \emph{global} tensor at the problem level
(where many more variables could be present).
% this might not be very clear, but it is a good start I think.
In fact, once we are able to compute the local tensor for all expressions
of interest, getting the global tensor simply comes down to combining the local
tensors and applying appropriate row and column \emph{offsets}.

\paragraph{Column and parameter offsets.}
Every variable is associated with an offset which indicates its index
in the global variable vector. In expressions which involve only a subset
of variables, we must make use of these offsets to correctly place
the problem data.
We also clarify that a single variable can have multiple entries or values,
therefore when we say number of variables, we refer to the number of variable
objects not the number of entries of the variable (which we refer to as its \emph{size}).
% can also mention that otherwise we call this the size of the variable.
% TODO rewrite this last sentence or remove since it could be obvious.

\paragraph{Row offsets.}
When an optimization model contains multiple constraints (this refers to constraint
objects), we must also be able to correctly place the problem data.
The offsets for constraints are used to keep track of the \emph{ordering} of the constraints.
They are also used to correctly place the problem data but on a different axis
than variables.

\section{Computing derivatives}
\label{sec:computing-derivatives}

Finding the rate of change or the \emph{derivative} of a function at a particular point is a
fundamental concept in calculus that was discovered by Leibniz and Newton in the late 1600s.
Since then, although the underlying theory has practically remained the same, various methods
have been developed to efficiently compute derivatives in different contexts and applications.
More recently, the rise of machine learning and deep learning brought renewed interest in this
age-old problem through a new application of derivatives in training \emph{neural networks},
it is known as the \emph{backward pass} or \emph{backpropagation} \cite{lecun2015deep,
Bottou2018Optimization}.
Some theorists will claim that backpropagation is little more than a clever application of the
\emph{chain rule} \cite{lecun1988theoretical}, but the large scale of modern workloads has led
to the development of incredible software tools and implementation techniques which are
interesting in their own right.
This section provides an overview of these new tools and techniques, with a particular
emphasis on \emph{algorithmic differentiation} (AD) and its applications to computing sparse
Jacobians \cite{griewank2008evaluating}.

\paragraph{Numerical differentiation.}
Other than computing derivatives by hand, the simplest method is to use \emph{numerical
differentiation}, which approximates the derivative of a function at a point by evaluating the
function at nearby points using a \emph{finite difference} formula similar to either
\begin{equation}
f'(x) \approx \frac{f(x + h) - f(x)}{h},
\end{equation}
or
\begin{equation}
f'(x) \approx \frac{f(x + h) - f(x - h)}{2h},
\end{equation}
where $h$ is a small step size. Although this approach is straightforward to implement and
can achieve reasonable accuracy, there are important downsides to consider.
First, it requires a linear number of function evaluations with respect to the number of
input variables, which is expensive for high-dimensional functions.
Second, it can easily lead to \emph{truncation errors} (when $h$ is too large) or
\emph{rounding errors} (when $h$ is too small) in the computed derivative if the step size is
not carefully chosen \cite{chakravarti1961truncation}.
Despite these downsides, numerical differentiation is still widely used in practice,
especially for verifying the correctness of derivative computations (also known as a
\emph{derivative checker}) \cite{wolfe1982checking}.

\paragraph{Symbolic differentiation.}
Mathematical expressions can be manipulated automatically using simple derivative rules of
calculus, such as the product and sum rule. This \emph{symbolic} approach to differentiation
is used in computer algebra systems such as Mathematica \cite{mathematica} and Maple
\cite{maple} as well as the SymPy library in Python \cite{sympy2017}.
Unlike its numerical counterpart, symbolic differentiation tools compute derivatives as
closed-form expressions, which can be simplified and evaluated at any arbitrary point.
These closed-form expressions are particularly useful for deriving analytic solutions of
optimization problems, and can be further used in mathematical proofs and analyses.

However, a naive implementation of symbolic differentiation can easily lead to exponentially
large symbolic expressions, which is impractical and inefficient for many problems
\cite{griewank2008evaluating}.
Interestingly, when intermediate expressions are stored as \emph{common subexpressions}, and
the expression is represented with a \emph{directed acyclic graph} (DAG) instead of a tree,
symbolic differentiation performs the same set of operations as \emph{reverse mode
differentiation} \cite{Laue2019OnTE}.

\paragraph{Algorithmic differentiation.}
There is a lot of confusion on the terminology surrounding the various methods for computing
derivatives; \emph{automatic differentiation} and \emph{computational differentiation} are
often used to describe the field, but we will instead refer to it as \emph{algorithmic
differentiation} since it emphasizes the algorithms behind the different implementations
rather than a particular method (it is also the convention in the seminal book by Griewank
and Walther \cite{griewank2008evaluating}).
Fundamentally, AD is a non-standard interpretation of a computer program: it augments the
\emph{evaluation trace} of a function (the sequence of floating point values calculated during
the execution) with calculations of its derivatives \cite{baydin2017ADsurvey}.
This trace can be represented as a \emph{computational graph}, a DAG in which each node
corresponds to an elementary operation with known derivatives.
Combining the derivatives of these operations throughout the graph using the chain rule gives
the derivative of the overall function \cite{griewank2008evaluating}.
The computational graph is the central data structure of AD; the various \emph{modes} of AD
correspond to different ways elementary derivatives are accumulated on this graph.

\paragraph{Forward mode AD.}
The method of propagating tangents forward through the computational graph is known as
\emph{forward mode} AD.
A single forward pass simultaneously computes the value and derivative of every intermediate
variable with respect to a single input variable, giving the sensitivity of all outputs to
that input.
The cost of a forward pass is a small constant factor of the cost of evaluating the original
function, since each elementary operation is augmented with at most a few additional
arithmetic operations for the derivatives.
However, one downside of forward mode AD is that the number of forward passes scales linearly
with the number of input variables, which is impractical for certain functions (which have
many input variables and very few output variables).

\paragraph{Reverse mode AD.}
In contrast to forward mode, \emph{reverse mode} AD propagates adjoints backward through the
computational graph.
It first requires a forward pass to compute and store the value of every intermediate
variable, and it then performs a reverse pass to compute the sensitivities of a single output
variable with respect to all input variables.
The cost of a reverse pass is also a small constant factor of the cost of evaluating the
original function, but the number of passes required now scales linearly with the number of
output variables rather than the number of input variables.
This makes reverse mode AD particularly efficient for computing gradients of scalar-valued
functions, making it the default method for modern machine learning libraries such as Jax
\cite{jax2018github}, Pytorch \cite{pytorch2019}, and Tensorflow \cite{tensorflow2016}.

\section{Sparse matrices}
\label{sec:sparse-matrices}

Matrices that contain many number of zero entries are known as \emph{sparse matrices}.
The simplest sparse matrix data structure is the \emph{coordinate} or \emph{triplet}
format. It consists of two integer index arrays \texttt{rows} and \texttt{cols} and a floating point
value array \texttt{vals} of length equal to the number of \emph{nonzero entries} in the matrix.

For example, the matrix
\begin{equation}\label{eq:sparse-matrix}
  \begin{bmatrix}
  0 & 0 & 3.2 & 0\\
  4.1 & 1.8 & 0 & 2.2\\
  0 & 2.8 & 0 & 3.4\\
  \end{bmatrix}
\end{equation}
can be represented in coordinate format as
\begin{lstlisting}[language=C]
int     rows[] = {0,    1,    1,    1,    2,    2};
int     cols[] = {2,    0,    1,    3,    1,    3};
double vals[] = {3.2,  4.1,  1.8,  2.2,  2.8,  3.4};
\end{lstlisting}

where we use zero-based indexing and array declaration notation from the C programming
language \cite{Kernighan1988}.
The coordinate format is the easiest to understand and form, but it is not effective for most
operations on sparse matrices; the \emph{compressed sparse row} or CSR format is commonly
used instead.

\paragraph{Compressed sparse row format.}
The CSR format differs from the coordinate format in that it replaces the \texttt{rows} array with
a row pointer array \texttt{idxptr} of length equal to the number of rows plus one.
The row pointer array indicates the starting index of each row in the \texttt{cols} arrays.
For example, the matrix in \eqref{eq:sparse-matrix}
can be represented in CSR format as
\begin{lstlisting}[language=C]
int  idxptr[] = {0,    1,                4,         6};
int    cols[] = {2,    0,    1,    3,    1,    3};
double vals[] = {3.2,  4.1,  1.8,  2.2,  2.8,  3.4};
\end{lstlisting}
where we deliberately format \texttt{idxptr} to align with the start of each
row in the \texttt{cols} arrays.
% talk about benefits of CSR format. fast row slicing, fast matrix-vector products, etc.
The benefits of the CSR format are more than a reduced size of the \texttt{idxptr} array
compared to the \texttt{rows} array.
In the CSR format, accessing a row takes constant time and is very \emph{cache-friendly}
since the nonzero entries are stored contiguously in memory.
For this reason, the CSR format is the default for \emph{iterative methods}
to solve sparse linear systems \cite{saad2003iterative}.

\paragraph{Compressed sparse column format.}
% talk about CSC as a direct extension of CSR but with column pointers.
However, one downside of the CSR format is that accessing a column is much more difficult;
one would need to look at every row to find the nonzero entries in a column.
An alternative format is the \emph{compressed sparse column} or CSC format, 
which swaps the role of the \texttt{idxptr} array to refer to column indices instead.
In contrast to iterative methods, the CSC format is the preferred format for
\emph{direct methods} to solve sparse linear systems \cite{davis2006direct}.

\paragraph{Other formats.}
The coordinate, CSR and CSC formats are the most widely used sparse matrix formats,
but many others exist for different specialized use cases.
The scientific Python sparse library \texttt{scipy.sparse} \cite{2020SciPy-NMeth}
allows users to form other types of sparse matrices such as the list of lists (LIL) matrix,
the dictionary of keys (DOK) matrix, and the block-sparse row (BSR) matrix.

\paragraph{Sparse matrix struct in C.}
A CSR matrix struct in C looks like this.
\begin{lstlisting}[language=C]
typedef struct CSR_Matrix {
    int *p;       /* row pointers, size m+1   */
    int *i;       /* column indices, size nnz */
    double *x;    /* values, size nnz         */
    int m, n, nnz;
} CSR_Matrix;
\end{lstlisting}
