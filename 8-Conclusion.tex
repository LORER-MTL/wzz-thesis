\Chapter{CONCLUSION}\label{sec:Conclusion}
\acresetall

Throughout this Master's thesis, we revisit the performance of compiling a high-level
model into conic problem data. Despite being essential to solving optimization problems, the
compilation step has mostly been an afterthought. The reason for this is that the cost is
often negligible, and when it is not, most users accept it as necessary. In our work, we take
the perspective of computing the coefficients of the problem data as sparse derivatives, which
differs from most modelling languages. The closest is \texttt{CasADi}, whose
\ac{AD} is built for general nonlinear functions. Applied to affine functions, where the
coefficients follow directly from the constants of the expression graph, \texttt{CasADi}
would still need to detect the sparsity patterns at runtime and compress the Jacobian
computation by graph colouring.
\texttt{AMPL} and \texttt{JuMP} take the coefficients as the user declares them, but both
scalarize the model. A dense block in the problem data becomes a list of scalar
coefficients. \texttt{CVXPY}'s backends, on the other hand, convert everything to sparse
matrices. No modelling language that forms the problem matrix keeps dense blocks as they are.
To address this, we
built \texttt{SparseDiffEngine}, a sparse differentiation library that operates on
vectorized expressions without scalarizing them, requires no sparsity detection or graph
colouring, and mixes sparse and dense formats throughout the computation. In addition to
using BLAS operations and dense storage on dense blocks, we implement a two-phase approach
which caches many computations during the symbolic pass. For parametric problems, the
numeric pass reuses these computations, with no restrictions on how the parameters enter
the problem.

We also propose \texttt{diffengine}, a new canonicalization backend for \texttt{CVXPY} with a
simple interface to \texttt{sparsediffpy}, the Python bindings of
\texttt{SparseDiffEngine}. We compare
\texttt{diffengine} with \texttt{CVXPY}'s three existing backends in numerical
experiments and obtain promising results. They allow us to conclude that
\texttt{diffengine} can replace \texttt{cvxcore} as the default backend of \texttt{CVXPY}
in certain circumstances. Overall, the work in this thesis is based on a combination of
fundamental subjects in matrix computations, computing derivatives, and modelling languages
for optimization.

\section{Limitations}\label{sec:Limitations}

The benchmark suite of \texttt{CVXPY} is a collection of synthetic problems accumulated over
the years by the library's developers~\cite{cvxpybenchmarks}. However, it is not a standard
benchmark collection like the ones maintained for optimization solvers. Two examples are the
Mittelmann benchmarks~\cite{mittelmann2020benchmarking} and the repository of convex
\acp{QP} of Maros and M\'esz\'aros~\cite{maros1999repository}. Unfortunately, these
collections distribute their
instances in standard form, ready to be passed to the solver, so there is no high-level
model to compile. Our conclusions therefore rely on a single suite, and their generality is
not yet completely validated. If and when a standard benchmark suite written at the
modelling level becomes available, the experiments of Chapter~\ref{sec:Theme2} should be
run again on it.
It would also allow us to begin comparing compilation times across modelling languages.
The difficulty in creating such a suite is that every modelling language has its own syntax
and conventions, so the problems would have to be written once per language.

The results of Chapter~\ref{sec:Theme2} also show that the peak memory of
\texttt{diffengine} is higher on several problems of the suite. Part of the cost is the
cached problem itself. The numeric pass evaluates the expression trees at every parameter
change, so the \texttt{problem} object must stay in memory for the lifetime of the problem
family. The parameter-to-data tensor does not have this constraint. Once the tensor is
built, a re-solve needs only its product with the current parameter values, and the
formulation can be set aside. This decoupling brings similar benefits as \texttt{AMPL}'s
\texttt{.nl} format, which separates the problem instance from the model.
The separated data can be archived, shipped to another machine, and used by downstream packages
such as \texttt{CVXPYgen}~\cite{schaller2022cvxpygen} and \texttt{CVXPYlayers}~\cite{agrawal2019dpp}.
Another part of the memory cost comes from the global layout. Every node of the expression
trees holds a Jacobian over all $n$ variables, together with integer work arrays of
length~$n$. The values stored remain proportional to the nonzeros, but this overhead grows
with the number of nodes times the number of variables. On problems with very many
variables and deep trees, it can exceed the memory of \texttt{CVXPY}'s local layout, whose
blocks span only the variables that each node depends on.

\section{Future Research}\label{sec:FutureResearch}

The contributions of this thesis range from the creation of new packages, to improvements
of existing ones, to new data structures and algorithms. For this reason, we see three
directions for future work, one in each type of contribution.
The first direction concerns \texttt{sparsediffpy}. We plan to add a standalone
Python interface, so that the sparse Jacobians and Hessians can be built and evaluated
without \texttt{CVXPY}. We believe there can be many applications of such derivatives without
necessarily calling an optimization solver. The user would build the expression trees directly with
the functions of \texttt{sparsediffpy} instead of with \texttt{CVXPY} expressions.

The second direction is closer to development than research. It covers the remaining work
on the \texttt{diffengine} backend within
\texttt{CVXPY}. The immediate goal is to make \texttt{diffengine} the default backend on the
\texttt{ignore\_dpp} path. One challenge is that existing reductions must change behaviour
without breaking backwards compatibility. The next task is the removal of
\texttt{cvxcore}, which the \texttt{CVXPY} developers have already deprecated. The removal
would mean that \texttt{CVXPY} no longer needs to compile and ship C++ binaries, which
would simplify the build process of the library. As a replacement, \texttt{diffengine} can
become the new default backend, with \texttt{COO} as an alternative candidate for \ac{DPP}
problems. A further improvement concerns parameter updates. On the problems where the tensor
re-solves faster, most of a re-solve goes to converting the engine's output to the solver's
format (\S\ref{sec:bench-param}), although the sparsity patterns do not change between
re-solves. Computing this conversion once, in the symbolic pass, would let a re-solve write
the new values directly into the final matrices. Another improvement concerns dense constants.
The backend keeps a constant factor of a matrix product as a dense block when at least
$5\,\%$ of its entries are nonzero, and the constant matrix of a quadratic objective whenever
it is given as a dense array. A density test set from the cost of the kernels, and applied to
the quadratic objective as well, would reduce the slowdowns of ConvexPlasticity and of the density experiment
(\S\ref{sec:bench-oneshot} and \S\ref{sec:bench-sensitivity}).

The final direction would be to extend the permuted dense matrix classes of
Chapter~\ref{sec:Theme1} to the rest of the
optimization process. Both the presolve and the solver operate on a generic sparse matrix,
where the dense blocks are no longer explicit. The high-level step would be to pass the
block structure along with the problem data, so that the presolve and the factorization can
work on the dense blocks directly instead of rediscovering them in a sparse
matrix~\cite{davis2006direct}. This change would require much
more research, because nothing beyond basic intuition indicates that it is worth doing.
For existing presolve
routines and sparse linear system solvers, it would also require adapting their code to
operate on matrix representations other than the typical sparse matrix.
