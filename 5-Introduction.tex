\Chapter{INTRODUCTION}\label{sec:Introduction}

Since the early days of linear programming, optimization practitioners
have needed to translate mathematical formulations into data that solvers can process.
At first, this meant encoding each coefficient of the problem matrices by
hand~\cite{fourer1978modern}.
Matrix generators were introduced in the late 1960s to automate this task: they compute the
coefficients through explicit loops and write them out in solver-readable formats like
MPS~\cite{marceau1971matrix, ibm1976mpsx}.
Matrix generators were able to remove most of the manual labour, but a gap still remained.
Modellers naturally think in terms of sets, indices, and algebraic expressions,
while procedural code constructs the coefficient matrices entry by entry.
This mismatch between how a model is expressed and how it is implemented made models difficult to
verify, modify, and communicate with others \cite{fourer1983modeling}.
Algebraic modelling languages such as \texttt{AMPL} \cite{fourer1990ampl},
\texttt{AIMMS} \cite{bisschop2006aimms}, and \texttt{GAMS} \cite{brooke1988gams} closed this gap by
accepting problem descriptions that closely follow the mathematical formulation.
The survey \cite{orchard-hays1984history} provides a complete overview
of the early history of modelling languages.

More recently, modelling languages embedded in general-purpose programming languages have
gained popularity. These include \texttt{Pyomo} \cite{bynum2021pyomo, hart2011pyomo} in Python,
\texttt{JuMP} \cite{dunning2017jump} in Julia, \texttt{CasADi} \cite{andersson2019} in C++, and
\texttt{YALMIP} \cite{lofberg2004yalmip} in MATLAB.
Other domain-specific modelling languages specialized for convex optimization \cite{boyd2004convex}
are built on disciplined convex programming (DCP), the composition rules under which the
convexity of a problem can be verified automatically
\cite{grant2004disciplined, grant2006disciplined}.
These DCP-based languages include \texttt{CVX} \cite{cvx} in MATLAB, \texttt{CVXR} \cite{Fu_2020} in
R, \texttt{CVXPY} \cite{diamond2016cvxpy} in Python, and \texttt{Convex.jl}
\cite{udell2014convex} in Julia.

In the meantime, modern general-purpose solvers \cite{mosekSolver, ge2022copt, clarabel}
have mostly transitioned towards conic programming, which generalizes linear programming and
can represent and solve nearly every convex program used in practice \cite{bental2001lectures}.
The translation task remains a responsibility of the modelling languages, which now target
conic problem data instead of \ac{LP} coefficient matrices. In DCP-based languages, this
translation process is called canonicalization \cite{agrawal2018rewriting}.
While the time taken to solve an optimization problem is often dominated by the solver, the
time taken to canonicalize (or \emph{compile}) it can also be significant \cite{agrawal2019dpp}.
The main goal of this Master's thesis is to reduce the compilation time of \texttt{CVXPY}.

\section{Problem statement}\label{sec:problem-statement}

The standard form of a convex optimization problem is
\BEQ \label{e:parametric-family}
\begin{array}{ll}
\underset{\mvec{x} \in \reals^n}{\mbox{minimize}}   & f_0(\mvec{x}; \gvec{\theta}) \\
\mbox{subject to} & f_i(\mvec{x}; \gvec{\theta}) \le 0, \quad i = 1,\ldots,m_1 \\
                  & g_j(\mvec{x}; \gvec{\theta}) = 0, \quad j = 1,\ldots,m_2
\end{array}
\EEQ
where $\mvec{x} \in \reals^n$ is the optimization variable, the objective
$f_0 : \reals^n \times \reals^p \to \reals$ and inequality constraint functions
$f_1,\ldots,f_{m_1} : \reals^n \times \reals^p \to \reals$ are convex, and the equality
constraint functions $g_1,\ldots,g_{m_2} : \reals^n \times \reals^p \to \reals$ are affine
\cite{boyd2004convex}.
The parameter $\gvec{\theta} \in \reals^p$ specifies data that can change between solves but is fixed
and given when solving an instance of the problem. We call the parametrized problem \eqref{e:parametric-family}
a problem family; for a fixed value of $\gvec{\theta}$, we call it a problem instance.

% \paragraph{Quadratic conic form.}  (heading removed per advisor; kept for reference)
Canonicalization converts the high-level description \eqref{e:parametric-family} to a
quadratic conic form used by many general-purpose convex solvers
\BEQ \label{e:quad-conic-form}
\begin{array}{ll}
\underset{\mvec{x} \in \reals^n}{\mbox{minimize}} & \frac{1}{2} \mvec{x}^\top \mmat{P}(\gvec{\theta}) \mvec{x} + \mvec{c}(\gvec{\theta})^\top \mvec{x}\\
\mbox{subject to} & \mvec{b}(\gvec{\theta})-\mmat{A}(\gvec{\theta})\mvec{x} \in \cone{K}
\end{array}
\EEQ
where the \emph{problem data} are the symmetric positive semidefinite matrix
$\mmat{P}(\gvec{\theta}) \in \symm^n_+$,
the matrix $\mmat{A}(\gvec{\theta}) \in \reals^{m \times n}$, the vectors
$\mvec{b}(\gvec{\theta}) \in \reals^m$ and
$\mvec{c}(\gvec{\theta}) \in \reals^n$, and the non-empty closed convex cone
$\cone{K} \subseteq \reals^m$.
Problem \eqref{e:quad-conic-form} generalizes both quadratic programs (QPs), when
$\cone{K} = \reals^m_+$ is the nonnegative orthant, and standard conic programs, when
$\mmat{P}(\gvec{\theta}) = 0$.

% \paragraph{Canonicalization in \texttt{CVXPY}.}  (heading removed per advisor; kept for reference)
Most of the cost of canonicalization lies in the final step, where symbolic
expression trees are converted to numerical problem data.
This step is often called matrix stuffing or the backend of canonicalization
\cite{zhang2026cvxpy}.
During the first solve of a problem family, \texttt{CVXPY} forms and caches a
parameter tensor that maps the parameter vector to the problem data.
On subsequent solves, new problem data can be obtained with a single matrix-vector product
\cite{agrawal2019dpp}.

For large-scale problems, forming the parameter tensor can be prohibitively expensive, so
\texttt{CVXPY} lets users opt out of it entirely.
Users must thus choose between paying a large upfront cost on the first solve and repeating
the full canonicalization, with nothing reused, at every solve.
We review \texttt{CVXPY} and the frontend of canonicalization in \S\ref{sec:intro-canon},
as well as the parameter tensor and matrix stuffing in \S\ref{sec:matrix-stuffing}.

% \paragraph{Matrix stuffing as a derivative.}  (heading removed per advisor; kept for reference)
The constraint matrix~$\mmat{A}$ is the Jacobian of the stacked constraint expressions and
$\mmat{P}$ is the
Hessian of the objective, so matrix stuffing amounts to computing a sparse Jacobian and Hessian.
Classical methods build these matrices column by column with multiple passes of algorithmic
differentiation (AD), using graph colouring to group columns that can be recovered in a single
pass \cite{curtis1974estimation, gebremedhin2005color}.
These methods treat the expression as a blackbox: the sparsity pattern must first be
detected and the columns grouped before a single entry of the matrix is obtained.
We review the basics of computing derivatives in \S\ref{sec:bg-derivatives} and present
sparse AD and graph colouring methods in \S\ref{sec:computing-derivatives}.

% \paragraph{Other approaches.}  (heading removed per advisor; kept for reference)
A modelling language, by contrast, knows which variables enter each constraint.
\texttt{AMPL} (A Mathematical Programming Language) is split into two components: its commercial
translator writes the structure of the model to a \texttt{.nl} file
\cite{gay2005writing}, and the open source AMPL Solver Library (ASL) evaluates constraints
and their derivatives from this file inside the solver process \cite{gay1997hooking}.
\texttt{Pyomo} also interfaces to solvers through \texttt{.nl} files,
among other formats, though it generally writes them more slowly than the \texttt{AMPL}
translator.

On the other hand, \texttt{JuMP} has no single standard form to target;
it decouples modeller and solver through \ac{MOI}, a typed in-memory interface
\cite{legat2020mathoptinterface}.
The model is built constraint by constraint, and each constraint stores its coefficients directly,
so extraction reduces to copying them into the format of the chosen solver.
None of these approaches operates on expression trees: the AD tools record the expression as a
flat tape of instructions, \texttt{AMPL} exchanges the model through a file, and \texttt{JuMP}
stores lists of coefficients. In \texttt{CVXPY} the expression trees themselves are the input
of the backend.
We review both these modelling languages in \S\ref{sec:declared-structure}.

\paragraph{Our approach.}
We make use of the fact that the sparsity patterns of $\mmat{A}$ and $\mmat{P}$ are fixed
across a problem
family, because the parameter $\gvec{\theta}$ changes the values of the problem data but not
their structure.
We can therefore split matrix stuffing into a symbolic and a numeric phase.
The symbolic phase runs once on the first solve, where it computes the sparsity patterns,
allocates memory for all intermediate matrices, and caches other computations that remain valid
across the problem family.
The numeric phase then fills in new values at every solve.
This separation between structure and values is inspired by the interfaces of \ac{NLP}
solvers such as \texttt{IPOPT} \cite{wachter2006ipopt, cederberg2025disciplined}.

The symbolic phase is much cheaper to form and cache than the parameter tensor, and the
numeric phase is often similar in cost to applying the matrix-vector product.
The problem data is also assembled entirely in memory rather than through a separate model
file.
Finally, we exploit structure within the sparsity patterns themselves, which often contain dense
blocks of data.
When possible, we store these blocks as dense matrices and compute with dense linear algebra
kernels, rather than always relying on generic sparse formats and routines (we provide
background on dense and sparse matrix computations in \S\ref{sec:intro-matrix}).

\section{Canonicalization}\label{sec:intro-canon}
The problem family \eqref{e:parametric-family} is written in functional form, as objective and
constraint functions of the variable and the parameters.
In a modelling language, the optimization variables $\mvec{x}_1,\ldots,\mvec{x}_k$ are collected
into a single
vector $\mvec{x} \in \reals^n$, and likewise the parameters $\gvec{\theta}_1,\ldots,\gvec{\theta}_l$
into $\gvec{\theta} \in \reals^p$ \cite{boyd2004convex}.
Users are not required to write constraints with a zero right-hand side as in
\eqref{e:parametric-family}. Modelling languages accept inequalities with a convex left-hand
side and a concave right-hand side, and equalities with both sides affine.
Converting to the form \eqref{e:parametric-family} is trivial and only requires moving every
term to the left-hand side.
Internally, each function is represented as an \emph{expression tree}.

% \paragraph{Atoms.}  (heading removed per advisor; kept for reference)
Modelling languages for convex optimization are built on top of a library of functions which can be
used to describe problems. These functions are known as \emph{atoms} in \texttt{CVXPY} because they
are the fundamental building blocks of the modelling language \cite{grant2004disciplined}.
Alongside its numerical definition, each atom declares useful attributes such as
its curvature, monotonicity with respect to each argument, and the
sign of its output. A selection of common atoms is shown in Table~\ref{tab:atoms}.

% \paragraph{Expression trees.}  (heading removed per advisor; kept for reference)
An expression is defined recursively as an atom evaluated at \emph{subexpressions}, each of which is
itself another expression. Such an expression is naturally stored as an expression tree,
with atoms at its internal nodes and variables, parameters, and constants at its leaves.
In Python, this tree can be formed automatically from user code through operator overloading.
Most operations on an expression, from evaluation to verifying convexity to
differentiation, traverse the tree and combine the intermediate results at each node.

% \paragraph{Disciplined convex programming.}  (heading removed per advisor; kept for reference)
To certify the convexity of a problem, DCP-based modelling languages use the DCP composition
rules to classify
the curvature of each function \cite{grant2004disciplined}.
Once all functions are classified, a problem is \emph{DCP-compliant} if the objective and
each constraint have curvatures compatible with a convex problem: a convex objective,
convex $\leq$ concave inequalities, and affine equalities.
Otherwise, if a curvature is incompatible (\emph{e.g.}, $f_0$ is concave) or cannot be
determined, the modelling language raises an error and terminates.
Because these rules are only sufficient for convexity, a problem that is genuinely convex
but not expressed in a recognized form may still be rejected.

% Subexpressions renamed from f_i to u_i per the advisor's annotation: f_i already denotes the
% inequality constraints of the problem family.
% \paragraph{Composition rules.}  (heading removed per advisor; kept for reference)
The composition $\phi(u_1(\mvec{x}), u_2(\mvec{x}), \dots, u_k(\mvec{x}))$ of an atom
$\phi : \reals^k \to \reals$ with subexpressions $u_i : \reals^n \to \reals$
is convex when $\phi$ is convex and, for each argument $i \in \{1, \dots, k\}$, one of the
following holds:
\begin{itemize}
    \item $\phi$ is non-decreasing in argument $i$ and $u_i$ is convex;
    \item $\phi$ is non-increasing in argument $i$ and $u_i$ is concave; or
    \item $u_i$ is affine.
\end{itemize}
The same results hold for concave functions by swapping convex and concave.
Affine expressions require $\phi$ and all of its arguments to be affine \cite{grant2004disciplined}.

\subsection{Conic reformulation}\label{sec:bg-canonicalization}

Once a problem is verified to be DCP-compliant, canonicalization
rewrites its functional form \eqref{e:parametric-family} into an equivalent functional conic form
\BEQ\label{eq:conic-form}
\begin{array}{ll}
\underset{\mvec{x} \in \reals^n}{\mbox{minimize}}   & f_0(\mvec{x}; \gvec{\theta}) \\
\mbox{subject to} & h_i(\mvec{x}; \gvec{\theta}) \in \cone{K}_i, \quad i = 1,\ldots,m,
\end{array}
\EEQ
where $f_0$ is affine or quadratic, each $h_i : \reals^n \times \reals^p \to \reals^{d_i}$ is
affine, and each $\cone{K}_i \subseteq \reals^{d_i}$ is one of
the standard cones supported by general-purpose conic solvers: the zero, nonnegative,
second-order, power, exponential, and positive semidefinite cones.

% \paragraph{Conic reformulation.}  (heading removed per advisor; kept for reference)
Every nonlinear atom is rewritten into conic constraints in three steps.
The first step rewrites the problem into \emph{Smith form}, where each
nonlinear atom is replaced by a new variable coupled with an equality constraint; every atom
then acts only on affine arguments \cite{smith1996}.
For a convex atom $\phi$, the Smith form gives an auxiliary variable $t \in \reals$ with the
equality constraint $\phi(\mvec{x}) = t$. The second step relaxes this equality to the
inequality $\phi(\mvec{x}) \le t$.
The DCP rules allow a convex atom only where its value is minimized or upper-bounded, so the solver
always prefers $t$ as small as possible; the relaxation is therefore lossless.
The pair $(\mvec{x}, t)$ then lies in the \emph{epigraph}
$\{(\mvec{x}, t) \in \reals^n \times \reals : \phi(\mvec{x}) \le t\}$ of $\phi$, so we
often refer to $t$ as an \emph{epigraph variable}.
A concave atom relaxes to $\phi(\mvec{x}) \ge t$ instead, giving a \emph{hypograph variable}.
The third and final step expresses each epigraph (hypograph) inequality as the membership of
an affine function of $(\mvec{x}, t)$ in a convex cone \cite{grant2008graph}.

\paragraph{Example of reformulations.}
A first example is the $\ell_2$ norm atom $\|\mvec{x}\|_2$ of $\mvec{x} \in \reals^n$, whose
epigraph $\|\mvec{x}\|_2 \le t$ is exactly the second-order cone constraint
$(t, \mvec{x}) \in \cone{K}_{\mathrm{soc}}$, where
$\cone{K}_{\mathrm{soc}} = \{(t, \mvec{x}) \in \reals \times \reals^n : \|\mvec{x}\|_2 \le t\}$.
A second example is the nondifferentiable absolute value atom $|x|$ of a scalar $x$, whose
epigraph $|x| \le t$ can
be written as the pair of affine inequalities $-t \le x \le t$.
A final example is the sum of the $k$ largest entries of $\mvec{x}$, which expands into a small
\ac{LP}: the epigraph $\mathrm{sum\_largest}(\mvec{x}, k) \le t$ holds if and only if there exist a
scalar $q \in \reals$ and a vector $\mvec{w} \in \reals^n$ such that
% Auxiliary vector renamed u -> w: u_i already denotes the subexpressions of the composition
% rules above.
\BEQ\label{eq:sum-largest}
q\ones + \mvec{w} \ge \mvec{x}, \qquad \mvec{w} \ge 0, \qquad kq + \ones^\top \mvec{w} \le t,
\EEQ
where the inequalities are applied element-wise.
Here $q$ acts as a threshold and each $w_i$ measures how far the entry $x_i$ rises above it, so that
the sum of the $k$ largest entries is bounded by $kq + \ones^\top \mvec{w}$ \cite{boyd2004convex}.

\subsection{\texttt{CVXPY}}\label{sec:canonicalization}

\texttt{CVXPY} is a DCP-based modelling language embedded in Python \cite{diamond2016cvxpy},
which began in 2013 as an implementation of the modelling principles of \texttt{CVX} \cite{cvx}.
It differed from \texttt{CVX} in three design decisions: modular components built around a few
shared data structures, the expression tree formed by Python's operator overloading as the
central representation, and support for parameters, which lets compilation work be reused when
a problem is solved repeatedly.
These ideas matured with version 1.0, which redesigned canonicalization as
a general reduction-based rewriting system \cite{agrawal2018rewriting}.
The new design enabled the addition of other disciplined
grammars \cite{agrawal2019dgp, agrawal2020dqcp, cederberg2025disciplined}, and the early
parameter support grew into DPP, a restricted grammar
under which canonicalized programs can be updated efficiently \cite{agrawal2019dpp}.

The open source project has since grown through contributions from many other enthusiastic
developers; a recent paper surveys the new canonicalization and modelling features
introduced between versions 1.1 and 1.9 \cite{zhang2026cvxpy}.

% \paragraph{Reductions.}  (heading removed per advisor; kept for reference)
The rewriting from the functional form \eqref{e:parametric-family} to the functional conic form
\eqref{eq:conic-form} is carried out as a sequence of \emph{reductions}. Each reduction provides an
\texttt{apply} step that converts a problem into an equivalent one, and a \texttt{retrieve}
step that recovers a solution of the original problem from a solution of the rewritten one
\cite{agrawal2018rewriting}.
A first example is \texttt{FlipObjective}, which turns a maximization problem into a
minimization one by flipping the sign of the objective, and flips it back in its
\texttt{retrieve} step.
A second example is \texttt{CvxAttr2Constr}, which replaces variable attributes such as
nonnegativity with explicit constraints when the target solver does not support them natively.

% \paragraph{The \texttt{Dcp2Cone} reduction.}  (heading removed per advisor; kept for reference)
The main reduction, \texttt{Dcp2Cone}, applies the epigraph reformulation of
\S\ref{sec:bg-canonicalization} atom by atom: the problem is first rewritten into Smith form,
each resulting equality is relaxed to an epigraph (or hypograph) inequality, and each
inequality is finally expressed as a cone membership \cite{smith1996, grant2008graph}.
In practice the three steps are performed at once: each nonlinear atom is replaced directly by its
epigraph variable and cone constraints, and the intermediate Smith form and its relaxation
never appear explicitly.

\subsection{Example}\label{sec:canon-example}
We consider a simple fitting with regularization problem:
\BEQ
    \begin{array}{ll}
        \underset{\mvec{x} \in \reals^n}{\text{minimize}} & \|\mmat{F}\mvec{x}-\mvec{g}\|_2 + \mu \|\mvec{x}\|_2\\
        \text{subject to} & \mvec{x} \ge 0\\
    \end{array}
      \label{eq:example}
\EEQ
% Constraint written x >= 0 instead of x \succeq 0 per the advisor's note: (1.4) already uses
% element-wise >=, and \succeq is reserved for PSD or general cone orders.
with variable $\mvec{x} \in \reals^n$, fixed problem data $\mmat{F}\in \reals^{m\times n}$, and
parameters
$\mvec{g}\in \reals^m$ and $\mu \geq 0$; the constraint $\mvec{x} \ge 0$ requires every entry of
$\mvec{x}$ to be nonnegative.
The problem formulation in \texttt{CVXPY} code is
\begin{lstlisting}[language=Python]
import cvxpy as cp
import numpy as np
F = np.random.randn(m, n)
x = cp.Variable(n)
g = cp.Parameter(m)
mu = cp.Parameter(nonneg=True)
objective = cp.Minimize(cp.norm(F @ x - g) + mu * cp.norm(x))
prob = cp.Problem(objective, [x >= 0])
\end{lstlisting}
where we also use the numerical computation library \texttt{NumPy} \cite{numpy} for
the data arrays. The expression tree representation of the problem
is shown in Figure~\ref{fig:dcp-expression-tree}.

% \paragraph{Conic form expression tree.}  (heading removed per advisor; kept for reference)
After applying the reductions, the problem has been \emph{canonicalized} to
\BEQ\label{eq:graph}
\begin{array}{ll}
  \underset{t_1,\, t_2,\, \mvec{x}}{\mbox{minimize}}  & t_1 + \mu t_2 \\
  \mbox{subject to}  &
\mvec{x} \ge 0 \\
& (t_1, \mmat{F}\mvec{x} -\mvec{g}) \in \cone{K}_{\mathrm{soc},m+1} \\
& (t_2, \mvec{x}) \in \cone{K}_{\mathrm{soc},n+1} \\
\end{array}
\EEQ
where $t_1, t_2 \in \reals$ are new epigraph variables, and the cone $\cone{K}$ from
\eqref{e:quad-conic-form} is the product $\reals_+^n \times \cone{K}_{\mathrm{soc},m+1}
\times \cone{K}_{\mathrm{soc},n+1}$.
Problem \eqref{eq:graph} is now in the functional conic form of \S\ref{sec:bg-canonicalization}:
every constraint
is a cone membership, and the objective and constraint expressions are affine.
Comparing the DCP trees of Figure~\ref{fig:dcp-expression-tree} with the trees of
Figure~\ref{fig:conic-form-tree} shows the effect of canonicalization: the nonlinear norm atoms
have been replaced by epigraph variables, leaving affine expression trees in the variables,
which we call the conic-form trees of the problem.
The three rows of \eqref{eq:graph} remain three separate cone constraints, each carrying the
affine expressions that must lie in its cone; Figure~\ref{fig:conic-form-tree} accordingly shows
one expression tree per constraint, rather than a single combined tree.

\section{Computing derivatives}\label{sec:bg-derivatives}

Computing derivatives is a fundamental task in scientific computing, with many methods that
differ in cost, in accuracy, and in the form of the result \cite{baydin2017ADsurvey}.
The derivatives in this Master's thesis are the constraint Jacobian~$\mmat{A}$ and the objective
Hessian~$\mmat{P}$ of a canonicalized problem, both large sparse matrices.
Most differentiation software instead targets dense derivatives of scalar expression graphs.
This section presents the Jacobian and the Hessian, the elementary methods for computing them,
and the choices that distinguish the software implementations; \S\ref{sec:computing-derivatives}
reviews sparse AD and graph colouring methods.

% \paragraph{The Jacobian.}  (heading removed per advisor; kept for reference)
For a vector-valued map $F : \reals^n \to \reals^m$ of an input $\mvec{x} \in \reals^n$, the
first-order
derivative is the Jacobian $\mmat{J} \in \reals^{m \times n}$ of partial derivatives of
the outputs
with respect to the inputs,
\BEQ\label{eq:jacobian}
  J_{ij} = \frac{\partial F_i}{\partial x_j}, \qquad i = 1, \dots, m, \quad j = 1, \dots, n.
\EEQ
We mainly consider the constraint function, which stacks the potentially many affine
expressions of a canonicalized problem into a single vector function of the variables.
Its Jacobian is the constant constraint matrix~$\mmat{A}$ of \eqref{e:quad-conic-form}, whose
sparsity
pattern is fixed although its values may change from one solve to the next.

% \paragraph{The Hessian.}  (heading removed per advisor; kept for reference)
For a scalar function $f : \reals^n \to \reals$, the second-order derivative is the Hessian
$\mmat{H} \in \reals^{n \times n}$ of second partial derivatives,
\BEQ\label{eq:hessian}
  H_{ij} = \frac{\partial^2 f}{\partial x_i \, \partial x_j}, \qquad i, j = 1, \dots, n.
\EEQ
The Jacobian of the gradient of $f$ is $\mmat{H}^\top$; the Hessian is symmetric whenever
$f$ is twice continuously differentiable, so the two coincide.
It can therefore be obtained by differentiating the gradient with the
same methods used for the Jacobian, although dedicated methods that compute it directly also exist.
The function we consider is the canonicalized objective, whose Hessian is the matrix~$\mmat{P}$ of
\eqref{e:quad-conic-form}.

\subsection{Numerical differentiation}\label{sec:bg-numerical-diff}
Other than computing derivatives analytically, the simplest method is to use numerical
differentiation, which approximates the derivative of a function at a point by evaluating the
function at nearby points using a finite difference formula such as
\BEQ
f'(x) \approx \frac{f(x + h) - f(x)}{h},
\EEQ
where $h$ is a small step size.
Note that the central variant $f'(x) \approx (f(x+h) - f(x-h)) / 2h$ improves accuracy;
both formulas use two function evaluations, but the forward difference can reuse the already
computed value $f(x)$ across directions, while the central variant cannot.
The approach is simple but has two downsides.
First, it requires a linear number of function evaluations with respect to the number of
input variables, which is expensive for high-dimensional functions.
Second, it can easily lead to truncation errors, when $h$ is too large, or
rounding errors, when $h$ is too small, in the computed derivative if the step size is
not carefully chosen \cite{chakravarti1961truncation}.
Despite these downsides, numerical differentiation is still widely used in practice,
especially for verifying the correctness of derivative computations, also known as a
derivative checker \cite{wolfe1982checking}.

\subsection{Symbolic differentiation}\label{sec:bg-symbolic-diff}
Mathematical expressions can be manipulated automatically using simple derivative rules of
calculus, such as the product and sum rule. This symbolic approach to differentiation
is used in computer algebra systems such as \texttt{Mathematica} \cite{mathematica} and
\texttt{Maple}
\cite{maple} as well as the \texttt{SymPy} library in Python \cite{sympy2017}.
Unlike its numerical counterpart, symbolic differentiation tools compute derivatives as
closed-form expressions, which can be simplified and evaluated at any arbitrary point.
These closed-form expressions are particularly useful for deriving analytic solutions of
optimization problems, and can be further used in mathematical proofs and analyses.

However, a naive implementation of symbolic differentiation can quickly form exponentially
large symbolic expressions, which is impractical and inefficient for many problems
\cite{griewank2008evaluating}.
When intermediate expressions are stored as common subexpressions, and
the expression is represented with a directed acyclic graph (DAG) instead of a tree,
symbolic differentiation performs the same set of operations as reverse mode
differentiation \cite{Laue2019OnTE}.

\subsection{Algorithmic differentiation}\label{sec:bg-ad}
Algorithmic differentiation (AD) treats the function as a computational graph of
elementary operations, each with a known local derivative rule.
The chain rule is then applied to combine these local derivatives throughout the graph, giving the
derivative of the whole function.
AD is also commonly referred to as automatic differentiation; we prefer the term
algorithmic to emphasize that AD differentiates the algorithm that computes a function,
rather than a numerical approximation or a symbolic formula \cite{griewank2008evaluating}.
In this broad sense, AD can refer to any method that applies the chain rule over a computational
graph.
Its implementations differ in four basic choices: whether the graph is scalar or
vectorized, whether the chain rule runs forward or in reverse, whether the
derivative is assembled directly or accessed through an oracle of matrix--vector
products, and whether the result is stored sparse or dense.

% \paragraph{Scalar and vectorized graphs.}  (heading removed per advisor; kept for reference)
In most AD tools, every node is a single elementary operation, an addition, a multiplication, or a
univariate function, and every edge carries a scalar partial derivative
\cite{griewank2008evaluating}.
A vectorized graph coarsens this representation: a node is a whole vector or matrix
operation, and its local derivative is a matrix, a block of the Jacobian.
Nearly all tools operate on scalar graphs; the vectorized exceptions include the MX expressions of
\texttt{CasADi} \cite{andersson2019} and JAX \cite{jax2018github}, although the latter still stores
its derivatives densely.
% \paragraph{Modes of differentiation.}  (heading removed per advisor; kept for reference)
The chain rule can be applied in different orders, all giving the same result.
Writing the derivative as a product of local derivatives, forward mode (or tangent
mode) associates the product from the input side, following the order of evaluation, while
reverse mode (or adjoint mode) associates it from the output side, which requires
storing the intermediate values of the evaluation \cite{baydin2017ADsurvey}.
The two modes have asymmetric costs: in forward mode the work scales with the number of inputs, and
in reverse mode with the number of outputs.

% \paragraph{Oracle and direct assembly.}  (heading removed per advisor; kept for reference)
An oracle returns the action of the derivative, the product $\mmat{J}\mvec{v}$ in
forward mode or $\mmat{J}^\top \mvec{w}$ in reverse mode, without ever forming $\mmat{J}$;
a direct method assembles $\mmat{J}$ itself, each node combining the local derivatives
of its arguments.
Either result can be stored dense or sparse.
For a sparse matrix, an oracle requires the sparsity pattern to be detected and
graph colouring to recover the matrix in few products; direct assembly carries sparse
local derivatives through the graph and needs neither.
Direct assembly is practical only on vectorized graphs, whose few coarse nodes make carrying
a matrix per node affordable.
This thesis assembles the sparse Jacobian and Hessian directly on a vectorized graph, without
oracle sweeps or colouring.

\section{Matrix computations}\label{sec:intro-matrix}
The derivatives of \S\ref{sec:bg-derivatives} are matrices, and every matrix is stored in one
of two representations: dense, which stores all entries in a single array, or sparse, which
stores only the nonzero entries alongside their positions.
The representation determines the memory a matrix occupies and the algorithms that operate on
it, and each has its own use cases.
This section reviews the storage formats, the conventions, and some of the history behind both
types of matrices.

\subsection{Dense matrices}\label{sec:bg-blas}
% \paragraph{Dense storage.}  (heading removed per advisor; kept for reference)
A dense matrix is stored as a single contiguous array of its entries, ordered row by row
(row-major) or column by column (column-major), as shown in Figure~\ref{fig:dense-storage}.
The position of an entry is computed directly from its indices, so no index arrays are
needed, and rows or columns are traversed sequentially in memory.
C arrays are row-major while Fortran arrays are column-major, a distinction that matters when
exchanging matrices across languages because the reference dense linear algebra interfaces
follow the Fortran convention.

\label{fig:dense-storage}

% \paragraph{The BLAS.}  (heading removed per advisor; kept for reference)
Dense linear algebra is served by the Basic Linear Algebra Subprograms (BLAS), a standardized
interface of vector and matrix kernels \cite{lawson1979blas, dongarra1990level3}.
The BLAS is a specification rather than an implementation.
Implementations such as \texttt{OpenBLAS}, Intel \texttt{MKL}, and Apple \texttt{Accelerate}
are tuned to each processor family, and every program calling the interface benefits.
In practice, an optimized implementation is available on nearly every machine, whether
shipped with the operating system or bundled by numerical libraries, and LAPACK, the library
behind dense factorizations and linear system solving in most scientific software, is built
on top of these kernels \cite{anderson1999lapack}.

The interface is organized in three levels by the ratio of computation to data.
Level 1 covers vector operations such as dot products, scaled copies, and additions, level 2
covers matrix--vector products, and level 3 covers matrix--matrix products.
The routine names abbreviate the precision and the operation: \texttt{dgemv} is the
double-precision general matrix--vector product, and \texttt{dgemm} is the double-precision
general matrix--matrix product.

% \paragraph{Why dense kernels are fast.}  (heading removed per advisor; kept for reference)
A modern processor multiplies numbers far faster than it loads them from main memory.
Optimized BLAS implementations account for this by organizing the computation to reuse data
already in cache and by processing several entries per instruction with \ac{SIMD} units
\cite{goto2008anatomy}.
Level-3 kernels benefit the most because they perform a cubic number of operations on a
quadratic amount of data, so each entry loaded from memory is reused many times.

\subsection{Sparse matrices}\label{sec:bg-sparse}
In optimization problems, the matrices $\mmat{P}$ and $\mmat{A}$ often contain mostly zero
entries; such
matrices are called sparse, and conic solvers expect their problem data in sparse formats.
Techniques that store and compute with only the nonzero entries date back to the linear
programming computations of the 1950s and the work of Markowitz \cite{markowitz1957elimination}.
The simplest sparse matrix data structure is the coordinate or triplet
format. It consists of two integer index arrays \texttt{rows} and \texttt{cols} and a floating point
value array \texttt{vals} of length equal to the number of nonzero entries in the matrix.
For example, the matrix
\BEQ\label{eq:sparse-matrix}
  \mmat{S} = \begin{bmatrix}
  0 & 1 & 0 & 0\\
  2 & 0 & 3 & 4\\
  0 & 5 & 6 & 0\\
  \end{bmatrix}
\EEQ
can be represented in coordinate format as
\begin{lstlisting}[language=C]
int    rows[] = {0,  1,  1,  1,  2,  2};
int    cols[] = {1,  0,  2,  3,  1,  2};
double vals[] = {1,  2,  3,  4,  5,  6};
\end{lstlisting}
where we use zero-based indexing and array declaration notation from the C programming
language \cite{Kernighan1988}.
The coordinate format is the easiest to understand and form, but it is not effective for most
operations on sparse matrices; the compressed sparse row (CSR) format is commonly
used instead.

% \paragraph{Compressed sparse row format.}  (heading removed per advisor; kept for reference)
The CSR format differs from the coordinate format in that it replaces the \texttt{rows} array with
a row pointer array \texttt{idxptr} of length equal to the number of rows plus one.
The row pointer array indicates the starting index of each row in the \texttt{cols} arrays.
For example, the matrix in \eqref{eq:sparse-matrix}
can be represented in CSR format as
\begin{lstlisting}[language=C]
int  idxptr[] = {0,  1,          4,      6};
int    cols[] = {1,  0,  2,  3,  1,  2};
double vals[] = {1,  2,  3,  4,  5,  6};
\end{lstlisting}
where we deliberately format \texttt{idxptr} to align with the start of each
row in the \texttt{cols} arrays.
The benefits of the CSR format are more than a reduced size of the \texttt{idxptr} array
compared to the \texttt{rows} array.
In the CSR format, accessing a row takes constant time and is very cache-friendly
because the nonzero entries are stored contiguously in memory.
For this reason, the CSR format is the default for iterative methods
to solve sparse linear systems \cite{saad2003iterative}.

% \paragraph{Compressed sparse column format.}  (heading removed per advisor; kept for reference)
The compressed sparse column (CSC) format applies the same compression to the
columns instead.
The pointer array \texttt{idxptr} now points into a \texttt{rows} array, and the nonzero
entries are stored column by column.
The CSC arrays of a matrix read exactly as the CSR arrays of its transpose, so transposition
is a conversion between the two formats, computable without sorting in one counting pass over
the nonzeros \cite{gustavson1978two}.
Accessing a column of a CSR matrix instead requires a scan of every row, so algorithms
that traverse columns prefer CSC; direct methods for sparse linear systems are the
standard example \cite{davis2006direct}.

% \paragraph{Other sparse formats.}  (heading removed per advisor; kept for reference)
% Paragraph moved up from the end of the section: LIL/DOK/BSR belong with the formats.
The coordinate, CSR and CSC formats are the most widely used sparse matrix formats,
but many others exist for different specialized use cases.
The scientific Python sparse library \texttt{scipy.sparse} \cite{2020SciPy-NMeth}
allows users to form other types of sparse matrices such as the list of lists (LIL) matrix,
the dictionary of keys (DOK) matrix, and the block-sparse row (BSR) matrix.

% \paragraph{Matrix-matrix products.}  (heading removed per advisor; kept for reference)
The product of two sparse matrices is formed row by row with Gustavson's algorithm
\cite{gustavson1978two}: because the sparsity pattern of the result is not known in advance,
each row is built as a combination of the rows of the second operand selected by the nonzeros
of the first, gathered in a dense accumulator before compaction into sparse storage
\cite{bank1993smmp}. It is the standard sparse matrix product, implemented in popular
packages such as \texttt{Eigen} \cite{guennebaud2010eigen} and \texttt{scipy.sparse}.

In contrast to the BLAS kernels of \S\ref{sec:bg-blas}, sparse products access memory
irregularly: the loops traverse the index arrays, so every nonzero costs an index load and an
indirect access, and contiguous reads, \ac{SIMD}, and cache tiling do not apply.
Sparse formats are also a poor fit for dense data: a dense block stored in coordinate format
triples its storage, one index pair per entry, and multiplying it through the sparse loop is
far slower than the equivalent BLAS call.
