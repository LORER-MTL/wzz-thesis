\Chapter{INTRODUCTION}\label{sec:Introduction}

Domain specific modeling languages for convex optimization such as CVXPY \cite{diamond2016cvxpy} and
YALMIP \cite{lofberg2004yalmip} allow users to formulate optimization problems in a natural
mathematical syntax. A convex optimization problem parametrized by $\theta \in \reals^p$ can be
written as
\BEQ \label{e:parametric-family}
\begin{array}{ll}
\mbox{minimize}   & f_0(x; \theta) \\
\mbox{subject to} & f_i(x; \theta) \le 0, \quad i = 1,\ldots,m_1 \\
                  & g_j(x; \theta) = 0, \quad j = 1,\ldots,m_2
\end{array}
\EEQ
where $x \in \reals^n$ is the optimization variable, the objective $f_0$ and inequality constraints
$f_1,\ldots,f_{m_1}$ are convex and the equality constraints $g_1,\ldots,g_{m_2}$ are affine
\cite{boyd2004convex}.
The parameter $\theta$ specifies data that can change but is fixed and given
when solving an instance of the problem. We call the parametrized problem \eqref{e:parametric-family}
a problem \emph{family}; for a fixed value of $\theta$, we call it a problem \emph{instance}.

Through a process called \emph{canonicalization}, these
high-level problem descriptions are converted to a \emph{standard conic form} used by many
general-purpose convex solvers
\BEQ \label{e:standard-form}
\begin{array}{ll}
\mbox{minimize} & \frac{1}{2} x^T P(\theta) x + c(\theta)^T x\\
\mbox{subject to} & b(\theta)-A(\theta)x \in K
\end{array}
\EEQ
where the \emph{problem data} are the symmetric positive semidefinite matrix $P(\theta) \in \symm^n_+$,
the matrix $A(\theta) \in \reals^{m \times n}$, the vectors $b(\theta) \in \reals^m$ and
$c(\theta) \in \reals^n$ and the non-empty closed convex cone $K \subseteq \reals^m$.
Almost all of optimization practice can be divided into two groups, \emph{modeling} and
\emph{solving}. The modeler's role is to formulate problems based on real-world business
or engineering applications.
The solver's role is to find an optimal solution given the data of a problem instance.
Modeling languages serve as the communication bridge between these two groups.
When improvements in solvers are made, modeling languages must adapt to allow users
to benefit from them. Conversely, it is through natural formulations that modelers can
express their requirements and help motivate solver improvements.

While the time taken to solve an optimization problem is often dominated by the solver,
the time taken to \emph{canonicalize} (or \emph{compile}) a problem can also be significant,
especially for large problems, or when many instances of a family are solved.
In the case of CVXPY, this compilation cost lies largely in \emph{matrix stuffing},
the final step of canonicalization where symbolic expression trees are converted to
the explicit numerical problem data $P$, $A$, $b$ and $c$.

\paragraph{Expression trees.}
Modeling languages for convex optimization are built on top of a library of functions which can be
used to describe problems. These functions are known as \emph{atoms} in CVXPY since they are the
fundamental building blocks of the modeling language \cite{grant2004disciplined}.
An expression is defined recursively as an atom evaluated at \emph{subexpressions}, each of which is
itself another expression. Such an expression is naturally stored as an \emph{expression tree},
with atoms at its internal nodes and variables, parameters, and constants at its leaves.
After canonicalization the constraint expressions are affine and the objective is quadratic.

\paragraph{Matrix stuffing in CVXPY.}
CVXPY currently canonicalizes a parametrized problem in one of two ways: re-canonicalizing it from
scratch for each new value of the parameters, or forming a \emph{parameter map}, an affine map from the
parameters to the problem data computed once and re-applied on each solve \cite{agrawal2019dpp}. We
cover CVXPY's matrix stuffing in detail in \S\ref{sec:matrix-stuffing}. For fast canonicalization,
\texttt{cvxpygen}, a code-generation extension to CVXPY, can generate a
custom C solver for a given problem family, suitable for real-time and embedded optimization
\cite{schaller2022cvxpygen}.

\paragraph{Matrix stuffing as a derivative.}
After canonicalization, $A$ is the Jacobian of the constraints and $P$ the Hessian of the objective,
so matrix stuffing amounts to computing a sparse Jacobian and Hessian. Classical methods compute the
matrix with several passes of automatic differentiation, using graph coloring to group columns that
can be recovered in a single pass \cite{curtis1974estimation, gebremedhin2005color}. Recent vectorised
formulations of AD have appeared in specific domains such as statistics \cite{kwok2025vectorised} and
optimal control \cite{zou2025vectorized}, though not yet for matrix stuffing. We review these methods
of computing sparse derivatives in \S\ref{sec:computing-derivatives}.

\paragraph{Other modeling languages.}
Other modeling languages produce this data in different ways, a task we call
\emph{coefficient extraction}. JuMP and AMPL extract the coefficient data directly from the algebraic model,
with AMPL also recognizing second-order cone structure and rewriting it into the solver's conic form
\cite{dunning2017jump, lubin2023jump10recent, fourer1990ampl}. Through its quadratic-programming interface,
CasADi instead forms the Jacobian and Hessian by automatic differentiation,
recovering their sparsity pattern by graph coloring \cite{andersson2019}. CasADi compiles this into a
reusable function, fixing the sparsity pattern once and recomputing only the nonzero values on each
solve. We review these methods in much greater detail in \S\ref{sec:coefficient-extraction}.

\paragraph{Contributions.}
% could add a bridge paragraph which sums everything up and introduces what we will talk about.
We make the following contributions:
\begin{enumerate}
  \item We build \texttt{SparseDiffengine}, a C library with Python bindings that computes sparse
  Jacobians and Hessians of vectorized expressions, without graph coloring.
  \item We implement a canonicalization backend for CVXPY that builds on \texttt{SparseDiffengine}.
  \item We benchmark this backend against existing canonicalization approaches, comparing compilation
  time and memory use across a range of problem families.
\end{enumerate}
