\Chapter{A LIGHTWEIGHT CANONICALIZATION ENGINE}\label{sec:Theme1}

Mathematically, \texttt{SparseDiffEngine} computes the same derivatives as
\texttt{CVXPY}'s canonicalization backend: both apply the chain rule of matrix calculus
to trees of vectorized expressions, producing the Jacobian and Hessian of
% TODO(read-through): drop the framing clause "which we will present in this chapter".
\S\ref{sec:bg-derivatives}. The differences are in the implementation details,
which we will present in this chapter.
% TODO(read-through): "symbolic/numeric phases" used before being defined (Atom classes
% paragraph); see the pass-naming TODO there.
Firstly, the use of a custom sparse matrix data structure allows a natural split
between the symbolic and numeric phases of the derivative computation. This separation
is particularly useful for compiling problems involving parameters, where
the structure is fixed but the numerical values can change.
Secondly, in addition to being sparse, the data of most optimization
problems also have a lot of structure, such as dense blocks or diagonality.
In \texttt{SparseDiffEngine} we introduce two new matrix classes: \texttt{permuted-dense}
and \texttt{stacked-permuted-dense} for this purpose; they enable us to make
use of dense storage and BLAS subroutines when possible.

Finally, some important design decisions differ from \texttt{CVXPY}'s backends for
simplicity rather than speed. Every node carries a single Jacobian whose columns span
all of the variables of the problem, rather than a dictionary of local Jacobians keyed by
variables. As a consequence, the chain rule is a single matrix product, and the
constraint matrix is built by stacking the Jacobians of the constraints.
In addition, quadratic functions pass through
dedicated Hessian oracles instead of a separate substitution and matrix stuffing pass.

The rest of the chapter is structured as follows: we begin with a brief overview of
the engine, describing how expressions are represented and how the code is organized.
We then present the matrix representations used for the derivative computations,
where we will focus much of our attention on the \texttt{permuted-dense}
matrix, which appears most often. Next we describe the algorithms, or \emph{kernels},
which allow us to operate on and combine these matrix representations.

\section{Overview of the engine}\label{sec:theme1-overview}

\texttt{SparseDiffEngine} is a small C library which is around seventeen thousand lines
of code (and a similar number of lines for the test suite).
The expression node is defined in \texttt{expr.h}; atoms that carry extra data, such as
the exponent of a power, define a larger structure in \texttt{subexpr.h}.
Each atom is implemented in its own file in the \texttt{atoms/}

mathematical properties: \texttt{affine}, elementwise and bivariate functions with full or
restricted domains, and a small group of \texttt{other} atoms such as the quadratic form.
The matrix data structures and the computational kernels that operate on them are in
\texttt{utils/}, and \texttt{problem.c} collects the objective and constraints of a
problem and implements the oracles that are passed to a solver.

Each atom implements three operations: a \emph{forward} pass, which evaluates the atom at
a point; a \emph{symbolic} pass, which computes the sparsity patterns of its derivatives
and allocates memory for them; and a \emph{numeric} pass, which computes the numerical
values inside the fixed patterns. The constructor of the atom
stores pointers to these three functions in the expression node.

\paragraph{The expression node.}
An expression node stores its dimensions, pointers to at most two children, a buffer for
its value, and its derivative matrices, whose \texttt{n\_vars} columns span all of the
variables of the problem. A simplified version of the definition in
\texttt{expr.h} is shown below.
% TODO(read-through): listing comments say "symbolic/numeric pass" next to the init/eval
% function names; align with whichever pass naming wins.
\begin{lstlisting}[language=C]
typedef struct expr
{
    int d1, d2, size, n_vars, refcount, var_id;
    struct expr *left;
    struct expr *right;

    double *value;     /* forward value                */
    matrix *jacobian;  /* Jacobian w.r.t. the variables */

    forward_fn        forward;
    jacobian_init_fn  jacobian_init_impl;  /* symbolic pass */
    eval_jacobian_fn  eval_jacobian;       /* numeric pass  */
    /* ... Hessian oracle, workspace and caching fields ... */
} expr;
\end{lstlisting}
Trees are built bottom up, with one constructor function per atom; the Python bindings
expose the same constructors, so a \texttt{CVXPY} expression is converted by a single
traversal that calls the constructor of the corresponding atom at each node
(\S\ref{sec:theme1-api}). Expressions that appear multiple times can be shared, in
which case the tree becomes a directed acyclic graph. Nodes are therefore reference
counted, and the symbolic pass returns early if a node was already initialized
through another parent.

\paragraph{Leaf nodes.}
There are two leaf nodes, variables and parameters. A \emph{variable} occupies a
contiguous slice of the global variable vector, starting at its offset \texttt{var\_id};
its Jacobian is a selection matrix with one unit entry per row, written once during the
symbolic pass. Unlike \texttt{CVXPY}, there is no separate constant node: constants and
parameters share a single leaf type, distinguished by an identifier that is $-1$ for
constants and, for updatable parameters, the offset of the parameter in the global
parameter vector. The Jacobian of this leaf is empty, since parameters are fixed during a
solve, and because parameters are leaves of the tree, the derivative structure remains
valid when their values change (\S\ref{sec:problem-statement}).

\section{Matrix representations}\label{sec:theme1-matrix-representations}
The \texttt{jacobian} field of the expression node has a polymorphic type called
\texttt{matrix}, with one representation for each kind of structure that we want to
exploit. Each atom chooses the representation of its Jacobian when it allocates it
during the symbolic pass; multiplication by dense data allocates a permuted dense
matrix, for example. After that, every operation on the matrix,
such as transposition, row indexing, or a chain-rule product, simply dispatches to a
kernel specific to the representations involved. The default representation is a generic
sparse matrix stored in the CSR format of \S\ref{sec:bg-sparse}.

\subsection{The permuted dense matrix}\label{sec:theme1-permuted-dense}

The Jacobians that appear during canonicalization are usually not sparse in the sense of
having scattered, isolated nonzeros. Multiplication by problem data places the data
itself, or a product involving it, as a dense block at a subset of the rows and columns
of the Jacobian. Consider the expression $Bx$ with dense
data $B \in \reals^{50 \times 50}$, in a problem with ten thousand variables. Its Jacobian
with respect to the full variable vector is a matrix with ten thousand columns that
contains $B$ in the fifty columns of $x$ and is zero everywhere else. If this Jacobian is
stored in a generic sparse format, every subsequent product goes through sparse kernels,
and the hardware efficiency of \S\ref{sec:bg-blas} is lost.

\paragraph{Definition.}
We therefore store such matrices in \emph{factored form}: we keep the dense block and the
index vectors that place it, and never assemble the global matrix. A \emph{permuted dense} matrix
is a triple $(X, r, c)$, where $X \in \reals^{m_0 \times n_0}$ is a dense block and $r$ and
$c$ are strictly increasing index vectors, representing
\BEQ\label{eq:permuted-dense}
  A = S_r^T X S_c \in \reals^{m \times n},
  \qquad A_{r_i,\, c_j} = X_{ij},
\EEQ
where $S_r \in \{0,1\}^{m_0 \times m}$ and $S_c \in \{0,1\}^{n_0 \times n}$ are the selector
matrices whose rows are the rows of the identity indexed by $r$ and $c$: multiplying a
vector by $S_r$ selects the entries indexed by $r$, and multiplying by $S_r^T$ scatters
them back into a vector of length $m$, with zeros elsewhere. All other entries of
$A$ are structurally zero and never stored. Figure~\ref{fig:permuted-dense} shows an
example with a $3 \times 3$ block inside a $6 \times 7$ matrix.

\paragraph{Storage.}
The block $X$ is stored contiguously in row-major order and the index vectors as two
integer arrays, so storage does not depend on the global dimensions. Two inverse maps,
which send a global index to its block index or to $-1$, make membership checks constant
time. Structure is computed with integer arithmetic on the index vectors; floating point
operations run only on the contiguous block.

\paragraph{Structural operations.}
Every operation we need maps a permuted dense matrix to another permuted dense matrix.
Transposition swaps the two index vectors and transposes the block. The structural atoms,
such as indexing, broadcasting, and the row partitions of \texttt{sum}, work the same
way: since row $r_i$ of $A$ is row $i$ of $X$ and every other row is zero, an operation
on the rows of $A$ reduces to the same operation on the rows of $X$, guided by the
inverse row map.

\paragraph{The chain-rule product.}
The product of two permuted dense matrices is also permuted dense: for
permuted dense $A$ and $B$, the chain-rule product $B^T A$ factors as
\BEQ\label{eq:pd-product}
B^T A
= S_{c_B}^T X_B^T \underbrace{\left(S_{r_B} S_{r_A}^T\right)}_{\text{row-set intersection}}
  X_A S_{c_A},
\EEQ
The middle factor is a zero-one matrix whose entry $(k, l)$ is one exactly when
$r_{B,k} = r_{A,l}$, so the sparsity analysis of the product amounts to intersecting two
sorted integer arrays. The result has row vector $c_B$ and column vector $c_A$, which are
known before any numerical values exist. For the values there are three cases. If the two
row sets are equal, the product is computed on the two blocks with a single call to
\texttt{dgemm}, the double precision general matrix--matrix product of level-3 BLAS
(\S\ref{sec:bg-blas}). If they overlap partially, the matching rows are first gathered
into a workspace (allocated during the symbolic pass),
followed by the same \texttt{dgemm}. If they are
disjoint, the product is zero, and nothing is computed in the numeric pass. The weighted
product $B^T D A$, needed for the Hessian of the objective, is handled the same way.

\paragraph{Performance.}
% TODO(read-through): restates the CSR-loses-BLAS motivation from the chapter intro;
% consider merging the two statements.
The main benefit of the factored form \eqref{eq:permuted-dense} is that the floating
point work is done by dense kernels. If the same matrix is stored in the CSR format, its
products go through sparse kernels, whose indexed accesses and irregular inner loops
reach only a fraction of the throughput of BLAS \cite{goto2008anatomy} at the same
operation count. In the factored
form, the numeric pass of each kernel consists of a few BLAS calls on contiguous buffers.
The product $A^T D A$, for example, is computed with one copy, $m_0$ scalings, and one
\texttt{dgemm}, and the cost does not depend on the global dimensions.

\paragraph{Limitations.}
A permuted dense matrix cannot represent nonzeros outside its block: by
\eqref{eq:permuted-dense}, every such entry is structurally zero. A Jacobian that mixes a
dense block with scattered entries simply uses the default CSR representation, and an
operation whose result does not keep the block structure, such as adding operands with
different patterns, is performed on CSR views of its operands. The remaining risk is
dense data that contains many zeros, which would be stored and multiplied densely,
spending floating point work on zeros; since \texttt{CVXPY} supplies sparse data in
sparse formats, this does not arise in practice.

\subsection{The stacked permuted dense matrix}\label{sec:theme1-stacked-pd}

When an expression with matrix shape $n \times p$ is multiplied by data
$A \in \reals^{m \times n}$, the effect on the vectorized expression is that of the block
diagonal operator $I_p \otimes A$; this is the \texttt{left\_matmul} atom. The operator
is never formed: the engine keeps one copy of $A$ and applies it block by block. In
memory, the $p$ segments of length $n$ of a vector $x$ form a $p \times n$ row-major
matrix $\tilde{X}$, and by a standard vectorization identity \cite{magnus2019matrix},
\BEQ\label{eq:kron-reshape}
  y = (I_p \otimes A)\, x
  \quad\Longleftrightarrow\quad
  \tilde{Y} = \tilde{X} A^T,
\EEQ
so applying the operator to a vector is a single \texttt{dgemm} on the stored $A$.
% TODO(read-through): "roughly one hundred times faster" is unsupported here; add the
% measurement context or move the number to Theme2.
Avoiding the explicit operator made the initialization of the atom's sparsity pattern
roughly one hundred times faster.

% TODO(read-through): "The identity" is a bare referent; name it, e.g. "Identity
% \eqref{eq:kron-reshape} applies the operator...".
The identity applies the operator; the atom must also store its Jacobian. The parent node
receives $(I_p \otimes A)\, J$, where $J$ is the Jacobian of the child, and transposes,
indexes, and multiplies it like any other Jacobian. This matrix is made of $p$ dense
blocks at disjoint rows, one per column of the operand, and each block generally sits at
its own global columns, so no single triple $(X, r, c)$ describes it. Merging the blocks
into one larger triple would store the full block diagonal, $p$ copies of $A$ separated
by blocks of zeros, and falling back to generic sparse would lose the dense kernels. The
engine instead keeps the blocks as they are, in a third representation.

\paragraph{Definition.}
A \emph{stacked permuted dense} matrix is a vertical union of permuted dense blocks
whose row vectors are pairwise disjoint; the column vectors may overlap. The blocks share
one value buffer. Every kernel treats the blocks one at a time: structural atoms rewrite
the index vectors of each block, and products distribute over the blocks, with one
\texttt{dgemm} for each pair of blocks with intersecting row sets and nothing at all for
the pairs with disjoint row sets, as in \eqref{eq:pd-product}. The assembled matrix is
never allocated or traversed, and each stacked kernel is a short loop over the
corresponding permuted dense kernel. Figure~\ref{fig:stacked-pd} shows the Jacobian of
$AX$ for a variable $X$ with two columns: one block per column of $X$, each a copy of $A$
at its own rows and columns.

\paragraph{The three representations.}
Generic sparse, permuted dense, and stacked permuted dense are the only three matrix
representations in the engine. Generic sparse is the default: it is produced by the
variable leaves and by every atom that does not hold dense data.
Permuted dense and stacked permuted dense are created by the two atoms that
hold dense data, \texttt{left\_matmul} and the quadratic form, and propagate from there
through the structural atoms and the chain rule.

\section{Computational kernels}\label{sec:theme1-kernels}

A kernel is an operation on one or two of the matrix representations of
\S\ref{sec:theme1-matrix-representations}: a transposition, a row selection, a
chain-rule product. Every kernel is split into an alloc function and a fill function,
called by the symbolic and numeric passes respectively: alloc computes the structure of the
result and reserves its memory, and fill writes numerical values into the fixed
structure. This section describes the kernels from the point of view of the atoms that
call them. \S\ref{sec:theme1-kernel-dispatch} describes
how a product selects a kernel when each operand can have any of the three
representations, and \S\ref{sec:theme1-reusing-work} collects the work that is done once
during the symbolic pass instead of at every evaluation.

\subsection{Kernel dispatch}\label{sec:theme1-kernel-dispatch}

Unary operations are dispatched through the function pointer table of
\S\ref{sec:theme1-matrix-representations}, based on the representation of their single
operand. The chain-rule products $B^T A$ and $B^T D A$ depend on the representations of
both operands, which a single table cannot express. They are instead resolved with double
dispatch: a dispatch function switches on the type tags of $B$ and then of $A$, and calls
one of nine kernels.

\subsection{Reusing work across passes}\label{sec:theme1-reusing-work}

\paragraph{Affine atoms.}

The Jacobian of an affine atom does not depend on $x$: for the structural atoms, such as
indexing, transposition, reshaping, stacking, and summation, it is determined by shapes
and index sets alone, and the remaining affine atoms, such as \texttt{left\_matmul},
\texttt{scalar\_mult}, \texttt{convolve}, and \texttt{kron}, place problem data in the
Jacobian, whose values only change when a parameter update sets their refresh flag. The
quadratic form is the only atom outside the affine class that appears in canonicalized
problems; it contributes the objective matrix $P$ through the Hessian oracle
(\S\ref{sec:theme1-api}).

\paragraph{Work done once.}
The numeric pass never allocates memory; every buffer, including the scratch space of the
kernels, is allocated during the symbolic pass. Beyond allocation, several other kinds of
work are done only once. Sparsity patterns are computed symbolically: \texttt{add} merges the
patterns of its children with a sorted merge, the sparse products run the symbolic phase
of Gustavson's algorithm \cite{bank1993smmp}, and the factored products of
\S\ref{sec:theme1-matrix-representations} determine their output index vectors before any
values exist. Index maps are also precomputed: transposition stores its row permutation,
\texttt{kron} its per-row copy maps, and \texttt{sum} the map from child nonzeros to
output entries, so the numeric pass performs no index arithmetic. When the index vectors
of two operands do not intersect, the product is recorded as empty during the symbolic
pass, and its numeric pass does nothing. Finally, values that cannot change are written
once; the Jacobian of a variable, for example, is filled during the symbolic pass and
never touched again.

Figure~\ref{fig:sum-idx-map} illustrates this for the \texttt{sum} atom. During the

\texttt{idx\_map}, an array
that maps each nonzero of the child Jacobian to the output entry it is added to. The axis
convention and all other index decisions are handled at this point. The numeric pass is a
single loop, the same for every axis and every representation. Indexing, transposition,
and \texttt{kron} work the same way, with a copy instead of an addition.

\paragraph{The problem level.}
Assembly works in the same way. The solver receives one global CSR matrix, formed by
concatenating the constraint Jacobians, whose layout is fixed during the symbolic pass;
an evaluation only copies the values of each constraint root into this matrix at a fixed
offset. Affine constraints are skipped entirely after the first evaluation, since their
values cannot change until the parameters do.

\paragraph{Parameter updates.}
An update only involves the numeric pass: \texttt{update\_params} writes
the new values into the parameter leaves and sets a refresh flag on each affected
subtree, and the next
evaluation recomputes the values through the fixed maps and kernels. In comparison,
without parametric compilation \cite{agrawal2019dpp}, \texttt{CVXPY} traverses the
expression graph again, recomputes every sparsity pattern, and reallocates every buffer
each time a parameter changes. The difference is measured in Chapter~\ref{sec:Theme2}.

\section{The API and the CVXPY interface}\label{sec:theme1-api}

The engine is distributed as a C library with a thin Python binding called
\texttt{sparsediffpy}, which exposes the node constructors. It is used in two places
inside \texttt{CVXPY}. The nonlinear programming interface wraps the bindings in a class
called \texttt{C\_problem}, which is built from the expression trees of a problem. The
canonicalization backend, which is the one measured in this thesis, is selected by
passing \texttt{ignore\_dpp=True}, and replaces the stuffed matrices of
\S\ref{sec:matrix-stuffing} with a cone program object that wraps the same
\texttt{C\_problem}. The code below is lightly condensed from the actual interface.

The lifecycle of a \texttt{C\_problem} mirrors the symbolic and numeric passes:
\begin{lstlisting}[language=Python]
prob = C_problem(problem)        # convert the tree, register parameters
prob.init_jacobian_coo()         # symbolic pass: patterns, maps, buffers
rows, cols = prob.get_jacobian_sparsity_coo()  # structure, fetched once

prob.objective_forward(x)        # numeric pass, repeated per iterate
prob.constraint_forward(x)
grad = prob.gradient()
vals = prob.eval_jacobian_vals() # values aligned with (rows, cols)
\end{lstlisting}
The sparsity pattern is fetched once and does not change afterwards; the later calls
return value arrays that are aligned with it.

The canonicalization backend extracts the problem data, an objective
$\tfrac{1}{2}x^T P x + q^T x + d$ and constraints $Ax + b$ that must lie in a cone, by
evaluating the oracles at $x = 0$. The forward passes give $d$ and $b$, the gradient
gives $q$, and the Jacobian and Hessian values fill the fixed patterns of $A$ and $P$.
Parameter updates go through a single method:
\begin{lstlisting}[language=Python]
def apply_parameters(self, id_to_value):
    theta = flatten_and_concatenate(id_to_value)
    if theta == self.cached_theta:       # same values: reuse everything
        return self.P, self.q, self.d, self.A, self.b
    self.c_problem.update_params(theta)  # numeric pass only
    self.P, self.q, self.d, self.A, self.b = self.extract()  # at x = 0
    self.cached_theta = theta
    return self.P, self.q, self.d, self.A, self.b
\end{lstlisting}
Repeated solves with unchanged parameter values return the cached matrices; an actual
update costs one run of the numeric pass.

The caching follows the same pattern as in \S\ref{sec:theme1-reusing-work}. The
\texttt{C\_problem} and its sparsity structures live as long as the problem family, the
extracted matrices are kept until the parameter values change, and only numerical values
are recomputed. After construction, nothing in the Python layer traverses an expression
tree.
Chapter~\ref{sec:Theme2} compares the engine with \texttt{CVXPY}'s canonicalization
backends, implementations of the matrix-stuffing approach reviewed in
Chapter~\ref{sec:RevLitt}.
