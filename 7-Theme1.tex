This chapter presents the \texttt{SparseDiffEngine} and how it forms the constraint matrix $A$ from
the canonicalized expression trees of \S\ref{sec:canonicalization}. We reframe the matrix stuffing
of \S\ref{sec:matrix-stuffing} as the computation of a single sparse Jacobian, assembled by one
recursive rule applied atom by atom.

After canonicalization the constraints are affine, so $A$ is their Jacobian and is constant in $x$.
Matrix stuffing walks the expression tree accumulating each atom's linear coefficient into $A$; this
accumulation is exactly a bottom-up computation of that constant Jacobian.

The rule behind it is that every affine atom is a linear operator $L$ with a constant offset. If a
subexpression $z$ has Jacobian $J_z$, then the atom's output $Lz + c$ has Jacobian $L J_z$, so the
Jacobian of a node is its atom's operator applied to the Jacobians of its children,
\BEQ \label{eq:jacobian-rule}
J_{\mathrm{node}} = L_{\mathrm{atom}} \begin{bmatrix} J_{\mathrm{left}} & J_{\mathrm{right}} \end{bmatrix}.
\EEQ
Every atom in this chapter is one choice of $L$: addition sums its children, negation flips their
sign, transpose permutes the rows, and the matmul $Fx$ left-multiplies by $F$. A single pass from
the leaves to the root composes these operators into $A$.

Because the constraints are affine, the Jacobian is constant and its sparsity pattern is fixed by
the composition of the atoms' operators. We read that pattern off directly, in one structural pass,
rather than discovering it by probing the Jacobian one column group at a time as the coloring-based
methods of \S\ref{sec:computing-derivatives} do.

This walk is the one CVXPY's \texttt{cvxcore} already performs, applying each atom's linear operator
to assemble the problem data. The engine keeps the walk but changes it in two ways, each developed
below. It splits the single walk into a structural pass that fixes the sparsity pattern of $L J_z$
once per problem family and a value pass that refills only the numbers on each solve
(\S\ref{sec:reusing-work}). It also stores each Jacobian block in the representation that matches
its structural class, applying the dense and Kronecker-structured operators without ever forming
them (\S\ref{sec:atom-implementations}).

\S\ref{sec:data-structures} describes the data structures and \S\ref{sec:atom-implementations} the
atom implementations. \S\ref{sec:reusing-work} develops the caching the two passes enable, and
\S\ref{sec:revisit-limitations} returns to the limitations of \S\ref{sec:matrix-stuffing}. We
assume the sparse-matrix background of \S\ref{sec:sparse-matrices}.

\section{Fundamental data structures}
\label{sec:data-structures}

% first describe in english what an expression is
% and what we need. Then show the struct.
The main data structure in the engine is the expression struct.
\begin{lstlisting}[language=C]
typedef struct expr {
    int    d1, d2, size;   /* shape (d1 x d2) and size = d1*d2 */
    int    n_vars;         /* total number of variables         */
    int    var_id;         /* offset into u, or NOT_A_VARIABLE  */

    struct expr *left;     /* left child  (NULL for leaves)     */
    struct expr *right;    /* right child (NULL for leaves)     */

    double     *value;     /* forward-pass output, size entries */
    matrix     *jacobian;  /* size x n_vars Jacobian            */

    forward_fn       forward;
    jacobian_init_fn jacobian_init_impl;
    eval_jacobian_fn eval_jacobian;
} expr;
\end{lstlisting}

Each node carries a \texttt{value}, the output of its forward pass, and a Jacobian. The Jacobian is
held through a polymorphic \texttt{matrix} type: a base struct of shape and a small table of
operator function pointers, embedded as the first member of each concrete representation. The
representation an atom uses is fixed once during initialization and is the subject of
\S\ref{sec:atom-implementations}. Each node also implements three functions: \texttt{forward},
\texttt{jacobian\_init}, and \texttt{eval\_jacobian}.

\paragraph{Leaf nodes.}
The leaves are variables and parameters.

\section{Atom implementations}
\label{sec:atom-implementations}
An atom takes one or two expression operands and produces an expression. Each atom implements the
three functions: \texttt{forward} computes the value, \texttt{jacobian\_init} fixes the Jacobian's
sparsity pattern once, and \texttt{eval\_jacobian} fills its values on each solve. The affine atoms
number in the dozens, but their Jacobian blocks fall into the few representations of
\ref{tab:jacobian-classes}. We organize the atoms by representation and give one worked atom for
each, describing the rest in prose. Two further operators, the diagonal of an elementwise scaling
and the Kronecker product of a matrix-valued product, are applied to the child Jacobian without
ever being stored. Throughout, \texttt{x} and \texttt{y} denote variables, \texttt{a} a parameter,
and \texttt{F} a constant matrix, all of compatible shape.

\subsection{Generic sparse blocks}
The default representation is a generic sparse matrix in CSR form (\S\ref{sec:sparse-matrices}). A
variable leaf of size $n$ has the identity as its Jacobian, stored as an $n \times n_{\mathrm{vars}}$
selection matrix with one nonzero per row. The atoms whose blocks relabel, select, or add the
child's rows keep this representation: the output has a nonzero wherever an input does, so its
pattern is a rearrangement of the children's.

Addition is the template every such atom follows. The forward pass evaluates the children and sums
their values. \texttt{jacobian\_init} allocates the output Jacobian, whose number of nonzeros is at
most the sum of the children's, and fixes its pattern. \texttt{eval\_jacobian} sums the children's
Jacobians into it.

Negation negates an expression elementwise. The forward pass flips the sign of each value; the
Jacobian has the child's pattern, so \texttt{jacobian\_init} copies it and \texttt{eval\_jacobian}
negates its values. Transpose (\texttt{cp.transpose(x)}) only relabels the output entries, so its
Jacobian is a fixed row permutation of the child's: \texttt{jacobian\_init} records the permutation
and \texttt{eval\_jacobian} copies the child's values into the permuted rows. The vertical stack
\texttt{cp.vstack([x, y])} needs no new code, using the identity
\texttt{vstack([A, B]) = transpose(hstack([transpose(A), transpose(B)]))}. Reshape, indexing,
summation, and broadcasting are of the same kind: each fixes an output pattern that selects or
accumulates the child's entries and refills it by copying or adding values.

\subsection{Dense blocks}
\label{sec:dense-blocks}
When a constant dense matrix $F \in \reals^{m \times n}$ multiplies a vector expression, $F x$, the
Jacobian is $F$ itself, placed at the columns of $x$'s variables. A dense $F$ stored as a generic
sparse matrix carries the full CSR index overhead for a block with no zeros to exploit. The engine
stores it instead as a \emph{permuted dense} block: a single $m \times n$ dense array together with
the global rows and columns it occupies,
\BEQ \label{eq:permuted-dense}
M[\,\mathrm{row}[i],\ \mathrm{col}[j]\,] = F[i, j],
\EEQ
with every other entry zero. \texttt{jacobian\_init} places the block once and \texttt{eval\_jacobian}
refills its $mn$ values, both by applying $F$ to the child's Jacobian following
\eqref{eq:jacobian-rule}.

A parameter that scales an expression elementwise, $a \odot x$, is the diagonal case: its Jacobian
is $\diag(a)$. The engine never forms $\diag(a)$; it applies the operator to the child Jacobian $J$
as $\diag(a)\,J$, scaling row $i$ of $J$ by $a_i$. Only the vector $a$ is stored.

\subsection{Matrix-valued products and the Kronecker block}
\label{sec:kron-blocks}
The same matmul atom handles a matrix-valued operand $F X$, where $X$ has $p$ columns. Vectorizing
column by column,
\BEQ \label{eq:kron-matmul}
\operatorname{vec}(F X) = (I_p \otimes F)\, \operatorname{vec}(X),
\EEQ
so the operator is the Kronecker product $I_p \otimes F$, a block-diagonal matrix with $p$ copies of
$F$ on its diagonal, and the Jacobian is $(I_p \otimes F)\, J_X$ by \eqref{eq:jacobian-rule}.

Forming $I_p \otimes F$ is wasteful: it is $p$ times the size of $F$ and completely structured. The
engine never forms it. It loops over the $p$ diagonal blocks, applies the single stored $F$ to the
corresponding block of $J_X$, and collects the $p$ results as a vertical stack of permuted dense
blocks. The engine's own note records the effect: it forms the Kronecker product ``only
conceptually,'' which ``led to a 100x speedup in the initialization of the Jacobian sparsity
pattern.'' The stacked representation carries this structure through the rest of the walk, so an
atom above a matrix-valued product also operates block by block rather than on a materialized
Kronecker product.
