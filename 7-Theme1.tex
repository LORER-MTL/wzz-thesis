\Chapter{A LIGHTWEIGHT CANONICALIZATION ENGINE}\label{sec:Theme1}

This chapter presents \texttt{SparseDiffEngine}, our C library for assembling the
constraint and objective matrices of a canonicalized problem. The engine computes the same
derivatives as \texttt{CVXPY}'s canonicalization backends. Both apply the
chain rule of matrix calculus to trees of vectorized expressions. Our contributions lie in the
implementation. Our main contribution exploits the fact that the data of most optimization
problems is not only sparse but also structured, with dense blocks and diagonal patterns.
We introduce two new matrix classes for this purpose,
\texttt{permuted-dense} and \texttt{stacked-permuted-dense}, which let us use
dense storage and BLAS subroutines.
In addition, we split the computation into a symbolic pass, which computes and
caches the structure of every intermediate matrix, and a numeric pass, which fills in values.
This separation is particularly useful for compiling problems involving parameters, where
the structure is fixed but the numerical values can change. The two-phase approach is
standard in sparse direct factorization and in the interfaces of \ac{NLP} solvers.
Neither the two matrix classes nor the two-phase approach exists in \texttt{CVXPY}'s backends.
By bringing both to canonicalization, we address the research gap we identified
in \S\ref{sec:research-gap}.

Other important design decisions differ from \texttt{CVXPY}'s backends for
simplicity rather than performance. Every node carries one Jacobian taken with respect to
all of the variables of the problem, rather than a dictionary of local Jacobians keyed by
variable. As a consequence, the chain rule is a single matrix product, and the
constraint matrix is built by stacking the Jacobians of the constraints.
In addition, quadratic functions have a dedicated Hessian pass, instead of a
variable substitution followed by a second matrix stuffing pass.

The rest of the chapter is organized as follows. We begin with a brief overview of
the engine, describing how expressions are represented and how the code is organized.
We then present the three matrix representations used for the derivative computations.
Next, we describe the
algorithms, or kernels, which operate on and combine these matrix representations.
Finally, we describe the problem interface of the engine, and how \texttt{CVXPY} obtains
and updates the problem data through it. We conclude with a summary.

\section{Overview of the engine}\label{sec:theme1-overview}

\texttt{SparseDiffEngine} is a small C library, around seventeen thousand lines
of code and a similar number of lines for the test suite.
The expression node is defined in \texttt{expr.h}. Atoms that carry extra data, such as
the exponent of a power, define a larger structure in \texttt{subexpr.h}.
We implement each atom in its own file in the \texttt{atoms/}
directory. There are around forty-five of them, divided into six subdirectories based on their
mathematical properties.
The matrix data structures and the computational kernels that operate on them are in
\texttt{utils/}, and \texttt{problem.c} collects the objective and constraints of a
problem and evaluates the values and derivatives that a solver asks for.

\subsection{Atom classes}\label{sec:theme1-atom-classes}
Atoms in the same subdirectory compute their derivatives in the same way.
Table~\ref{tab:atom-classes} lists the classes and how each computes its Jacobian.
Canonicalization leaves the constraints affine and the
objective affine or quadratic. The quadratic atoms of a DCP problem, such as a squared power,
a quadratic over a linear term, or a Huber penalty, are all rewritten as quadratic forms by
the canonicalization frontend of \S\ref{sec:canonicalization}. Therefore, only affine atoms
and quadratic forms reach the engine from a canonicalized DCP problem.
The rest of the chapter describes the affine atoms. The quadratic form contributes the
objective matrix~$\mmat{P}$ through the Hessian, described in \S\ref{sec:theme1-api}. The
remaining classes are used by the \ac{NLP} interface of
\texttt{CVXPY} \cite{cederberg2025disciplined}.

Each atom implements three operations. The forward pass evaluates the atom at a point. The
symbolic pass computes the sparsity patterns of its derivatives and allocates memory for
them. The numeric pass computes the numerical values inside the fixed sparsity patterns.
Each atom also has a constructor, the C function that allocates and initializes the
corresponding expression node. The constructor stores
pointers to these three operations in the node.

\subsection{Expression node}\label{sec:theme1-expression-node}
An expression node stores its dimensions, pointers to at most two children, a buffer for
its value, and its derivative matrices. Every derivative matrix has \texttt{n\_vars}
columns, the total number of entries of all the variables of the problem.
Listing~\ref{lst:expr-node} shows a simplified version of the node.
\begin{lstlisting}[language=C, caption={A simplified version of the expression
node in \texttt{expr.h}.}, label=lst:expr-node]
typedef struct expr
{
    int d1, d2, size, n_vars, refcount, var_id;
    struct expr *left;
    struct expr *right;

    double *value;     /* forward value                */
    matrix *jacobian;  /* Jacobian w.r.t. the variables */

    forward_fn        forward;
    jacobian_init_fn  jacobian_init_impl;  /* symbolic pass */
    eval_jacobian_fn  eval_jacobian;       /* numeric pass  */
} expr;
\end{lstlisting}
Trees are built bottom up, with one constructor per atom. A \texttt{CVXPY} expression
is converted in one pass over the tree, which calls the constructor of the corresponding atom
at each node, as described in \S\ref{sec:theme1-api}. Expressions that appear multiple times
can be shared, in which case the tree becomes a directed acyclic graph. Nodes are therefore
reference counted, and the symbolic pass returns early if a node was already initialized.

The engine has only two kinds of leaf node, variables and parameters, where \texttt{CVXPY}
also has constants. A variable occupies a contiguous slice of the stacked variable vector,
starting at the column offset \texttt{var\_id}. Its Jacobian is an identity block at the
columns of the variable, written once during the symbolic pass. The Jacobian of a parameter
is empty, because parameters are fixed during a solve. The engine treats a constant as a
parameter whose value cannot be updated between solves.

\section{Matrix representations}\label{sec:theme1-matrix-representations}
We store the Jacobian of a node in one of three representations, a generic sparse matrix, a
permuted dense matrix, or a stacked permuted dense matrix. The generic sparse matrix is the
default. The other two are created by matrix multiplication and the quadratic form, the
operations whose data is dense. Each implements the same operations, so an atom picks one
when it allocates its Jacobian during the symbolic pass.
Keeping dense blocks inside a sparse matrix is not a new idea, and
Appendix~\ref{app:dense-blocks} compares our representations with the formats that do so.
They differ from these formats in where the blocks sit. A permuted dense matrix places one
block at arbitrary rows and columns, and a stacked matrix places several at disjoint rows.

\subsection{Sparse matrix}\label{sec:theme1-generic-sparse}

The generic sparse representation stores a Jacobian in the CSR format of
\S\ref{sec:bg-sparse}. A Jacobian has one row for each entry of the value of its node,
and most operations, such as
indexing, broadcasting, and stacking, operate on those rows. Each row is stored contiguously
and reached in constant time.
For this reason we chose the CSR format over the CSC format.
In \texttt{SparseDiffEngine} the column indices within each row are kept sorted. The CSR
format does not necessarily require this order, and libraries differ on it. For example, of
the two sparse libraries behind \texttt{CVXPY}'s backends, \texttt{Eigen} keeps its indices
sorted \cite{guennebaud2010eigen}, while \texttt{scipy.sparse} does not always enforce it
\cite{2020SciPy-NMeth}. The merges
and intersections of the symbolic pass depend on this sorted order guarantee.

The symbolic pass allocates the row pointer and column index arrays, and the numeric pass
writes only the value array. \S\ref{sec:theme1-reusing-work} describes what this split
between the sparsity pattern and the values saves across solves.

\subsection{Permuted dense matrix}\label{sec:theme1-permuted-dense}

The Jacobians that appear during canonicalization do not always have scattered, isolated
nonzeros. Multiplying an expression by a data matrix, for example, places a dense block at a
subset of the rows and columns of the Jacobian. Consider the expression~$\mmat{B}\mvec{x}$ with
dense data. Its Jacobian holds the data at the columns of the variable and is zero everywhere
else, as visualized in Figure~\ref{fig:pd-motivation}. Those columns are usually a small part
of the Jacobian.
The generic sparse representation would instead need to store a column index for each entry of
the block.

The dense block can instead be stored together with the indices of the rows and columns it
occupies, one index per row and column rather than one per entry, and the global matrix is
never formed. We define a permuted dense matrix as the
triple~$(\mmat{X}, \mvec{r}, \mvec{c})$, with $\mmat{X} \in \reals^{m_0 \times n_0}$ dense
and $\mvec{r}$ and $\mvec{c}$ strictly increasing index vectors, representing
\BEQ\label{eq:permuted-dense}
  \mmat{A} = \mmat{S}_r^\top \mmat{X} \mmat{S}_c \in \reals^{m \times n},
  \qquad A_{r_i,\, c_j} = X_{ij},
\EEQ
where the rows of $\mmat{S}_r \in \{0,1\}^{m_0 \times m}$ and
$\mmat{S}_c \in \{0,1\}^{n_0 \times n}$ are the rows of the identity indexed by $\mvec{r}$
and~$\mvec{c}$, as shown in Figure~\ref{fig:permuted-dense}. Every other entry of~$\mmat{A}$ is
structurally zero and never stored. The entries of~$\mvec{c}$ are columns of the global
variable vector and the entries of~$\mvec{r}$ are rows of the Jacobian.

the storage does not depend on the global dimensions~$m$ and~$n$. Structural atoms, which only
rearrange entries, turn a permuted dense matrix into another permuted dense matrix by
manipulating the row and column indices alone. The transpose of a permuted dense matrix
swaps the two index vectors and transposes the dense block.

of~$\mmat{B}\mvec{x}$. The row vector of the result is~$(0,1)$ rather than~$(0,3)$, because

rows of the original block is kept internally, and the numeric pass copies the values
through this map at every evaluation.

A permuted dense matrix has nonzeros only inside its dense block. The Jacobian
of~$\mmat{B}\mvec{x} + \mvec{y}$ contains the block of~$\mmat{B}$ at the columns of~$\mvec{x}$
and an identity at the columns of~$\mvec{y}$, which no single block covers. The sum is
instead performed on CSR views of the two operands. A view is built during the symbolic
pass, and its value array points to the dense block, so no values are copied. The result is
stored as a generic sparse matrix, and so is everything computed from it.

\subsection{Stacked permuted dense matrix}\label{sec:theme1-stacked-pd}

Multiplying a matrix-valued expression with $k$ rows and $q$ columns by
data~$\mmat{B} \in \reals^{r \times k}$ multiplies each of the $q$ columns by~$\mmat{B}$. On
the vectorized expression the multiplication acts as the block diagonal
operator~$\mmat{I}_q \otimes \mmat{B}$ of Table~\ref{tab:views-copies}. In practice this
operator is not formed, unlike in \texttt{CVXPY}'s backends. The atom stores a single copy
of~$\mmat{B}$ and applies it to one column at a time. Its Jacobian contains
one dense block for each of the $q$ columns, at pairwise disjoint rows and in general at
different columns, as in Figure~\ref{fig:stacked-pd}. No single
triple~$(\mmat{X}, \mvec{r}, \mvec{c})$ describes such a matrix. Merging the blocks into one
larger block would store the zeros between them, and falling back to the generic sparse
representation would lose the dense structure. We instead keep the blocks as they are, in a
third representation.

We define a stacked permuted dense matrix as a vertical union of permuted dense blocks whose
row vectors are pairwise disjoint, while the column vectors may overlap. Every operation
treats the blocks one at a time, and the global matrix is never formed. The stacked matrix
owns a single value buffer, and each block points into it.

\subsection{Kernel dispatch}\label{sec:theme1-kernel-dispatch}

The operations of Table~\ref{tab:kernel-operations} divide into unary operations, which
operate on a single matrix, and binary operations, which combine two matrices. A call on a
Jacobian must select the kernel that matches its representation, a step called dispatch.
For a unary operation, each representation implements the operation and the call runs that
implementation. The kernel of a binary operation may depend on the representations of both
operands.

For example, on a generic sparse matrix the symbolic pass of the \texttt{index} kernel
allocates a new CSR pattern and copies the column indices of the selected rows.
On a permuted dense matrix
it intersects the selected rows with the row index vector, exactly as in
Figure~\ref{fig:permuted-dense-index}. On a stacked matrix the permuted dense kernel is
applied to each block, and the blocks left with no selected rows are dropped. In all three
representations the numeric pass only copies the values of the rows that were kept.

Of the three binary operations, only the transposed products dispatch on both operands.
Addition always operates in the CSR format. Both operands are read through their CSR views
and the result is a generic sparse matrix, so no dispatch is needed.
In the product~$\mmat{B}\mmat{A}$, the matrix~$\mmat{B}$ is data rather than a Jacobian, so
only the representation of~$\mmat{A}$ selects the kernel. In the transposed
products~$\mmat{B}^\top \mmat{A}$ and~$\mmat{B}^\top \mmat{D} \mmat{A}$, both operands are
Jacobians, each with its own representation. We select their kernel by
double dispatch, meaning that the pair formed by the representations of both operands
selects the implementation. Figure~\ref{fig:kernel-dispatch} lists the nine possible
combinations.

The nine kernels fall into four families. When both operands are permuted dense, the
kernel is a single \texttt{dgemm} on the two blocks. When an operand is stacked, the
kernel pairs the blocks of the two operands and calls one \texttt{dgemm} for each pair
with intersecting row sets. When one operand is dense and the other is
generic sparse, the kernel is a hand-written product that multiplies the stored nonzeros of
the sparse operand against the dense block, without converting either operand.
When both operands are generic sparse, the kernel is Gustavson's algorithm
\cite{gustavson1978two}. A product with a permuted dense or stacked operand produces a
result of the same kind, so once a dense block appears, the dense representations take
over.

The product of two permuted dense matrices stays permuted dense. With the selector
matrices of~\eqref{eq:permuted-dense}, the transposed product of
$\mmat{A} = (\mmat{X}_A, \mvec{r}_A, \mvec{c}_A)$
and $\mmat{B} = (\mmat{X}_B, \mvec{r}_B, \mvec{c}_B)$ expands to
\BEQ\label{eq:pd-product}
\mmat{B}^\top \mmat{A}
= \mmat{S}_{c_B}^\top \mmat{X}_B^\top
\underbrace{\left(\mmat{S}_{r_B} \mmat{S}_{r_A}^\top\right)}_{\mathclap{\text{index-set intersection}}}
\mmat{X}_A \mmat{S}_{c_A},
\EEQ
and the product without transpose expands to
\BEQ\label{eq:pd-product-ba}
\mmat{B} \mmat{A}
= \mmat{S}_{r_B}^\top \mmat{X}_B
\left(\mmat{S}_{c_B} \mmat{S}_{r_A}^\top\right)
\mmat{X}_A \mmat{S}_{c_A}.
\EEQ
In~\eqref{eq:pd-product}, the term~$\mmat{S}_{r_B} \mmat{S}_{r_A}^\top$ keeps the rows that
appear in both~$\mvec{r}_B$ and~$\mvec{r}_A$, and the outer selectors place the product at
the rows~$\mvec{c}_B$ and the columns~$\mvec{c}_A$. In~\eqref{eq:pd-product-ba}, both
selectors of~$\mmat{B}$ swap roles: the inner term intersects~$\mvec{c}_B$ with~$\mvec{r}_A$,
and the product is placed at the rows~$\mvec{r}_B$. In both cases the result is again one
dense block at permuted positions. In practice, the symbolic pass
intersects the two sorted index vectors, the numeric pass multiplies the two blocks with
one \texttt{dgemm}, and no selector matrix is formed. The cost of this operation depends
on the sizes of the blocks and not on the global dimensions.

An elementary count makes this precise. A permuted dense matrix with an
$m' \times n'$ block stores $m'n'$ values and $m' + n'$ indices, whereas the same block in
\ac{CSR} form stores $m'n'$ values, $m'n'$ column indices, and $m + 1$ row pointers, where $m$
is the number of rows of the whole matrix. For the product~\eqref{eq:pd-product}, let
$s = |\mvec{r}_A \cap \mvec{r}_B|$ be the number of shared rows. The symbolic pass merges two
sorted index vectors in $O(m_A + m_B)$ operations, and the numeric pass performs
$n_B\, s\, n_A$ multiply-adds in one \texttt{dgemm}. On the same blocks stored as generic
sparse matrices, Gustavson's algorithm performs the same multiply-adds, but its symbolic
pass builds the pattern of the result entry by entry, with $O(n_B\, s\, n_A)$ operations and
one stored index per entry. The dense representations therefore reduce the symbolic work
and the index storage from the number of entries of a block to the number of its rows and
columns. In the numeric pass they keep the operation count, and replace an index-driven
loop by a \ac{BLAS} call, a gain in the constant factor rather than in the asymptotic cost.
For a stacked operand, these counts are summed over the pairs of blocks with intersecting
rows.

\subsection{Caching structure across solves}\label{sec:theme1-reusing-work}

% (subsection reorganized per advisor review of 2026-08-19: define the split once, then group
%  what is cached into patterns / layouts / maps; the payoff-across-solves ¶ moved to §3.4.1
%  on 2026-08-22, at constraint-tree granularity, see plans/document8-advisor-comments.md #31)
The split between the two passes determines what the engine reuses across solves. In the
symbolic pass, a kernel computes everything determined by the structure of its operands
and stores it. In the numeric pass it computes only the values inside that structure, and
allocates nothing, because every buffer, including the work arrays of the kernels, is
allocated in the symbolic pass. Depending on the kernel, the stored structure is a
sparsity pattern, a block layout, or an index map.

The sparse kernels cache sparsity patterns.
The \texttt{add} atom merges the sorted patterns of its operands, and the sparse products
run the symbolic phase of Gustavson's algorithm \cite{gustavson1978two, bank1993smmp}, which
finds the
pattern of the product row by row. Finding the pattern is the costly and irregular part of
both operations, and the numeric pass only computes the values and fills the stored
pattern. For a product, the numeric
pass computes one sparse dot product per stored nonzero, as shown in
Figure~\ref{fig:sparse-product-passes}. It does not have to find which entries of the
product exist or where they are stored, and evaluates each one directly.

The dense kernels cache block layouts in place of a sparsity pattern.
The permuted dense kernels intersect the index vectors of their operands during the
symbolic pass, and on the stacked matrices of \S\ref{sec:theme1-stacked-pd} the symbolic
pass also determines which pairs of blocks have intersecting row sets. The numeric pass
gathers the matching rows, multiplies them with
\texttt{dgemm}, and scatters the products to fixed positions.

The atoms that only move or add entries of the child Jacobian, which we call structural
atoms, cache index maps. The Jacobian of \texttt{sum} is a sum of groups of rows of the
child Jacobian. The symbolic pass records, for each nonzero of the child Jacobian, the
output entry it is added to, as shown in Figure~\ref{fig:sum-idx-map}. The numeric pass is
one loop with one addition per nonzero. Other structural atoms such as \texttt{index},
\texttt{transpose}, and \texttt{broadcast} build their maps in the same way, with a copy in
place of an addition.

\section{Problem interface}\label{sec:theme1-api}

We collect the objective and constraint trees in one
\texttt{problem} object, defined in \texttt{problem.c}. We also wrote
\texttt{sparsediffpy}, a Python extension module that exposes the atom constructors and
the functions that build and evaluate the \texttt{problem} object.
We keep everything specific to \texttt{CVXPY} in a converter and a canonicalization
backend named \texttt{diffengine}. The lower-case name distinguishes the backend from
\texttt{SparseDiffEngine}. The converter builds the C trees of the canonicalized
problem in one pass over it, with one constructor call per node. The backend obtains the
problem data as the values and derivatives of the trees, replacing the matrix stuffing
pass of \S\ref{sec:matrix-stuffing}.

\subsection{Stacking the constraint Jacobians}\label{sec:theme1-problem-interface}

The \texttt{problem} object stores the constraint trees in the order in which they are
registered, and the row blocks of the constraint Jacobian follow that order. Conic
solvers expect the constraints grouped and ordered by cone, but the engine knows nothing
about cones. Registering the trees in the order the solver expects and recording the cone
of each row block are both handled by \texttt{CVXPY}, as part of the canonicalization frontend of
\S\ref{sec:canonicalization}.

The split between structure and values of \S\ref{sec:theme1-reusing-work} is applied at
the problem level as well. The solver receives one global CSR matrix, which the symbolic
pass builds once by stacking the sparsity patterns of the constraint Jacobians, as in
Figure~\ref{fig:jacobian-stacking}.
The numeric pass copies the values of each tree into a fixed slice of the global value
array. The Jacobian of an affine tree does not depend on the variable values. Its entries
are determined by shapes and index sets, or by problem data, and change only when a
parameter is updated. The numeric pass therefore skips an affine tree after the first
evaluation, until the next parameter update. The Hessian follows the same split. An affine tree
contributes nothing to it, so for a canonicalized problem only the objective is evaluated.
The Hessian is symmetric, and only its lower triangular entries are passed to the solver.

\subsection{\texttt{CVXPY} interface}\label{sec:theme1-backend}

The converter maps a variable leaf to its column offset in the stacked variable vector,
and a parameter leaf to its offset in the flattened parameter vector~$\gvec{\theta}$.
Each constraint contributes one tree per
argument, in the order in which \texttt{CVXPY} groups the cones: zero, nonnegative,
second-order, semidefinite, exponential, and power.

The \texttt{diffengine} backend wraps the \texttt{problem} object in one class, which has
the same interface as the output of matrix stuffing, so the rest of \texttt{CVXPY} is
unchanged. Listing~\ref{lst:diffengine-cone-program} outlines the class.

The class is built once per problem family. Its constructor converts the Python problem
to C trees with the converter and runs the symbolic pass. It then evaluates the
\texttt{problem} object once at the origin, which recovers the problem data
of~\eqref{e:quad-conic-form}.
The class stores each constraint as the affine function it evaluates, $\mmat{A}\mvec{x} +
\mvec{b} \in \cone{K}$, as in the docstring of Listing~\ref{lst:diffengine-cone-program}.
\texttt{CVXPY} then negates~$\mmat{A}$ to obtain the form
$\mvec{b} - \mmat{A}\mvec{x} \in \cone{K}$ of~\eqref{e:quad-conic-form}. A parameter update
involves only the numeric pass. The method \texttt{apply\_parameters} writes the new
values into the parameter leaves and repeats the evaluations at the origin. After the
solve, \texttt{split\_solution} slices the stacked solution vector into the variables of
the original problem. Listing~\ref{lst:extract-at-origin} shows the evaluations at the
origin.

A.rows, A.cols = problem.jacobian_sparsity()

\section{Summary}\label{sec:theme1-summary}

% (chapter wrap-up added per advisor review of 2026-08-19; promoted to a headed section
%  2026-08-22 to match §2.4 and §4.3; rewritten around the contributions from William's
%  draft 2026-08-23)
This chapter presents our approach to canonicalizing
optimization problems faster. Our main contribution is two new matrix classes that take
advantage of the dense blocks in problem data. Along with these data structures, we
present the kernels of Table~\ref{tab:kernel-operations} that operate on them. The
kernels are new but fairly straightforward, as each reduces to simple index manipulations
followed by calls to existing sparse and dense routines. Together, the matrix classes
and the kernels let sparse and dense Jacobians mix in the same tree without converting
to one specific format.

In addition, for parametric problems, our contribution is the two-phase approach to computing
derivatives. The idea goes back to sparse direct solvers, which separate symbolic analysis
from numeric factorization~\cite{davis2006direct}, and to Gustavson's sparse
product~\cite{gustavson1978two}. Like the sparse \ac{AD} of \texttt{CasADi}
in \S\ref{sec:casadi}, the symbolic pass caches sparsity patterns, but we pair each pattern
with index maps instead of a graph colouring, and our numeric pass writes the coefficient
values directly in place rather than through compressed sweeps.
The cached structure also covers every problem, not only the problems that conform to the
\ac{DPP} ruleset.

Finally, the choice to implement the engine in C with custom matrix classes forced us to
think carefully about memory allocation, sparse formats, and opportunities to cache
computation. We use the term
lightweight to describe the engine because it is a small dependency-free C library
(other than BLAS, which is a standard dependency) that only implements the required
operations. 

The next chapter presents the results of these contributions. For a fair
comparison, we compare only against \texttt{CVXPY}'s existing backends of
\S\ref{sec:matrix-stuffing}, which take the same canonicalized expressions as input and
produce the same problem data. The other modelling languages of
Chapter~\ref{sec:RevLitt} store and compute their coefficients differently. A comparison
with them would be difficult to assess, because their times can cover more than just the
coefficient computation.
