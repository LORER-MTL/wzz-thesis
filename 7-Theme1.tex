\Chapter{A LIGHTWEIGHT COEFFICIENT EXTRACTION ENGINE}\label{sec:Theme1}

The previous chapter showed that coefficient extraction in modern modeling
languages relies on generic sparse matrix multiplication---an approach that
creates intermediate matrices at every node of the expression tree and
treats each linear operator as an arbitrary sparse matrix. This chapter
presents an alternative: a lightweight engine written in C that operates
directly on CSR index arrays, avoiding intermediate matrices entirely.

%%
%% SECTION 1: Design principles
%%
\section{Design principles}
\label{sec:design-principles}

The engine is guided by three principles, each addressing a specific
inefficiency identified in the previous chapter's analysis of existing
systems.

\paragraph{Principle 1: Direct CSR rewriting}
Every affine atom transforms the CSR arrays \texttt{(indptr, indices, data)}
of the child's Jacobian directly, rather than forming an operator matrix and
composing via sparse matrix multiplication. A \texttt{sum} node merges row
pointers; a \texttt{left\_matmul} node applies block-diagonal dot products;
an \texttt{index} node copies row segments. No intermediate sparse matrices
are formed at any point.

\paragraph{Principle 2: Two-phase evaluation}
Sparsity patterns are computed once at build time (\emph{init phase});
numerical values are filled at solve time (\emph{eval phase}). The init
phase traverses the expression tree bottom-up, determining the exact number
of nonzeros in each Jacobian and allocating all arrays to their final sizes.
The eval phase traverses the same tree, filling values into pre-allocated
arrays without any allocation. This separation mirrors the compile-once,
evaluate-many paradigm used in parametric optimisation.

\paragraph{Principle 3: Precomputed index mappings}
Where rows must be combined, reordered, or selected, a mapping from source
to destination positions is precomputed during init. At eval time, the
operation reduces to a single $O(\texttt{nnz})$ scatter loop. The
\texttt{sum} atom's \texttt{idx\_map} array (Section~\ref{sec:atom-sum}) is
the prototypical example: rather than performing a sparse matrix
multiplication $\ones^T J_x$ at every evaluation, the engine scatters the
child's nonzeros through a fixed map.

\subsection{Architecture overview}
\label{sec:architecture}

The engine represents each affine expression as a node in a directed acyclic
graph (DAG). Each node is a C~\texttt{struct} containing:
\begin{itemize}
\item the node's \emph{type} (one of the fifteen atoms in
  Table~\ref{tab:affine-atoms}),
\item a pair of function pointers---\texttt{jacobian\_init} and
  \texttt{eval\_jacobian}---that implement the two-phase protocol for that
  atom type,
\item pointers to child nodes (one or two, depending on the atom),
\item the Jacobian in CSR format: arrays \texttt{indptr}, \texttt{indices},
  and \texttt{data}, plus dimensions,
\item atom-specific auxiliary data (index maps, constant matrices, axis
  parameters).
\end{itemize}
Function-pointer dispatch on the node type provides polymorphism without
virtual-table overhead.

When two expressions share a common subexpression, the DAG representation
allows the shared node's Jacobian to be computed once and reused by both
parents. The engine tracks whether each node's Jacobian has been evaluated
via a \texttt{jacobian\_called} flag, avoiding redundant computation.

A \emph{problem container} groups the objective expression and all constraint
expressions, manages the global variable ordering, and stores the final
assembled coefficient matrices $(A, b, c)$ that are handed to the solver.

\section{Worked example: tracing coefficient extraction}
\label{sec:worked-example}

To build intuition before the atom-by-atom treatment, we trace the
least-squares problem $\text{minimize } \|Fx - g\|_2^2$ from
Chapter~\ref{sec:RevLitt} end-to-end through the engine.
After canonicalization (DCP verification, Smith form, and relaxed Smith form
as described in Section~\ref{sec:RevLitt}), the conic reformulation produces
the equality constraint $t = Fx - g$ linking the auxiliary variable $t$ to
the original expression. The engine must extract the coefficient matrix for
this affine expression.

\paragraph{Expression tree after canonicalization}
The affine expression $Fx - g$ is represented as:
\begin{center}
\begin{tikzpicture}[
    level distance=20mm,
    level 1/.style={sibling distance=35mm},
    every node/.style={circle, draw, minimum size=14mm, inner sep=0pt,
                       font=\small}
]
\node {\texttt{add}}
  child {
    node {\texttt{mul}}
      child { node {\texttt{F}} }
      child { node {\texttt{x}} }
  }
  child { node {\texttt{neg($g$)}} };
\end{tikzpicture}
\end{center}
The \texttt{mul} node represents left multiplication by the constant matrix
$F \in \reals^{3 \times 2}$, the \texttt{neg} node negates the constant
$g \in \reals^{3}$, and the \texttt{add} node sums the two children.

\paragraph{Init phase}
The engine traverses the tree bottom-up, computing sparsity patterns:
\begin{enumerate}
\item \textbf{Variable leaf} ($x$): Jacobian is $I_2$ (identity), so
  $\texttt{nnz} = 2$, \texttt{indptr} $= [0, 1, 2]$, \texttt{indices}
  $= [0, 1]$.
\item \textbf{\texttt{mul} node} ($F \cdot x$): The Jacobian with respect
  to~$x$ is~$F$ itself, a $3 \times 2$ matrix.
  Init determines $\texttt{nnz} = 6$ (all entries of $F$ are nonzero) and
  allocates arrays of the corresponding sizes.
\item \textbf{Constant leaf} ($-g$): No variable dependence, contributes
  only to the constant column. Jacobian with respect to~$x$ is the
  $3 \times 2$ zero matrix.
\item \textbf{\texttt{add} node}: Takes the union of the children's sparsity
  patterns. Since the constant $-g$ contributes no variable columns, the
  output sparsity matches the \texttt{mul} child: $\texttt{nnz} = 6$.
\end{enumerate}
After init, every node's CSR arrays are allocated to their exact final sizes.
No further allocation occurs.

\paragraph{Eval phase}
A second bottom-up traversal fills in numerical values:
\begin{enumerate}
\item \textbf{Variable leaf}: \texttt{data} $= [1, 1]$ (identity values).
\item \textbf{\texttt{mul} node}: Applies $F$ to the child's Jacobian via
  block-diagonal dot products (Section~\ref{sec:atom-leftmatmul}), writing
  the six entries of $F$ into \texttt{data}.
\item \textbf{\texttt{add} node}: Sums corresponding entries. The constant
  offset~$-g$ is added to the constant column of the output.
\end{enumerate}

\paragraph{Result}
The root node's Jacobian is the coefficient matrix:
\[
\begin{blockarray}{ccc}
x_1 & x_2 & 1 \\
\begin{block}{[cc|c]}
1 & 2 & -1 \\
3 & 4 & -2 \\
5 & 6 & -3 \\
\end{block}
\end{blockarray}
= [F \mid {-g}],
\]
which matches the constraint $t - Fx = -g$ from the canonicalization.
The entire computation involved no sparse matrix multiplication, no
intermediate matrix allocation, and no runtime sparsity discovery.

\subsection{Direct encoding of linear operators}

coefficient matrix in CSR (Compressed Sparse Row) format and directly
manipulate its index arrays without forming intermediate matrices. Each linear
operator is implemented as a transformation on the CSR arrays
\texttt{(indptr, indices, data)}. For example, the \texttt{sum} operator
collapses all rows into row~0 by setting all entries of \texttt{indptr} to
$[0, \texttt{nnz}]$, effectively mapping every row index to~0 without any
matrix multiplication.

\subsection{The \texttt{sum} atom and the \texttt{idx\_map} trick}
\label{sec:atom-sum}

Summing along an axis collapses multiple rows of the child's Jacobian into
fewer rows. Mathematically, for a full summation ($y = \ones^T x$, scalar
output), the Jacobian is $J_y = \ones^T J_{\text{child}}$---every row of
$J_{\text{child}}$ is accumulated into a single output row. The naïve
approach would compute this via sparse matrix multiplication, allocating a
new matrix each time. Instead, the engine precomputes a mapping from every
nonzero position in the child's Jacobian to its target position in the
output, then uses a simple scatter-accumulate loop at evaluation time.

\paragraph{Initialisation (Algorithm~\ref{alg:sum-init})}
During \texttt{jacobian\_init}, the output sparsity pattern is determined
by taking the union of all column indices that appear across the rows being
summed. Duplicate column indices from different rows are merged into a
single output entry. An array \texttt{idx\_map} of length
$\texttt{nnz}(J_{\text{child}})$ is then built: for each nonzero $k$ in
the child's Jacobian, $\texttt{idx\_map}[k]$ stores the position in the
output's \texttt{data} array where that value should be accumulated.

\begin{algorithm}[ht]
\caption{\texttt{sum} --- Jacobian initialisation (sparsity + index map)}
\label{alg:sum-init}
\begin{algorithmic}[1]
\Require Child Jacobian $J_x$ in CSR format; rows to sum: $\{r_0, \ldots, r_{s-1}\}$
\Ensure  Output Jacobian $J$ with one row per output element; array \texttt{idx\_map}
\State $\textit{cols} \gets$ union of column indices across summed rows of $J_x$
\State Sort \textit{cols}; remove duplicates
\Comment{$O(\texttt{nnz} \log \texttt{nnz})$}
\State Set $J.\texttt{indptr}$, $J.\texttt{indices}$ from \textit{cols}
\State Build reverse map $\texttt{col\_to\_pos}[\,]$: for each unique column $c$
  at position $p$, set $\texttt{col\_to\_pos}[c] \gets p$
\For{each nonzero $k$ in $J_x$ (across summed rows)}
  \State $\texttt{idx\_map}[k] \gets \texttt{col\_to\_pos}[J_x.\texttt{indices}[k]]$
\EndFor
\end{algorithmic}
\end{algorithm}

\paragraph{Evaluation (Algorithm~\ref{alg:sum-eval})}
At each parameter update, \texttt{eval\_jacobian} zeroes the output values
and then scatters the child's nonzeros through the precomputed map. The
loop body is a single indexed addition per nonzero---no sorting, no
allocation, and no matrix multiply.

\begin{algorithm}[ht]
\caption{\texttt{sum} --- Jacobian evaluation}
\label{alg:sum-eval}
\begin{algorithmic}[1]
\Require Child Jacobian $J_x$ (values updated); precomputed \texttt{idx\_map}
\Ensure  Output Jacobian $J$ with accumulated values
\State $J.\texttt{data} \gets \mathbf{0}$
\For{$k = 0$ \textbf{to} $\texttt{nnz}(J_x) - 1$}
  \State $J.\texttt{data}[\texttt{idx\_map}[k]]
         \mathrel{+}= J_x.\texttt{data}[k]$
\EndFor
\end{algorithmic}
\end{algorithm}

\paragraph{Complexity}
Initialisation costs $O(\texttt{nnz} \log \texttt{nnz})$ (dominated by the
sort) and runs once. Evaluation costs $O(\texttt{nnz})$ with a single pass
over the child's nonzeros. While sparse matrix multiplication
$\ones^T J_x$ is also $O(\texttt{nnz})$ in principle, it must allocate a
new result matrix, compute its sparsity pattern, and sort indices at every
call---overhead that the \texttt{idx\_map} approach eliminates entirely.
Figure~\ref{fig:csr-sum-operator} illustrates the CSR transformation for a
concrete example.

\subsection{The \texttt{left\_matmul} atom and Kronecker avoidance}
\label{sec:atom-leftmatmul}

Left multiplication computes $Y = A \, X$ where $A \in \reals^{m \times n}$
is a constant (or parameter) matrix and $X \in \reals^{n \times p}$ is the
child expression. Writing the operation in vectorised form gives
\begin{equation}
  \vect(Y) = (I_p \otimes A) \, \vect(X),
\end{equation}
so the Jacobian with respect to $\vect(X)$ is the block-diagonal matrix
$I_p \otimes A$ of size $mp \times np$. Forming this Kronecker product
explicitly would require storing $p \cdot \texttt{nnz}(A)$ entries in the
best case; worse, composing it with the child's Jacobian via sparse
matrix multiplication is $O(p^2 \cdot \texttt{nnz}(A))$ in general.

The engine avoids the Kronecker product entirely by exploiting the
block-diagonal structure. It stores only $A$ (of size $m \times n$) and
applies it independently to each of the $p$ column-blocks of the child's
Jacobian. The computation is carried out in CSC (Compressed Sparse Column)
format, because the child's Jacobian columns each decompose naturally into
$p$ consecutive blocks of $n$ rows.

\paragraph{Initialisation}
During \texttt{jacobian\_init}, the child's Jacobian sparsity is converted
to CSC. For each column $j$ and each block $b \in \{0, \ldots, p-1\}$,
the engine identifies which rows of $A$ have overlapping column support
with the child's nonzeros in block~$b$. These overlaps determine the
output sparsity without ever forming $I_p \otimes A$.

\paragraph{Evaluation (Algorithm~\ref{alg:leftmatmul-eval})}
At each parameter update, the child's Jacobian values are converted to
CSC, then each output nonzero is computed as a sparse dot product of a
row of $A$ with the corresponding block-slice of the child's column.

\begin{algorithm}[ht]
\caption{\texttt{left\_matmul} --- Jacobian evaluation
  (block-diagonal multiply)}
\label{alg:leftmatmul-eval}
\begin{algorithmic}[1]
\Require Constant matrix $A \in \reals^{m \times n}$; child Jacobian
  $J_x$ in CSC with $p$ column-blocks of $n$ rows;
  precomputed output sparsity $J$ in CSC
\Ensure  Output Jacobian $J$ with filled values
\State Convert $J_x$ values from CSR to CSC
  \Comment{pattern already fixed}
\For{each column $j$ of $J$}
  \For{each block $b = 0, \ldots, p-1$}
    \State $S \gets$ nonzeros of $J_x$ column $j$ in rows
      $[b \cdot n,\; (b+1) \cdot n)$
    \For{each output nonzero $(b \cdot m + i,\; j)$ in $J$}
      \State $J.\texttt{data}[\cdot] \gets
        \text{sparse\_dot}(A[i, :],\; S)$
    \EndFor
  \EndFor
\EndFor
\State Convert $J$ values from CSC to CSR
\end{algorithmic}
\end{algorithm}

\paragraph{Complexity}
Let $\bar{k}$ denote the average number of nonzeros per column of
$J_{\text{child}}$ within a single block. Each output nonzero requires a
sparse dot product of cost at most $O(\texttt{nnz\_row}(A) + \bar{k})$.
The total work is therefore
$O(\texttt{nnz}(J) \cdot (\texttt{nnz\_row}(A) + \bar{k}))$, which for
typical sparse problems is far smaller than the
$O(p^2 \cdot \texttt{nnz}(A))$ cost of forming and multiplying the
Kronecker product.

\subsection{The \texttt{index} atom and structural row selection}
\label{sec:atom-index}

Indexing selects a subset of elements from the child expression:
$y = x[\text{indices}]$. Its Jacobian is a row-selection matrix~$P$
whose rows are drawn from the identity---row~$i$ of $P$ is row
$\text{indices}[i]$ of $I$. Since the child's Jacobian is stored in CSR,
selecting rows amounts to copying contiguous segments of the
\texttt{indices} and \texttt{data} arrays guided by \texttt{indptr}. No
arithmetic is performed at all.

\paragraph{Initialisation (Algorithm~\ref{alg:index-init})}
During \texttt{jacobian\_init}, the output Jacobian's sparsity pattern is
constructed by copying the column-index segment of each selected row from
the child's Jacobian. The row pointer array \texttt{indptr} is built
incrementally.

\begin{algorithm}[ht]
\caption{\texttt{index} --- Jacobian initialisation (structural copy)}
\label{alg:index-init}
\begin{algorithmic}[1]
\Require Child Jacobian $J_x$ in CSR; selection array
  $\texttt{idx}[0 \ldots k{-}1]$
\Ensure  Output Jacobian $J$ in CSR with selected rows
\State $J.\texttt{indptr}[0] \gets 0$
\For{$i = 0$ \textbf{to} $k - 1$}
  \State $r \gets \texttt{idx}[i]$
  \Comment{source row in $J_x$}
  \State $\ell \gets J_x.\texttt{indptr}[r+1] - J_x.\texttt{indptr}[r]$
  \State Copy $J_x.\texttt{indices}[J_x.\texttt{indptr}[r] \ldots
    J_x.\texttt{indptr}[r] + \ell)$ into
    $J.\texttt{indices}[J.\texttt{indptr}[i] \ldots]$
  \State $J.\texttt{indptr}[i+1] \gets J.\texttt{indptr}[i] + \ell$
\EndFor
\State $J.\texttt{nnz} \gets J.\texttt{indptr}[k]$
\end{algorithmic}
\end{algorithm}

\paragraph{Evaluation (Algorithm~\ref{alg:index-eval})}
At each parameter update, \texttt{eval\_jacobian} copies the \texttt{data}
segments for the same selected rows. The sparsity pattern is identical to
the child's selected rows, so only values move.

\begin{algorithm}[ht]
\caption{\texttt{index} --- Jacobian evaluation (value copy)}
\label{alg:index-eval}
\begin{algorithmic}[1]
\Require Child Jacobian $J_x$ (values updated); selection array
  $\texttt{idx}[0 \ldots k{-}1]$; output Jacobian $J$ (pattern fixed)
\Ensure  Output Jacobian $J$ with copied values
\For{$i = 0$ \textbf{to} $k - 1$}
  \State $r \gets \texttt{idx}[i]$
  \State $\ell \gets J.\texttt{indptr}[i+1] - J.\texttt{indptr}[i]$
  \State Copy $J_x.\texttt{data}[J_x.\texttt{indptr}[r] \ldots
    J_x.\texttt{indptr}[r] + \ell)$ into
    $J.\texttt{data}[J.\texttt{indptr}[i] \ldots]$
\EndFor
\end{algorithmic}
\end{algorithm}

\paragraph{Complexity}
Both initialisation and evaluation cost
$O\!\bigl(\sum_{i=0}^{k-1} \texttt{nnz}(\text{row}_{\texttt{idx}[i]})\bigr)$,
proportional to the total number of nonzeros in the selected rows. The
operation involves no arithmetic---only \texttt{memcpy} calls---making it
one of the cheapest atoms in the engine.

\medskip
\noindent
The preceding atom deep-dives illustrate the common pattern: each atom
transforms the child's CSR arrays directly, using precomputed index
mappings to eliminate runtime allocation and sparsity discovery. The
remaining sections address the system-level concerns that complete the
engine design.

\section{Memory management}
\label{sec:memory-management}

The two-phase design described in Section~\ref{sec:design-principles}
enables tight control over memory allocation. This section describes the
four techniques the engine uses to minimise memory overhead.

\paragraph{Exact-size allocation}
The init phase determines the exact number of nonzeros in every node's
Jacobian before any numerical computation occurs. All \texttt{malloc} calls
therefore allocate arrays of exactly the required size---no over-allocation,
no reallocation, and no amortised-doubling strategies. For a tree with $N$
nodes, init performs at most $3N$ allocations (one each for \texttt{indptr},
\texttt{indices}, and \texttt{data} per node), and eval performs zero.

\paragraph{Affine Jacobian caching}
Nodes whose children are all constants (no variable or parameter
dependence) produce Jacobians that never change. The engine detects such
nodes during init and marks them as \emph{cached}: their
\texttt{eval\_jacobian} is called once, and subsequent evaluations skip them
entirely. In typical problems, constant subexpressions (data matrices,
fixed offsets) constitute a significant fraction of the tree, so caching
eliminates a proportional share of eval-time work.

\paragraph{No Python object overhead}
Because the engine is implemented in C, there is no \texttt{scipy.sparse}
object creation, no Python reference counting or garbage collection pressure
during evaluation, and no format-conversion copies between CSR and CSC.
Each Jacobian is stored as three raw C arrays and a set of dimension
fields. The total per-node overhead is a fixed-size \texttt{struct} plus
the three arrays, compared to the multiple Python objects, type metadata,
and indirection layers in a \texttt{scipy.sparse.csr\_matrix}.

\paragraph{Memory footprint analysis}
The engine's total memory consumption for a single expression tree is:
\[
  M = \sum_{i=1}^{N} \bigl(
    (n_i + 1) \cdot \texttt{sizeof(int)}
    + \texttt{nnz}_i \cdot (\texttt{sizeof(int)} + \texttt{sizeof(double)})
  \bigr)
  + N \cdot \texttt{sizeof(expr)},
\]
where $n_i$ is the number of rows and $\texttt{nnz}_i$ the number of
nonzeros in node~$i$'s Jacobian. In \texttt{CVXPY}'s approach, each sparse
matrix multiplication at node~$i$ temporarily allocates an additional result
matrix, so the peak memory includes both the child's matrix and the product.
The engine avoids this by writing directly into the pre-allocated output,
so peak memory equals the sum above with no temporary overhead.

\section{Parameter handling}
\label{sec:param-handling}

When a problem contains parameters (symbolic placeholders whose numerical
values change between solves), the engine must update the coefficient
matrices without repeating the init phase. The two-phase architecture
makes this straightforward.

\paragraph{Parameter lifecycle}
Parameters are registered during problem construction via
\texttt{register\_params}, which associates each parameter node in the
expression tree with a pointer to the user-supplied value storage. When
the user updates parameter values and requests a new solve,
\texttt{update\_params} copies the new values into the parameter nodes.

\paragraph{Lazy refresh via \texttt{jacobian\_called}}
Each node carries a Boolean flag \texttt{jacobian\_called}. After
\texttt{update\_params} is called, the engine resets this flag on every node
that depends (transitively) on a changed parameter. The subsequent eval
traversal then recomputes only the affected nodes. Nodes that depend solely
on constants retain their cached Jacobians and are not revisited.

\paragraph{Direct re-traversal}
Unlike \texttt{CVXPY}'s tensor-based parametric approach, which stores a
three-dimensional structure mapping each parameter to its coefficient
contributions, the engine simply re-traverses the expression tree with the
new parameter values. This avoids the storage overhead of the tensor
representation and reuses the same tree-walking infrastructure used for the
initial evaluation.

\paragraph{Contrast with the tensor approach}
\texttt{CVXPY}'s \texttt{TensorView} maintains a dictionary of
dictionaries: for each variable, for each parameter, a separate sparse
matrix. For problems with $p$ parameters and $v$ variables, this multiplies
the storage by up to $p \cdot v$. The engine's approach stores only one
Jacobian per node regardless of the number of parameters. The trade-off is
that a parameter update requires a full eval traversal rather than a single
sparse matrix substitution, but since eval is dominated by $O(\texttt{nnz})$
scatter and copy operations, this cost is modest in practice.
