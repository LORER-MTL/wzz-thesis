Fundamentally, there is not much difference between how \texttt{SparseDiffEngine}
and \texttt{CVXPY}'s canonicalization backend compute derivatives. However, there are many
interesting implementation details which we will present in this chapter.
Firstly, the use of a custom sparse matrix data structure allows a natural split
between the symbolic and numeric phases of the derivative computation. This separation
is particularly useful for compiling problems involving parameters, where
the structure is fixed but the numerical values can change.
Secondly, in addition to being sparse, the data of most optimization
problems also have a lot of structure, such as dense blocks or diagonality.
In \texttt{SparseDiffEngine} we introduce two new matrix classes: \texttt{permuted-dense}
and \texttt{stacked-permuted-dense} for this purpose; they enable us to make
use of dense storage and BLAS subroutines when possible.

Finally, some important design decisions differ from \texttt{CVXPY}'s backends for
simplicity rather than speed. Every node carries a single Jacobian whose columns span
all of the variables of the problem, rather than a dictionary of local Jacobians keyed by
variable. As a consequence, the chain rule is a single matrix product, and the problem
data assembles by concatenation. In addition, quadratic functions pass through
dedicated Hessian oracles instead of a separate substitution and matrix stuffing pass.

The rest of the chapter is structured as follows: we begin with a brief overview of
the engine, describing how expressions are represented as trees of atoms and how the
code is organized.
We then present the matrix representations used for the derivative computations,
where we will focus much of our attention on the \texttt{permuted-dense}
matrix, which appears most often. Next we describe the algorithms, or \emph{kernels},
which allow us to operate on and combine these matrix representations.
Rather than attempting to explain too much, we focus on the organization of
the code and on how we handle operations between different
types of matrices. An intrigued reader will learn more
from exploring the repository, which is open source.
The chapter ends with some comments about the \ac{API} of
\texttt{SparseDiffEngine} as well as how it is used within \texttt{CVXPY}.

\section{Overview of the engine}\label{sec:theme1-overview}

\texttt{SparseDiffEngine} is a small C library, roughly eighteen thousand lines of code,
with a test suite of about the same size.
The expression node and the routines that traverse trees of expressions are defined in
\texttt{expr.c}. Each atom is implemented in its own file in the \texttt{atoms/}
directory; there are forty-five of them, divided into six subdirectories based on their
mathematical properties: \texttt{affine}, elementwise and bivariate functions with full or
restricted domains, and a small group of \texttt{other} atoms such as the quadratic form.
The matrix data structures and the numerical kernels that operate on them are in
\texttt{utils/}, and \texttt{problem.c} collects the objective and constraints of a
problem and implements the oracles that are passed to a solver. Atoms in the same
subdirectory have Jacobians with the same structure, and their implementations share most
of their code (\S\ref{sec:theme1-atom-implementations}). In this chapter we only discuss
the affine atoms and the quadratic form, since these are the only atoms that appear in
canonicalized DCP problems; the remaining classes are used by the nonlinear programming
(\acs{NLP}) interface of \texttt{CVXPY} \cite{cederberg2025disciplined}.\acused{NLP}

Each atom implements three operations: a \emph{forward} pass, which evaluates the atom at
a point; an \emph{init} pass, which computes the sparsity patterns of its derivatives and
allocates memory for them; and a \emph{value} pass, which computes the numerical values
inside the fixed patterns. The constructor of the atom installs these operations as
function pointers on the expression node.
The init pass runs once per problem, while the value pass runs at every evaluation.
\S\ref{sec:theme1-reusing-work} describes the benefits of this separation.

An expression node stores its dimensions, pointers to at most two children, a buffer for
its value, and its derivative matrices. A simplified version of the definition in
\texttt{expr.h} is shown below.
\begin{lstlisting}[language=C]
typedef struct expr
{
    int d1, d2, size, n_vars, refcount, var_id;
    struct expr *left;
    struct expr *right;

    double *value;     /* forward value                */
    matrix *jacobian;  /* Jacobian w.r.t. the variables */

    forward_fn        forward;
    jacobian_init_fn  jacobian_init_impl;
    eval_jacobian_fn  eval_jacobian;
    /* ... Hessian oracle, workspace and caching fields ... */
} expr;
\end{lstlisting}
Trees are built bottom up, with one constructor function per atom; the Python bindings
expose the same constructors. Expressions that appear multiple times can be shared, in
which case the tree becomes a directed acyclic graph. Nodes are therefore reference
counted, and the initialization routines return early if a node was already initialized
through another parent.

There are two leaf atoms, variables and parameters. A \emph{variable} occupies a
contiguous slice of the global variable vector, starting at its offset \texttt{var\_id};
its Jacobian is a selection matrix with one unit entry per row, written once during the
init pass. Unlike \texttt{CVXPY}, there is no separate constant node: constants and
parameters share a single leaf type, distinguished by an identifier that is $-1$ for
constants and, for updatable parameters, the offset of the parameter in the global
parameter vector. The Jacobian of this leaf is empty, since parameters are fixed during a
solve, and because parameters are leaves of the tree, the derivative structure remains
valid when their values change (\S\ref{sec:problem-statement}).

\section{Matrix representations}\label{sec:theme1-matrix-representations}

The \texttt{jacobian} field of the expression node has a polymorphic type called
\texttt{matrix}, with one representation for each kind of structure that we want to
exploit. The representation of a Jacobian is chosen by the atom that owns it during the
init pass, that is, during the symbolic phase; after that, every operation on the matrix,
such as transposition, row indexing, or a chain-rule product, simply dispatches to a
kernel specific to the representations involved. The default representation is a generic
sparse matrix stored in the CSR format of \S\ref{sec:bg-sparse} \cite{davis2006direct}.

\subsection{The permuted dense matrix}\label{sec:theme1-permuted-dense}

The Jacobians that appear during canonicalization are usually not sparse in the sense of
having scattered, isolated nonzeros. More often they contain a dense block, typically
problem data or a product involving problem data, placed at a subset of the rows and
columns of a much larger matrix. As an example, consider the affine expression $Ax$ with
dense data $A \in \reals^{50 \times 50}$ in a problem with ten thousand variables. The
Jacobian of this expression is the matrix $A$ itself, stored in the fifty columns that
correspond to $x$, with all other entries equal to zero. If this Jacobian is stored in a
generic sparse format, all subsequent products go through sparse kernels, and the
hardware efficiency of \S\ref{sec:bg-blas} is lost.

We therefore store such matrices in factored form. A \emph{permuted dense} matrix
is a triple $(X, r, c)$, where $X \in \reals^{m_0 \times n_0}$ is a dense block and $r$ and
$c$ are strictly increasing index vectors, representing
\BEQ\label{eq:permuted-dense}
  A = S_r^T X S_c \in \reals^{m \times n},
  \qquad A_{r_i,\, c_j} = X_{ij},
\EEQ
where $S_r \in \{0,1\}^{m_0 \times m}$ and $S_c \in \{0,1\}^{n_0 \times n}$ are the selector
matrices whose rows are the rows of the identity indexed by $r$ and $c$. All other entries of
$A$ are structurally zero and never stored. Figure~\ref{fig:permuted-dense} shows an
example with a $3 \times 3$ block inside a $6 \times 7$ matrix.

The chain-rule product of two permuted dense matrices is also permuted dense: for
permuted dense $A$ and $B$, the product $B^T A$ factors as
\BEQ\label{eq:pd-product}
B^T A
= S_{c_B}^T X_B^T \underbrace{\left(S_{r_B} S_{r_A}^T\right)}_{\text{row-set intersection}}
  X_A S_{c_A},
\EEQ
The middle factor is a zero-one matrix whose entry $(k, l)$ is one exactly when
$r_{B,k} = r_{A,l}$, so the sparsity analysis of the product amounts to intersecting two
sorted integer arrays. The result has row vector $c_B$ and column vector $c_A$, which are
known before any numerical values exist. For the values there are three cases. If the two
row sets are equal, the product is computed with a single \texttt{dgemm} on the two
blocks. If they overlap partially, the matching rows are first gathered into a workspace
(allocated during init), followed by the same \texttt{dgemm}. If they are disjoint, the
product is zero, and nothing is computed in the value pass. The weighted product
$B^T D A$, which appears when Hessians are assembled, is handled the same way, since
$S_r D S_r^T$ reduces to a small diagonal that is applied by scaling the rows of the
block.

The main benefit of the factored form is that the floating point work is done by dense
kernels. If the same matrix is stored in the CSR format, its products go through sparse
kernels, whose indexed accesses and irregular inner loops reach only a fraction of the
throughput of BLAS at the same operation count \cite{goto2008anatomy}. In the factored
form, the value pass of each kernel consists of a few BLAS calls on contiguous buffers.
The product $A^T D A$, for example, is computed with one copy, $m_0$ scalings, and one
\texttt{dgemm}, and the cost does not depend on the global dimensions.

When an expression with matrix shape $n \times p$ is multiplied by data
$A \in \reals^{m \times n}$, the effect on the vectorized expression is that of the block
diagonal operator $I_p \otimes A$. This operator is never formed. In memory, the $p$
segments of length $n$ of a vector $x$ form a $p \times n$ row-major matrix $\tilde{X}$,
and by a standard vectorization identity \cite{magnus2019matrix},
\BEQ\label{eq:kron-reshape}
  y = (I_p \otimes A)\, x
  \quad\Longleftrightarrow\quad
  \tilde{Y} = \tilde{X} A^T,
\EEQ
so the operator, nominally of size $pm \times pn$, is applied with a single
\texttt{dgemm} and no data movement. The Jacobian products of the \texttt{left\_matmul}
atom use the same identity, and avoiding the explicit operator made the initialization of
its sparsity pattern roughly one hundred times faster.

\subsection{The stacked permuted dense matrix}\label{sec:theme1-stacked-pd}

% also I don't like the start with "the representaiton..." like which one are we talking about?
The representation is, however, not closed under one family of products. The Jacobian of
the \texttt{left\_matmul} atom is $(I_p \otimes A)\, J$, where $J$ is the Jacobian of the
child expression. This matrix consists of $p$ row blocks, each of them a permuted dense
product, placed at disjoint global rows, and blocks with different column index vectors
cannot be described by a single triple $(X, r, c)$. For this reason there is a third
representation. A \emph{stacked permuted dense} matrix is a vertical union of permuted
dense blocks whose row vectors are pairwise disjoint; the column vectors may overlap. The
blocks share one value buffer, and the kernels of this subsection apply block by block:
structural atoms modify the index vectors of each block, products distribute over the
blocks with one \texttt{dgemm} each, and pairs of blocks with disjoint row sets are
skipped, as in \eqref{eq:pd-product}. A few operations, such as transposition, can cause
row vectors to overlap; these are followed by a coalescing step that merges such blocks.

Generic sparse, permuted dense, and stacked permuted dense are the only three matrix
representations in the engine.

atoms, such as \texttt{left\_matmul}, \texttt{scalar\_mult}, \texttt{convolve}, and
\texttt{kron}, place problem data in the Jacobian. Their values only change when a
parameter update sets the refresh flag of \S\ref{sec:theme1-overview}.

\subsection{Reusing work across passes}\label{sec:theme1-reusing-work}

The value pass never allocates memory; every buffer, including the scratch space of the
kernels, is allocated during init. Beyond allocation, several other kinds of work are
done only once. Sparsity patterns are computed during init: \texttt{add} merges the
patterns of its children with a sorted merge, the sparse products run the symbolic phase
of Gustavson's algorithm \cite{bank1993smmp}, and the factored products of
\S\ref{sec:theme1-matrix-representations} determine their output index vectors before any
values exist. Index maps are also precomputed: transposition stores its row permutation,
\texttt{kron} its per-row copy maps, and \texttt{sum} the map from child nonzeros to
output entries, so the value pass performs no index arithmetic. When the index vectors of
two operands do not intersect, the product is recorded as empty during init, and its
value pass does nothing. Finally, values that cannot change are written once; the
Jacobian of a variable, for example, is filled during init and never touched again.

Figure~\ref{fig:sum-idx-map} illustrates this for the \texttt{sum} atom. During init, the
representation of the child allocates the output and fills \texttt{idx\_map}, an array
that maps each nonzero of the child Jacobian to the output entry it is added to. The axis
convention and all other index decisions are handled at this point. The value pass is a
single loop, the same for every axis and every representation. Indexing, transposition,
and \texttt{kron} work the same way, with a copy instead of an addition.

The problem level works in the same way. During init, the sparsity structures of the
constraint Jacobians are concatenated into one global CSR matrix, by shifting the row
pointers of each root and copying the column indices. At every evaluation, each subtree
is refreshed and the value array of each root is copied into the global buffer at a fixed
offset. If a root Jacobian is permuted dense, its CSR view is built once during init, and
the value array of the view is a pointer to the dense block itself, so no values are ever
copied or converted when the block is refilled. Affine constraints are skipped entirely
after the first evaluation, since their values cannot change until the parameters do.

A parameter update therefore only involves the value pass: \texttt{update\_params} writes
the new values into the parameter leaves and sets the refresh flags, and the next
evaluation recomputes the values through the fixed maps and kernels. In comparison,
without parametric compilation \cite{agrawal2019dpp}, \texttt{CVXPY} traverses the
expression graph again, recomputes every sparsity pattern, and reallocates every buffer
each time a parameter changes. The difference is measured in Chapter~\ref{sec:Theme2}.

\section{Revisiting the limitations of matrix stuffing}\label{sec:theme1-limitations}

\S\ref{sec:matrix-stuffing} listed three implementation details that are shared by the
two stuffing backends of \texttt{CVXPY}. We now describe how the engine handles each of
them. % we should maybe say, instead of we now describe, we summarize or emphasize again
% how the engine is able to be better on these cases.

\emph{External sparse libraries.} We use no external sparse library. All kernels are
written by hand and specialized to structure that is known at canonicalization time, such
as the selection-block Jacobians of variables and the factored products of
\S\ref{sec:theme1-matrix-representations}. This made it possible to design the storage
formats and the kernels around canonicalized problems instead of around generality.

\emph{Everything is sparse.} Dense atom data enters the engine as a permuted dense block,
remains in a structured representation through every product
(Figure~\ref{fig:kernel-dispatch}), and is processed by level-3 BLAS. The generic sparse
type is only used for data that is actually sparse.

\emph{Quadratic objectives are separate.} No dummy variables are substituted and no
second stuffing pass is run. A quadratic form remains in the tree as an atom, and its
contribution to $P$ is computed by the Hessian oracle of \S\ref{sec:theme1-overview},
with the same init and value passes as everything else. A full description of the Hessian
machinery is outside the scope of this chapter.

\section{The API and the CVXPY interface}\label{sec:theme1-api}

The engine is distributed as a C library with a thin Python binding called
\texttt{sparsediffpy}, which exposes the node constructors. It is used in two places
inside \texttt{CVXPY}. The nonlinear programming interface wraps the bindings in a class
called \texttt{C\_problem}, which is built from the expression trees of a problem. The
canonicalization backend, which is the one measured in this thesis, is selected by
passing \texttt{ignore\_dpp=True}, and replaces the stuffed matrices of
\S\ref{sec:matrix-stuffing} with a cone program object that wraps the same
\texttt{C\_problem}. The code below is lightly condensed from the actual interface.

The lifecycle of a \texttt{C\_problem} mirrors the two phases of this chapter:
\begin{lstlisting}[language=Python]
prob = C_problem(problem)        # convert the tree, register parameters
prob.init_jacobian_coo()         # init phase: patterns, maps, buffers
rows, cols = prob.get_jacobian_sparsity_coo()  # structure, fetched once

prob.objective_forward(x)        # value phase, repeated per iterate
prob.constraint_forward(x)
grad = prob.gradient()
vals = prob.eval_jacobian_vals() # values aligned with (rows, cols)
\end{lstlisting}
The sparsity pattern is fetched once and does not change afterwards; the later calls
return value arrays that are aligned with it.

The canonicalization backend extracts the problem data, an objective
$\tfrac{1}{2}x^T P x + q^T x + d$ and constraints $Ax + b$ that must lie in a cone, by
evaluating the oracles at $x = 0$. The forward passes give $d$ and $b$, the gradient
gives $q$, and the Jacobian and Hessian values fill the fixed patterns of $A$ and $P$.
Parameter updates go through a single method:
\begin{lstlisting}[language=Python]
def apply_parameters(self, id_to_value):
    theta = flatten_and_concatenate(id_to_value)
    if theta == self.cached_theta:       # same values: reuse everything
        return self.P, self.q, self.d, self.A, self.b
    self.c_problem.update_params(theta)  # numeric phase only
    self.P, self.q, self.d, self.A, self.b = self.extract()  # at x = 0
    self.cached_theta = theta
    return self.P, self.q, self.d, self.A, self.b
\end{lstlisting}
Repeated solves with unchanged parameter values return the cached matrices; an actual
update costs one run of the value pass.

The caching follows the same pattern as in \S\ref{sec:theme1-reusing-work}. The
\texttt{C\_problem} and its sparsity structures live as long as the problem family, the
extracted matrices are kept until the parameter values change, and only numerical values
are recomputed. After construction, nothing in the Python layer traverses an expression
tree. Chapter~\ref{sec:Theme2} compares the engine with the systems reviewed in
Chapter~\ref{sec:RevLitt}.
