\Chapter{A LIGHTWEIGHT CANONICALIZATION ENGINE}\label{sec:Theme1}

Mathematically, \texttt{SparseDiffEngine} computes the same derivatives as
\texttt{CVXPY}'s canonicalization backends. Both apply the chain rule of matrix calculus
to trees of vectorized expressions, and both produce the Jacobian and the Hessian defined
in \S\ref{sec:bg-derivatives}. The differences are in the implementation.
Firstly, a custom sparse matrix data structure allows a natural split between the symbolic
and numeric phases described in \S\ref{sec:problem-statement}. This separation
is particularly useful for compiling problems involving parameters, where
the structure is fixed but the numerical values can change.
Secondly, the data of most optimization problems is not only sparse but also
structured, with dense blocks and diagonal patterns.
In \texttt{SparseDiffEngine} we introduce two new matrix classes for this purpose,
\texttt{permuted-dense} and \texttt{stacked-permuted-dense}, which let us use
dense storage and BLAS subroutines when possible.

Finally, some important design decisions differ from \texttt{CVXPY}'s backends for
simplicity rather than speed. Every node carries a single Jacobian whose columns span
all of the variables of the problem, rather than a dictionary of local Jacobians keyed by
variables. As a consequence, the chain rule is a single matrix product, and the
constraint matrix is built by stacking the Jacobians of the constraints.
In addition, quadratic functions have a dedicated Hessian pass, instead of the
variable substitution and second matrix stuffing pass of \S\ref{sec:matrix-stuffing}.

The rest of the chapter is organized as follows. We begin with a brief overview of
the engine, describing how expressions are represented and how the code is organized
(\S\ref{sec:theme1-overview}). We then present the matrix representations used for the
derivative computations (\S\ref{sec:theme1-matrix-representations}), where we focus much of
our attention on the \texttt{permuted-dense} matrix, which appears most often. Next we
describe the algorithms, or kernels, which operate on and combine these matrix
representations (\S\ref{sec:theme1-kernels}).
Finally, we show how \texttt{SparseDiffEngine} is used within \texttt{CVXPY} to obtain the
problem data (\S\ref{sec:theme1-api}).

\section{Overview of the engine}\label{sec:theme1-overview}

\texttt{SparseDiffEngine} is a small C library which is around seventeen thousand lines
of code (and a similar number of lines for the test suite).
The expression node is defined in \texttt{expr.h}; atoms that carry extra data, such as
the exponent of a power, define a larger structure in \texttt{subexpr.h}.
Each atom is implemented in its own file in the \texttt{atoms/}
directory; there are around forty-five of them, divided into six subdirectories based on their
mathematical properties.
The matrix data structures and the computational kernels that operate on them are in
\texttt{utils/}, and \texttt{problem.c} collects the objective and constraints of a
problem and evaluates the values and derivatives that a solver asks for.

\subsection{Atom classes}\label{sec:theme1-atom-classes}
Atoms in the same subdirectory compute their derivatives in the same way
(Table~\ref{tab:atom-classes}). Canonicalization leaves the constraints affine and the
objective affine or quadratic. The quadratic atoms of a DCP problem (a squared power, a
quadratic over a linear term, a Huber penalty) are all rewritten as quadratic forms by the
canonicalization frontend (\S\ref{sec:matrix-stuffing}), so only affine atoms and quadratic
forms reach the engine from a canonicalized DCP problem.
This chapter describes the affine atoms. The quadratic form contributes the
objective matrix~$\mmat{P}$ through the Hessian (\S\ref{sec:theme1-api}). The remaining
classes are used by the nonlinear programming (\acs{NLP}) interface of
\texttt{CVXPY} \cite{cederberg2025disciplined}.\acused{NLP}

Each atom implements three operations: a forward pass, which evaluates the atom at
a point; a symbolic pass, which computes the sparsity patterns of its derivatives
and allocates memory for them; and a numeric pass, which computes the numerical
values inside the fixed sparsity patterns. The constructor of the atom
stores pointers to these three functions in the expression node.

\subsection{The expression node}\label{sec:theme1-expression-node}
An expression node stores its dimensions, pointers to at most two children, a buffer for
its value, and its derivative matrices. Every derivative matrix has \texttt{n\_vars}
columns, the total number of entries of all the variables of the problem.
A simplified version of the definition in \texttt{expr.h} is shown below.
\begin{lstlisting}[language=C]
typedef struct expr
{
    int d1, d2, size, n_vars, refcount, var_id;
    struct expr *left;
    struct expr *right;

    double *value;     /* forward value                */
    matrix *jacobian;  /* Jacobian w.r.t. the variables */

    forward_fn        forward;
    jacobian_init_fn  jacobian_init_impl;  /* symbolic pass */
    eval_jacobian_fn  eval_jacobian;       /* numeric pass  */
} expr;
\end{lstlisting}
Trees are built bottom up, with one constructor function per atom. A \texttt{CVXPY} expression
is converted in one pass over the tree, which calls the constructor of the corresponding atom
at each node (\S\ref{sec:theme1-api}). Expressions that appear multiple times can be shared, in
which case the tree becomes a directed acyclic graph. Nodes are therefore reference
counted, and the symbolic pass returns early if a node was already initialized.

There are two leaf nodes, variables and parameters. A variable occupies a
contiguous slice of the global variable vector, starting at the column offset
\texttt{var\_id}. Its Jacobian is an identity block at the columns of the variable, written
once during the symbolic pass. Unlike \texttt{CVXPY}, constants are parameters that cannot be
updated. The Jacobian of a parameter is empty, because parameters are fixed during a solve.

\section{Matrix representations}\label{sec:theme1-matrix-representations}
The Jacobian of a node is stored in whichever representation matches its structure. The
default is a generic sparse matrix in the CSR format of \S\ref{sec:bg-sparse}, which makes
no assumption about where the nonzeros are. Problem data is often dense in a small block,
and the engine adds two representations that keep such blocks dense so that products on
them go to level-3 BLAS. Each representation implements the same operations, so an atom
picks one when it allocates its Jacobian during the symbolic pass, and every later
operation is dispatched to the representations involved.

\subsection{The permuted dense matrix}\label{sec:theme1-permuted-dense}

The Jacobians that appear during canonicalization are usually not sparse in the sense of
having scattered, isolated nonzeros. Multiplication by problem data places the data
itself, or a product involving it, as a dense block at a subset of the rows and columns
of the Jacobian. Consider the expression~$\mmat{B}\mvec{x}$ with dense
data~$\mmat{B} \in \reals^{50 \times 50}$, in a problem with ten thousand variables. Its Jacobian
with respect to the full variable vector is a matrix with ten thousand columns that
contains $\mmat{B}$ in the fifty columns of $\mvec{x}$ and is zero everywhere else
(Figure~\ref{fig:pd-motivation}). In the generic sparse format that block costs a column
index for each of its twenty-five hundred entries, and every later product involving it
runs through the sparse loop instead of a BLAS call.

Mixing dense blocks into sparse storage appears in several settings. Supernodal and
multifrontal solvers gather dense submatrices of a sparse factor and process them with
level-3 BLAS \cite{duff1983multifrontal, demmel1999supernodal}; see also the survey
\cite{liu1992multifrontal}. Blocked sparse formats and autotuned kernels exploit small
dense blocks found in the matrix \cite{im2004sparsity, vuduc2005oski}. In these systems the
blocks are discovered in the data; here they are known from canonicalization, which is what
makes it possible to keep them in a dedicated representation from the start.

A \emph{permuted dense} matrix stores such a Jacobian in \emph{factored form}, as the dense
block together with the index vectors that place it, and the global matrix is never
assembled. It is a triple~$(\mmat{X}, \mvec{r}, \mvec{c})$,
where $\mmat{X} \in \reals^{m_0 \times n_0}$ is a
dense block and $\mvec{r}$ and
$\mvec{c}$ are strictly increasing index vectors, representing
\BEQ\label{eq:permuted-dense}
  \mmat{A} = \mmat{S}_r^\top \mmat{X} \mmat{S}_c \in \reals^{m \times n},
  \qquad A_{r_i,\, c_j} = X_{ij},
\EEQ
where $\mmat{S}_r \in \{0,1\}^{m_0 \times m}$ and $\mmat{S}_c \in \{0,1\}^{n_0 \times n}$ are
the selector
matrices whose rows are the rows of the identity indexed by $\mvec{r}$ and $\mvec{c}$.
Multiplying a
vector by $\mmat{S}_r$ selects the entries indexed by $\mvec{r}$, and multiplying by
$\mmat{S}_r^\top$ scatters
them back into a vector of length~$m$, with zeros elsewhere. All other entries of
$\mmat{A}$ are structurally zero and never stored. Figure~\ref{fig:permuted-dense} shows an
example with a $3 \times 3$ block inside a $6 \times 7$ matrix, and
Figure~\ref{fig:selector-matrices} writes out the two selectors of that example.

The block~$\mmat{X}$ is stored contiguously in row-major order and the index vectors as two
integer arrays, so the storage does not depend on the global dimensions~$m$ and~$n$. Two
inverse maps send a global row or column index to its position in the block, or to $-1$
when the index is not in the block, which makes a membership test constant time. Every
kernel below determines the shape of its result from these integer arrays alone, and does
its floating point work on the dense block.

Transposition and the structural atoms turn a permuted dense matrix into another permuted
dense matrix. Transposition swaps the two index vectors and transposes the block. Indexing,
broadcasting, and the row partitions of \texttt{sum} work the same
way: because row~$r_i$ of~$\mmat{A}$ is row~$i$ of~$\mmat{X}$ and every other row is zero, an
operation
on the rows of~$\mmat{A}$ reduces to the same operation on the rows of~$\mmat{X}$, guided by the
inverse row map.

Figure~\ref{fig:permuted-dense-index} traces the indexing of rows~$(3,0,4)$ of the
matrix in Figure~\ref{fig:permuted-dense}. A repeated index in the request would copy the
same block row twice. Rows outside~$\mvec{r}$ are requested whenever an earlier atom
widened the row space: \texttt{diag} places the $n$ rows of the Jacobian of its argument at
the diagonal positions of a matrix with $n^2$ rows, so all but $n$ of them are structurally
zero, and an indexing or a sum applied downstream reads them through the inverse row map.

The product of two permuted dense matrices is again permuted dense. The Jacobian of
\texttt{left\_matmul} is the product~$\mmat{B}\mmat{A}$ of its data block with the Jacobian
of its argument, and the Hessian of the quadratic form accumulates
$\mmat{B}^\top \mmat{D} \mmat{A}$ with a diagonal weight~$\mmat{D}$. The transposed form
factors as
\BEQ\label{eq:pd-product}
\mmat{B}^\top \mmat{A}
= \mmat{S}_{c_B}^\top \mmat{X}_B^\top
  \underbrace{\left(\mmat{S}_{r_B} \mmat{S}_{r_A}^\top\right)}_{\text{index-set intersection}}
  \mmat{X}_A \mmat{S}_{c_A},
\EEQ
and $\mmat{B}\mmat{A}$ factors the same way, with $\mvec{c}_B$ in place of $\mvec{r}_B$ in
the middle factor and as the row vector of the result.
The middle factor is a zero-one matrix whose entry~$(k, l)$ is one exactly when the two
indices agree, so the sparsity analysis of the product amounts to intersecting two
sorted integer arrays. The result has column vector~$\mvec{c}_A$ and a row vector that is
known before any numerical values exist. For the values there are three cases. If the two
index sets are equal, the product is computed on the two blocks with a single call to
\texttt{dgemm}, the double precision general matrix--matrix product of level-3 BLAS
(\S\ref{sec:bg-blas}). If they overlap partially, the matching rows are first gathered
into a workspace (allocated during the symbolic pass),
followed by the same \texttt{dgemm}. If they are
disjoint, the product is zero, and nothing is computed in the numeric pass.

Two dense operands require a chain of products such as~$\mmat{A}(\mmat{B}\mvec{x})$, because
the Jacobian of a variable leaf is a generic sparse selection matrix. On the Hessian side
they require a quadratic form of a composite argument,
$(\mmat{A}\mvec{x})^\top \mmat{Q} \mmat{A}\mvec{x}$; a quadratic form of a bare variable has
Hessian~$2\mmat{Q}$ and is written out with no product at all.

In the factored form \eqref{eq:permuted-dense}, the numeric pass of each kernel is a few
BLAS calls on the dense block.
The product~$\mmat{A}^\top \mmat{D} \mmat{A}$, for example, is computed with one copy, $m_0$
scalings, and one
\texttt{dgemm}, and the cost does not depend on the global dimensions.

The gain is limited by what the representation can hold. A permuted dense matrix has
nonzeros only inside its block, so a Jacobian that mixes a dense block with scattered
entries falls back to the default CSR representation. This happens on every addition. The
Jacobian of~$\mmat{A}\mvec{x} + \mvec{y}$ carries the block of~$\mmat{A}$ at the columns
of~$\mvec{x}$ and an identity at the columns of~$\mvec{y}$, which no single block covers,
so the sum is performed on CSR views of its operands. The view itself is cheap, because its
value array points into the dense block and it is built once during the symbolic pass, but
its result is a generic sparse matrix, and the dense kernels no longer apply to it or to
anything computed from it. The remaining risk is dense data that contains many zeros, which
would be stored and multiplied densely, spending floating point work on zeros. Because
\texttt{CVXPY} supplies sparse data in sparse formats, this does not arise in practice.

\subsection{The stacked permuted dense matrix}\label{sec:theme1-stacked-pd}

Multiplying an $n \times p$ expression by data~$\mmat{A} \in \reals^{m \times n}$ acts on the
vectorized expression as the block diagonal operator of Table~\ref{tab:views-copies}, one
copy of~$\mmat{A}$ per column of the operand; this is the \texttt{left\_matmul} atom. Rather
than form that operator, the atom keeps a single copy of~$\mmat{A}$ and applies it block by
block. In memory, the $p$ segments of length~$n$ of a vector~$\mvec{x}$ form a
$p \times n$ row-major matrix~$\tilde{\mmat{X}}$, and by a standard vectorization
identity \cite{magnus2019matrix},
\BEQ\label{eq:kron-reshape}
  \mvec{y} = (\mmat{I}_p \otimes \mmat{A})\, \mvec{x}
  \quad\Longleftrightarrow\quad
  \tilde{\mmat{Y}} = \tilde{\mmat{X}} \mmat{A}^\top,
\EEQ
so applying the operator to a vector is a single \texttt{dgemm} on the stored~$\mmat{A}$, and
the storage does not grow with the number of blocks~$p$.

Storing the Jacobian of the atom is a separate problem. The parent node
receives $(\mmat{I}_p \otimes \mmat{A})\, \mmat{J}$, where $\mmat{J}$ is the Jacobian of the
child, and transposes,
indexes, and multiplies it like any other Jacobian. This matrix is made of $p$ dense
blocks at disjoint rows, one per column of the operand, and each block generally sits at
its own global columns, so no single triple~$(\mmat{X}, \mvec{r}, \mvec{c})$ describes it.
Merging the blocks
into one larger triple would store the full block diagonal, $p$ copies of~$\mmat{A}$ separated
by blocks of zeros, and falling back to generic sparse would lose the dense kernels. We
instead keep the blocks as they are, in a third representation.

A \emph{stacked permuted dense} matrix is a vertical union of permuted dense blocks
whose row vectors are pairwise disjoint; the column vectors may overlap. The blocks share
one value buffer. Every kernel treats the blocks one at a time. Structural atoms rewrite
the index vectors of each block, and products distribute over the blocks, with one
\texttt{dgemm} for each pair of blocks with intersecting row sets and nothing at all for
the pairs with disjoint row sets, as in \eqref{eq:pd-product}. The assembled matrix is
never allocated or traversed, and each stacked kernel is a short loop over the
corresponding permuted dense kernel. Figure~\ref{fig:stacked-pd} shows the Jacobian
of~$\mmat{A}\mmat{X}$ for a variable~$\mmat{X}$ with two columns: one block per column
of~$\mmat{X}$, each a copy of~$\mmat{A}$
at its own rows and columns.

\label{fig:stacked-pd}
\end{figure}

Generic sparse, permuted dense, and stacked permuted dense are the only three matrix
representations in the engine. Generic sparse is the default, produced by the variable
leaves and by every atom that does not hold dense data. The other two are created by
\texttt{left\_matmul} and the quadratic form, the two atoms that hold dense data, and
propagate from there through the structural atoms and the chain rule.

\section{Computational kernels}\label{sec:theme1-kernels}
A \emph{kernel} is an operation on one or two of the matrix representations of
\S\ref{sec:theme1-matrix-representations}. There is one kernel per operation and
representation rather than one per atom. Transposition, row indexing, broadcasting, row
partition sums, and the two products of \S\ref{sec:theme1-permuted-dense} cover every atom
in the library.
Each kernel is a pair of functions, one called by the symbolic pass, which determines the
structure of the result and reserves its memory, and one called by the numeric pass, which
writes values into that fixed structure.

\subsection{Kernel dispatch}\label{sec:theme1-kernel-dispatch}

Unary operations are dispatched on the representation of their single
operand, and so is~$\mmat{B}\mmat{A}$, whose left operand is always the data block of an
atom. The transposed products~$\mmat{B}^\top \mmat{A}$
and~$\mmat{B}^\top \mmat{D} \mmat{A}$
depend on the representations of
both operands, which a single table cannot express. They are instead resolved with double
dispatch. A dispatch function switches on the type tags of~$\mmat{B}$ and then of~$\mmat{A}$,
and calls
one of nine kernels.
Figure~\ref{fig:kernel-dispatch} shows the representation of the result for the nine
combinations of operand types.

\subsection{Reusing work across passes}\label{sec:theme1-reusing-work}

The Jacobian of an affine atom does not depend on~$\mvec{x}$. For the structural atoms, such
as indexing, transposition, reshaping, stacking, and summation, it is determined by shapes
and index sets alone. The remaining affine atoms, such as \texttt{left\_matmul},
\texttt{scalar\_mult}, \texttt{convolve}, and \texttt{kron}, place problem data in the
Jacobian, whose values only change when a parameter update sets their refresh flag.

The numeric pass never allocates memory; every buffer, including the scratch space of the
kernels, is allocated during the symbolic pass. Beyond allocation, several other kinds of
work are done only once. Sparsity patterns are computed symbolically: \texttt{add} merges the
patterns of its children with a sorted merge, the sparse products run the symbolic phase
of Gustavson's algorithm \cite{bank1993smmp}, and the factored products of
\S\ref{sec:theme1-matrix-representations} determine their output index vectors before any
values exist. Index maps are also precomputed. Transposition stores its row permutation,
\texttt{kron} its per-row copy maps, and \texttt{sum} the map from child nonzeros to
output entries, so the numeric pass performs no index arithmetic. When the index vectors
of two operands do not intersect, the product is recorded as empty during the symbolic
pass, and its numeric pass does nothing. Finally, values that cannot change are written
once; the Jacobian of a variable, for example, is filled during the symbolic pass and
never touched again.

Figure~\ref{fig:sum-idx-map} illustrates this for the \texttt{sum} atom. During the
symbolic pass, the representation of the child allocates the output and fills
\texttt{idx\_map}, an array
that maps each nonzero of the child Jacobian to the output entry it is added to. The axis
convention and all other index decisions are handled at this point. The numeric pass is a
single loop, the same for every axis and every representation. Indexing, transposition,
and \texttt{kron} work the same way, with a copy instead of an addition.

\subsection{Problem assembly and parameter updates}\label{sec:theme1-problem-assembly}

The same split between structure and values is applied at the problem level. The solver
receives one global CSR matrix, formed by
concatenating the constraint Jacobians, whose layout is fixed during the symbolic pass;
an evaluation only copies the values of each constraint root into this matrix at a fixed
offset. Affine constraints are skipped entirely after the first evaluation, because their
values cannot change until the parameters do.

A parameter update only involves the numeric pass. The function
\texttt{update\_params} writes
the new values into the parameter leaves and sets a refresh flag on each affected
subtree, and the next
evaluation recomputes the values through the fixed maps and kernels. On the
\texttt{ignore\_dpp} path of \S\ref{sec:ms-parameters}, \texttt{CVXPY} instead repeats the
whole matrix stuffing pass, recomputing every sparsity pattern and reallocating every
buffer, each time a parameter changes. The difference is measured in
Chapter~\ref{sec:Theme2}.

\section{From \texttt{CVXPY} to the engine}\label{sec:theme1-api}

The engine is a C library, and \texttt{sparsediffpy} is the Python extension module that
exposes it. The module is written against the C interfaces of \texttt{Python} and
\texttt{NumPy}. It declares one function per atom constructor, together with the
problem-level entry points, and each of these functions reads its arguments, calls the
corresponding C function, and returns an opaque handle to the node it created. Three
thousand lines of binding code cover the seventeen thousand lines of the engine, and none of
them mention \texttt{CVXPY}.

Everything specific to \texttt{CVXPY} is on the other side, in a converter that turns a
canonicalized problem into an engine graph. The converter is used on two paths. The
nonlinear programming interface \cite{cederberg2025disciplined} builds a graph from the
smooth reformulation of a problem. The canonicalization backend, named \texttt{diffengine}
and measured in
Chapter~\ref{sec:Theme2}, builds a graph from the conic form and extracts the problem data
from it, in place of the matrix stuffing pass of \S\ref{sec:matrix-stuffing}. It is selected
by passing \texttt{ignore\_dpp=True} to \texttt{CVXPY}. The two paths build the graph in the
same way, and differ in what they ask of it.

The conversion is a single pass over the tree. At a node, the children are converted first,
and the name of the atom then selects the engine constructor to call on the resulting
handles. That dispatch is a table with about fifty entries, one for each atom of
\texttt{CVXPY} that the engine implements. The following listing is condensed from the
converter.
\begin{lstlisting}[language=Python]
def convert(expr, var_dict, param_dict, n_vars):
    if isinstance(expr, cp.Variable):     # leaves are looked up,
        return var_dict[expr.id]          # never rebuilt
    if isinstance(expr, cp.Parameter):
        return param_dict[expr.id]
    if isinstance(expr, cp.Constant):     # a constant is a parameter
        d1, d2 = shape_2d(expr.shape)     # with the reserved offset -1
        return engine.make_parameter(d1, d2, -1, n_vars, dense(expr.value))

    children = [convert(arg, var_dict, param_dict, n_vars)
                for arg in expr.args]
    return ATOM_CONVERTERS[type(expr).__name__](expr, children)

ATOM_CONVERTERS = {
    "AddExpression": lambda expr, children: chain_add(children),
    "MulExpression": convert_matmul,
    "index":         convert_index,
    "QuadForm":      convert_quad_form,
    "exp":           lambda expr, children: engine.make_exp(children[0]),
}
\end{lstlisting}
Two checks are left out of the listing. Every constructor reports the dimensions of the node
it created, which are compared against the shape that \texttt{CVXPY} assigned to the
expression. A subtree that contains neither a variable nor a parameter is evaluated once and
folded into a single constant leaf, because canonicalization leaves such subtrees in place.

The two leaf dictionaries are built before the pass, from the inverse data that
\texttt{CVXPY} produces when it stacks the variables of the problem. A variable leaf is
created with its column offset in the stacked variable vector, the offsets of
Figure~\ref{fig:column-offsets}, and the engine uses that offset directly as the first
column of the selection Jacobian of \S\ref{sec:theme1-expression-node}. A parameter leaf is
created with its offset in the flattened parameter vector~$\gvec{\theta}$, which is where
\texttt{update\_params} reads its new values. Because the dictionaries are built once and
looked up by identity, every occurrence of a variable converts to the same node, and the
trees of the objective and of the constraints become the single graph of
\S\ref{sec:theme1-expression-node}.

The conversion is also where the representations of
\S\ref{sec:theme1-matrix-representations} are chosen. A multiplication by problem data is
converted by looking at which operand is constant and at how that operand is stored. Sparse
data is passed as a CSR triple, dense data as a dense block, and a dense array whose entries
are mostly zeros is passed as a CSR triple as well, after its nonzeros have been counted.
The dense block is what the atom later places in a permuted dense Jacobian. A sum of several
terms is converted to a balanced tree of binary additions, so the depth of the graph grows
with the logarithm of the number of terms.

The objective converts to one root, and each constraint contributes one root per argument,
in the order in which \texttt{CVXPY} groups the cones: zero, nonnegative, second-order,
semidefinite, exponential, and power. That order fixes the row blocks of the constraint
Jacobian assembled in \S\ref{sec:theme1-problem-assembly}. The engine has no notion of a
cone. It receives an objective root and an array of constraint roots, and the cone that each
block of rows belongs to is recorded on the \texttt{CVXPY} side.
Figure~\ref{fig:cvxpy-conversion} shows the graph and the roots of the running example.

A solver reaches the graph through an oracle interface.
\begin{lstlisting}[language=Python]
rows, cols = oracles.jacobianstructure()  # once, fixed afterwards
f    = oracles.objective(x)     # at each iterate
h    = oracles.constraints(x)
grad = oracles.gradient(x)      # reuses the cached forward values
vals = oracles.jacobian(x)      # aligned with (rows, cols)
\end{lstlisting}
The pattern is determined when the graph is built, and every later call returns a value array
aligned with it. Within an iterate, the forward values are computed by the first two calls
and reused by the other two, so the gradient and the Jacobian perform no forward pass of
their own. The Hessian of the Lagrangian is queried in the same way, with one call for its
pattern and one for its values.

The canonicalization backend asks the same questions exactly once, and at the origin. Write
$f_0$ for the
converted objective and $\mvec{h}$ for the stack of converted constraint roots. After
canonicalization $\mvec{h}$ is affine and $f_0$ is affine or quadratic, so
\BEQ\label{eq:extract-at-zero}
  d = f_0(\mvec{0}), \qquad
  \mvec{c} = \nabla f_0(\mvec{0}), \qquad
  \mmat{P} = \nabla^2 f_0, \qquad
  \mvec{b} = \mvec{h}(\mvec{0}), \qquad
  \mmat{A} = \nabla \mvec{h}(\mvec{0}),
\EEQ
which is the problem data of \eqref{e:quad-conic-form}. These are the matrices that
Figure~\ref{fig:matrix-stuffing} assembles by matrix stuffing, obtained instead as the
derivatives of \S\ref{sec:bg-derivatives}, and \eqref{eq:extract-at-zero} is the identity
that the \texttt{CasADi} listing of \S\ref{sec:casadi} writes with \texttt{jacobian} and
\texttt{substitute}. The sign convention of the cone form and the reordering of the rows
inside each cone are applied afterwards, by the step that formats the constraints for the
other backends as well. The sparsity patterns of~$\mmat{A}$ and~$\mmat{P}$ are read once,
when the graph is built, and every later evaluation returns value arrays aligned with them.

New parameter values go through one method.
\begin{lstlisting}[language=Python]
def apply_parameters(self, id_to_value):
    theta = flatten_and_concatenate(id_to_value)
    if np.array_equal(theta, self.extracted_theta):  # unchanged values:
        return self.P, self.c, self.d, self.A, self.b  # reuse everything
    self.extractor.update_parameters(theta)          # numeric pass only
    self.c, self.d, self.A, self.b, self.P = self.extractor.extract()
    self.extracted_theta = theta
    return self.P, self.c, self.d, self.A, self.b
\end{lstlisting}
Repeated solves at unchanged parameter values return the cached matrices. An actual update
costs one numeric pass over the graph and one evaluation of
\eqref{eq:extract-at-zero}, while the graph, its sparsity patterns and its buffers are built
once and live as long as the problem family.
Chapter~\ref{sec:Theme2} measures what this is worth against \texttt{CVXPY}'s
canonicalization backends, implementations of the matrix-stuffing approach reviewed in
Chapter~\ref{sec:RevLitt}.
