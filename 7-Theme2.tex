\Chapter{RESULTS}\label{sec:Theme2}

This chapter compares \texttt{diffengine}, the canonicalization backend we built in
Chapter~\ref{sec:Theme1} using \texttt{SparseDiffEngine}, against \texttt{CVXPY}'s three
existing backends. The three are the
default \texttt{cvxcore}, which we refer to as \texttt{CPP}, and the two Python
backends \texttt{SCIPY} and \texttt{COO}, all described in \S\ref{sec:matrix-stuffing}.
Two questions motivate these comparisons.
First, we want to evaluate the relative benefit of our proposed symbolic and numeric split
against the parameter-to-data tensor. Both approaches store results of the first
canonicalization so that subsequent parameter updates are cheap.
If the split matches the tensor's re-solve
times at a lower upfront cost, building the tensor becomes harder to justify.
Second, the \texttt{CVXPY} developers have deprecated \texttt{cvxcore} and plan
to remove it from the library~\cite{zhang2026cvxpy}. It nevertheless remains the default
backend, in part because neither Python backend has shown a decisive speedup on the first
canonicalization. These comparisons allow us to assess whether
\texttt{diffengine} could be a suitable replacement.

We use the $25$ problems of \texttt{CVXPY}'s public benchmark suite
\cite{cvxpybenchmarks}. The suite includes problems from portfolio selection, regression
and classification, image inpainting, and many more applications in convex optimization.
On parametric problems, canonicalization follows either
the \ac{DPP} path or the \texttt{ignore\_dpp} path, both described in
\S\ref{sec:ms-parameters}. We conduct numerical experiments on both. \S\ref{sec:bench-oneshot}
compares the first
canonicalization time of all $25$ problems on the \texttt{ignore\_dpp} path.
\S\ref{sec:bench-param} compares the parameter-to-data tensor against the symbolic and
numeric split on the seven \ac{DPP} parametric problems of the suite.

All measurements run single-threaded on a 2018 MacBook
Pro with a 6-core Intel Core i7-8850H and \SI{16}{\giga\byte} of memory. \texttt{CVXPY}'s
backends run on the released
version 1.9.2. The \texttt{diffengine} backend is in a separate branch,
available as a pull request:
\begin{center}
  \url{https://github.com/cvxpy/cvxpy/pull/3448}
\end{center}
Each measurement runs \texttt{get\_problem\_data} once with
\texttt{Clarabel}~\cite{clarabel} as the target solver, under a time limit of 20
minutes. The method canonicalizes the
problem and returns the resulting problem data without calling the solver. We exclude the
solver because the choice of backend affects only canonicalization.
The benchmark scripts and all recorded timings are available at
\begin{center}
  \url{https://github.com/SparseDifferentiation/Jacobian-accumulation}

\section{First canonicalization}
\label{sec:bench-oneshot}

Table~\ref{tab:oneshot-compile} summarizes the results. \texttt{diffengine} is the
fastest of the four backends on $21$ of the $25$ problems, with a geometric-mean ratio of
$0.36$, and on $17$ problems it is more than twice as fast as the best
\texttt{CVXPY} backend. It is slower on CVaR and OptimalAdvertising, where the times are
similar. On SDPSegfault1132 and
ConvexPlasticity, processing dense constant data dominates \texttt{diffengine}'s
canonicalization time.

Figure~\ref{fig:profiles}a reports the Dolan--Mor\'e performance profile
\cite{dolan2002} of the canonicalization times. A performance profile compares the backends
over the whole suite at once. We define $t_{p,s}$ as the time of backend $s$ on
problem $p$. The profile of backend $s$ is the fraction of the $n$ problems on which it
is within a factor $\tau$ of the fastest backend,
\BEQ\label{eq:perf-profile}
f_s(\tau) = \frac{1}{n}\,\bigl|\{\, p : t_{p,s} \le \tau \, \textstyle\min_b t_{p,b}
\,\}\bigr|.
\EEQ
The minimum $\min_b t_{p,b}$ is the time of the fastest backend on problem~$p$.
The value at $\tau = 1$ is the fraction of
problems on which the backend is the fastest, and the curve reaches $1$ at the factor the
backend needs to cover every problem. \texttt{diffengine} is within $3\times$ of
the best backend on every problem. No \texttt{CVXPY} backend is fastest on more than two problems,
and each needs $\tau \approx 8$ to cover $92$--$96\%$ of the problems.

Figure~\ref{fig:profiles}b reports the same profile for peak memory,
with $t_{p,s}$ replaced by the growth of the process's peak resident memory during
canonicalization. \texttt{SCIPY} has the lowest peak memory on
$16$ of the $25$ problems. \texttt{diffengine}
matches \texttt{CPP} and \texttt{COO} in geometric mean and uses about $1.4\times$ the memory
of \texttt{SCIPY}.

\section{Parametric canonicalization}
\label{sec:bench-param}

Table~\ref{tab:param-tensor} reports first canonicalization and re-solve times on the
seven \ac{DPP} parametric problems. We refer to a re-solve in this context as rebuilding the
problem data after a parameter update, so the reported times again exclude the solver.
On the first
canonicalization, each \texttt{CVXPY} backend runs the \ac{DPP} path and builds a
parameter-to-data tensor. \texttt{diffengine} instead runs its symbolic pass and one
numeric pass. It has the fastest first canonicalization on every problem, and among
the \texttt{CVXPY} backends only \texttt{COO} is able to build the tensor on all seven. On a
parameter update, the three \texttt{CVXPY} backends re-solve by applying the cached
tensor, so the tensor column is common to all three. \texttt{diffengine} instead
runs another numeric pass.

update nevertheless forces the
numeric pass to recompute the entire constant part, which can be costly.

\section{Discussion}
\label{sec:bench-summary}

The benchmark experiments in this chapter lead us to make the following three observations:
\begin{itemize}
\item Caching canonicalization does not necessarily require the \ac{DPP} ruleset. In
Table~\ref{tab:param-tensor}, the symbolic and numeric split re-solves within a factor of
about two of the cached tensor on every problem while ignoring the ruleset.
\item The tensor approach carries a large upfront cost that is not always justified. In
Table~\ref{tab:param-tensor}, the split's first canonicalization is faster than building
the tensor on every problem, and its re-solve is also faster on five of the seven
problems.
\item \texttt{cvxcore} can be replaced. \texttt{diffengine} canonicalizes faster on $24$ of
the $25$ problems, as reported in Table~\ref{tab:oneshot-compile} and
Figure~\ref{fig:profiles}. On the parametric problems of Table~\ref{tab:param-tensor},
\texttt{COO} builds the parameter-to-data tensor faster than \texttt{cvxcore} on all seven.
\end{itemize}

Traditionally, \texttt{CVXPY} has relied on \ac{DPP} to guarantee a meaningful
speedup between the first and subsequent canonicalizations of a parametric problem.
If a problem does not conform to the \ac{DPP} grammar, users have to either attempt
one of many possible reformulations or accept that every subsequent canonicalization
will cost the same as the first. In addition, even if the problem conforms to the grammar,
forming the tensor is sometimes prohibitive, especially for large-scale problems.
Our first two observations challenge this tradition and suggest that \ac{DPP} should be
used more carefully, for problems that are re-solved enough times or for applications
built on downstream packages that depend on the tensor, for example
\texttt{CVXPYgen}~\cite{schaller2022cvxpygen} and \texttt{CVXPYlayers}~\cite{agrawal2019dpp}.
With our approach, a similar speedup can be obtained through the symbolic and numeric split
without enforcing any rules about how parameters appear in the problem formulation.

In addition, the second and third observations suggest that \texttt{diffengine} can 
replace \texttt{cvxcore} as the default backend of \texttt{CVXPY}.
Canonicalization is faster on nearly
every benchmark problem, on both the first and subsequent canonicalizations, so there is
little reason to use \texttt{cvxcore} in the future.
Making this change will require substantial work and coordination with the
maintainers of \texttt{CVXPY}. We discuss these
next steps and the roadmap of future work in \S\ref{sec:FutureResearch}.
Finally, \texttt{diffengine} has downsides. Its peak
memory is higher on several problems, and its re-solve requires the cached program to stay in
memory. The benchmark suite also covers only a subset of possible optimization problems, and
more experiments would be needed to validate these observations further. We return to these
limitations in \S\ref{sec:Limitations}.
