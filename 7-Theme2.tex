\Chapter{Benchmark results}\label{sec:Theme2}

This chapter evaluates the C engine on the problems CVXPY users actually compile. We measure
canonicalization end to end---from a built expression tree to solver-ready problem data---in the
two regimes that matter in practice: the cold, single compilation of a fresh problem, and the warm
re-compilation of a parametrized problem whose parameter values change between solves. The engine
is compared against CVXPY's default \texttt{cvxcore} backend in both regimes
(\S\ref{sec:bench-cpp-single}, \S\ref{sec:bench-cpp-param}), and, in the same two regimes,
against CasADi, which obtains the same problem data by algorithmic differentiation of a symbolic
graph (\S\ref{sec:bench-casadi}).


\section{Benchmark Setup}

We benchmark on the public CVXPY benchmark suite~\cite{cvxpybenchmarks}, $25$ real-world problems
(linear and quadratic programs, least squares, portfolio models, robust regression, and conic and
semidefinite programs) maintained under \emph{airspeed velocity} (\texttt{asv})~\cite{asv} with
seeded, reproducible data. All $25$ problems run on both backends; three of them exercise the
\texttt{kron} atom, whose support the engine gained late in this work.

We time \emph{canonicalization} only---the construction of the problem data $(A,b,c,P)$. Concretely
we time \texttt{get\_problem\_data} with the target solver fixed to Clarabel~\cite{clarabel}: the
\texttt{CPP} (\texttt{cvxcore}) baseline is the default DPP path, and the C engine is selected with
\texttt{ignore\_dpp}.
\begin{lstlisting}[language=Python]
prob.get_problem_data(solver=cp.CLARABEL)                   # CPP baseline (DPP tensor)
prob.get_problem_data(solver=cp.CLARABEL, ignore_dpp=True)  # our C engine
\end{lstlisting}

All measurements run single-threaded (BLAS thread pools pinned to one thread) on a MacBook Pro
(15-inch, 2018): 6-core Intel Core i7-8850H at \SI{2.6}{\giga\hertz}, \SI{16}{\giga\byte} RAM,
macOS~15.7, with Python~3.14, CVXPY~1.10 (dev), NumPy~2.4~\cite{numpy}, and
SciPy~1.17~\cite{2020SciPy-NMeth}; the CasADi comparison uses CasADi~3.7.2~\cite{andersson2019}.
Reported times are medians of three fresh compilations (twenty re-evaluations for the re-solve
columns). Versions are pinned and the suite and engine are public, so the configuration is
reproducible.\footnote{The complete harness, per-problem CasADi models, mechanism probes, and raw
result files are published at
\url{https://github.com/SparseDifferentiation/Jacobian-accumulation} (directory
\texttt{canonicalization/}).}

We report three comparisons: single-solve compilation against \texttt{cvxcore}
(\S\ref{sec:bench-cpp-single}), parametric compilation against \texttt{cvxcore} across the first
solve and re-solves (\S\ref{sec:bench-cpp-param}), and both regimes against CasADi
(\S\ref{sec:bench-casadi}). In every table the ratio is $\text{C engine}/\text{baseline}$; a value
below $1$ favors the engine, and the final row is the geometric mean of the per-problem ratios.

The engine wins the re-solve on six of the eight parametric problems and the first solve on all
but \textsc{ConvexPlasticity}. Because the engine's program is cached, a re-solve only re-evaluates
the parameter-dependent coefficient entries; the DPP baseline instead multiplies its cached
parameter tensor by the new parameter vector, which is hard to beat when that tensor is small and
dense. The two rows where DPP retains a $\approx 2\times$ edge share one trait: a scalar parameter
whose effect is spread across many coefficients (\textsc{SVM}'s regularization weight,
\textsc{FactorCovariance}'s risk aversion multiplying the quadratic), the ideal case for the
tensor product and the worst case for entry-wise re-evaluation.

\section{Comparison against CasADi}
\label{sec:bench-casadi}
CasADi~\cite{andersson2019} extracts problem data by algorithmic differentiation of a symbolic
expression graph. Since CasADi has no notion of disciplined convex programming, it cannot
canonicalize the high-level models; for a fair comparison we hand it the \emph{already-lowered}
formulation: the same epigraph variables and the same conic rows that CVXPY's canonicalization
produces, written as CasADi \texttt{MX} expressions $f(z, \theta)$ (objective) and
$g(z, \theta) = b - Az$ (constraint slacks), where $z$ stacks the original and epigraph variables
and $\theta$ collects the parameters. The problem data are recovered exactly the way CasADi's own
quadratic-programming interface does, by differentiating the graph with no solver involved:
$c = \nabla_z f|_{z=0}$, $P = \partial(\nabla_z f)/\partial z$, $A = -\partial g/\partial z$, and
$b = g|_{z=0}$, wrapped in a \texttt{casadi.Function} mapping $\theta \mapsto (P, c, A, b)$;
$P$ is computed as the Jacobian of the gradient, CasADi's fastest path on these problems. The
\emph{single} regime times differentiation, function construction, and the first numeric
evaluation on a freshly built graph; the \emph{re-solve} regime times one further evaluation at
fresh parameter values on the compiled function. Graph construction itself is excluded, mirroring
the engine's timing, which also starts from a built expression tree. We verified on every
benchmark that the two systems produce identical $(P, c, A, b)$ at full benchmark size, so the
tables below time the construction of the same matrices. All $25$ problems are compared, with
\textsc{CVaR} reported as a did-not-finish.

The engine is fastest where the lowered matrices contain large dense blocks: it knows every
atom's Jacobian block and its sparsity pattern in closed form, while CasADi must discover the
pattern and reconstruct the values through seeded derivative sweeps, whose number a dense block
forces to the full dimension (on \textsc{CVaR}'s dense scenario block the extraction did not
finish within \SI{10}{\hour}). The ratio reverses on the smallest problems, where the engine
column is dominated not by extraction but by CVXPY's Python-side reduction chain, which the
hand-lowered CasADi models are spared by construction.

The re-solve is CasADi's home regime: evaluating the compiled function tape beats the engine's
re-solve, which still traverses CVXPY's solve path, by about $2\times$ in geometric mean, and
dramatically so when the parameters only touch $b$ (\textsc{ConvexPlasticity}). The engine
retains the advantage when a parameter reshapes the quadratic itself
(\textsc{FactorCovarianceModel}), where the tape must re-gather a large parameter-dependent $P$
on every evaluation.
