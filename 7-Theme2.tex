\Chapter{BENCHMARK RESULTS}\label{sec:Theme2}

This chapter compares \texttt{diffengine}, the \texttt{CVXPY} canonicalization backend of
Chapter~\ref{sec:Theme1} built on \texttt{SparseDiffEngine}, against \texttt{CVXPY}'s
three existing backends: the default \texttt{cvxcore} backend (which we refer to as
\texttt{CPP}) and the two pure-Python backends \texttt{SCIPY} and \texttt{COO}, all
described in \S\ref{sec:matrix-stuffing}. The central question is whether the symbolic
and numeric split of Chapter~\ref{sec:Theme1} can take the place of the
parameter-to-data tensor on parametric problems. A second motivation is the state of
\texttt{cvxcore} itself. It is the oldest of the backends and \texttt{CVXPY} has
deprecated it, so the project needs a replacement. All four backends build the same
problem data from the same expression trees. A replacement must build that data at least
as fast.

We use the $25$ problems of \texttt{CVXPY}'s public benchmark suite
\cite{cvxpybenchmarks}. The suite includes problems from portfolio selection, regression
and classification, image inpainting, and many more applications in convex optimization.
On parametric problems canonicalization follows either
the \ac{DPP} path or the \texttt{ignore\_dpp} path of \S\ref{sec:ms-parameters}. We conduct numerical
experiments on both. First, \S\ref{sec:bench-oneshot} compares the first
canonicalization time of all $25$ problems on the \texttt{ignore\_dpp} path. Second,
\S\ref{sec:bench-param} compares the parameter-to-data tensor against the symbolic and
numeric split on the seven \ac{DPP} parametric problems.

Each measurement runs \texttt{get\_problem\_data} once with
\texttt{Clarabel}~\cite{clarabel} as the target solver. The method canonicalizes the
problem for that solver and returns the resulting problem data without calling the solver.
All measurements run single-threaded on a 2018 MacBook
Pro with a 6-core Intel Core i7-8850H and \SI{16}{\giga\byte} of memory. \texttt{CVXPY}'s
backends run on the released
version 1.9.2. The \texttt{diffengine} backend is in a separate branch,
available as a pull request:
\begin{center}
  \url{https://github.com/cvxpy/cvxpy/pull/3448}
\end{center}
The benchmark scripts and all recorded timings are available at
\begin{center}
  \url{https://github.com/SparseDifferentiation/Jacobian-accumulation}
\end{center}

\section{First canonicalization}
\label{sec:bench-oneshot}

Table~\ref{tab:oneshot-compile} summarizes the results. \texttt{diffengine} is the
fastest of the four backends on $21$ of the $25$ problems, with a geometric-mean ratio of
$0.37$, and on seventeen problems it is more than twice as fast as the best
\texttt{CVXPY} backend. On the four problems where it is slower, canonicalization is
dominated by moving large blocks of constant data into the problem matrices.

Figure~\ref{fig:profiles} (top) reports the Dolan--Mor\'e performance profile
\cite{dolan2002} of the canonicalization times. With $t_{p,s}$ the time of backend $s$ on
problem $p$ and $n$ the number of problems, the profile of backend $s$ is the fraction of
problems on which it is within a factor $\tau$ of the fastest backend,
\BEQ\label{eq:perf-profile}
f_s(\tau) = \frac{1}{n}\,\bigl|\{\, p : t_{p,s} \le \tau \, \textstyle\min_b t_{p,b}
\,\}\bigr|,
\EEQ
the minimum running over all four backends. \texttt{diffengine} is within $7\times$ of
the best backend on every problem. No \texttt{CVXPY} backend is fastest on more than two,
and each needs $\tau \approx 8$ to cover $88$--$96\%$ of the suite.

The bottom panel of Figure~\ref{fig:profiles} reports the same profile for peak memory,
with $t_{p,s}$ replaced by the growth of the process's peak resident memory during
canonicalization, read with \texttt{getrusage}. \texttt{SCIPY} has the lowest peak memory on
$16$ of the $25$ problems. On one problem \texttt{CVXPY}'s backends report zero growth, as canonicalization never
pushes the process above the peak reached during setup; the ratio is undefined there and
the problem is excluded. Over
the remaining $24$ problems, \texttt{diffengine} matches \texttt{cvxcore} and
\texttt{COO} in geometric mean and uses about $1.5\times$ the memory of \texttt{SCIPY}.

\section{Parametric canonicalization}
\label{sec:bench-param}

\texttt{diffengine} builds no tensor. Its first canonicalization caches the sparsity
patterns and intermediate allocations of the symbolic pass, and a parameter update
re-runs only the numeric pass on the cached program. Table~\ref{tab:param-tensor}
compares the two strategies on both workloads, the first canonicalization and the
re-solve. \textsc{ConvexPlasticity} is not \ac{DPP} as the solving chain evaluates it
and is excluded; its construction appears in Table~\ref{tab:oneshot-compile}, and its
$6\times$ loss there stems from a sparse materialization defect discussed in
\S\ref{sec:Limitations}.

\section{Discussion}
\label{sec:bench-summary}

\texttt{diffengine} is the fastest backend on the large majority of the suite, on
parametric and non-parametric problems alike.

The parametric results bear on the choice posed in \S\ref{sec:problem-statement}, between
paying the tensor's upfront cost and repeating the full canonicalization at every solve.
Building the tensor costs the dense-tensor backends far more than direct construction and
fails outright at the largest parameter counts; only the coordinate-format tensor, which
scales with the stored nonzeros rather than the parameter dimension
(\S\ref{sec:bg-sparse}), builds at no extra cost, and this degradation is what the
backend substitution of \S\ref{sec:ms-parameters} avoids. The symbolic and numeric split
pays no comparable price; the cached program is a byproduct of the first canonicalization.
Once built, re-applying the tensor is not decisively faster than re-running the numeric
pass; it keeps a roughly $2\times$ advantage where the parameters enter as small dense
maps and loses elsewhere.

The tensor makes the map from parameters to problem data an explicit affine object, and
dependent packages consume that object directly: \texttt{cvxpylayers} differentiates
through it \cite{agrawal2019dpp} and \texttt{CVXPYgen} writes it into generated C code
\cite{schaller2022cvxpygen}. For a user who canonicalizes, solves, and re-solves under
new parameter values, the explicit map buys little; on the observed results it is mostly
overkill for standard parametric optimization. A direct extractor reaches the same
problem data at a fraction of the first-solve cost, re-solves at a comparable or better
rate, and applies unchanged to problems the \ac{DPP} ruleset rejects.
