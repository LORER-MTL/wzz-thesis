\Chapter{Benchmark results}\label{sec:Theme2}

In this chapter we evaluate the engine of \S\ref{sec:Theme1} against CVXPY's existing
canonicalization path. The central question is the cost of repeatedly forming the problem data for
a parameterized problem family, which is exactly the regime our two-phase design targets.

\section{Benchmark Setup}

We benchmark on the public CVXPY benchmark suite~\cite{cvxpybenchmarks}, $25$ real-world problems
(linear and quadratic programs, least squares, portfolio models, robust regression, and conic and
semidefinite programs) maintained under \emph{airspeed velocity} (\texttt{asv})~\cite{asv} with
seeded, reproducible data. Three problems need the unsupported \texttt{kron} atom and are excluded;
the remaining $22$ run on both backends.

We time \emph{canonicalization} only---the construction of the problem data $(A,b,c,P)$ from the
expression tree---and exclude the numerical solve, since that is what the engine changes. Concretely
we time \texttt{get\_problem\_data} with the target solver fixed to Clarabel~\cite{clarabel}: the
\texttt{CPP} (\texttt{cvxcore}) baseline is the default DPP path, and the C engine is selected with
\texttt{ignore\_dpp}.
\begin{lstlisting}[language=Python]
prob.get_problem_data(solver=cp.CLARABEL)                   # CPP baseline (DPP tensor)
prob.get_problem_data(solver=cp.CLARABEL, ignore_dpp=True)  # our C engine
\end{lstlisting}
We report two regimes: \emph{cold-start} (a fresh \texttt{Problem} built with nothing cached,
averaged over $3$ builds) and \emph{warm-restart} (parameter values reassigned on a warm cached
chain, averaged over $20$ re-compiles)---the latter being the regime the engine targets. Alongside
these wall-clock times we report \emph{peak memory}, and summarize across the suite with the
\emph{geometric mean} of the per-problem engine/\texttt{CPP} ratios, the standard scale-free
statistic for timings that span orders of magnitude~\cite{cederberg2026presolving}.

All measurements run single-threaded on a MacBook Pro (13-inch, M2, 2022): 8-core Apple M2,
\SI{24} GB RAM, macOS~26.3, with Python~3.14, CVXPY~1.10 (dev), NumPy~2.4~\cite{numpy}, and
SciPy~1.16~\cite{2020SciPy-NMeth}. Versions are pinned and the suite and engine are public, so the
configuration is reproducible.

\paragraph{Reading.}
In aggregate the engine is about $3\times$ faster on cold builds (geometric-mean ratio $0.32$) and
near parity on parametric re-compiles ($1.18$), but the per-problem split is the more informative
story. On \emph{cold} compilation the engine wins on the bulk of the LP, QP, portfolio, and conic
problems---typically $3$--$12\times$ faster, since it extracts the problem data directly from the
expression trees while \texttt{CPP} pays the full parameter-tensor build. It loses on
\texttt{Murray} ($1.55\times$), \texttt{ConvexPlasticity} ($2.63\times$), and the
\texttt{SemidefiniteProgramming} outlier ($8.9\times$), and reaches parity on
\texttt{FactorCovarianceModel} ($0.97\times$). On \emph{parametric re-compilation} the picture is
mixed and use-case dependent: the engine is faster on the matrix-stuffing and fully-parametrized-LP
re-solves ($0.29$--$0.72\times$) and near parity on \texttt{ParametrizedQP}, but $3.4$--$4.5\times$
slower on \texttt{FactorCovarianceModel}, \texttt{SVM}, and \texttt{ConvexPlasticity}, where
\texttt{CPP}'s cached DPP parameter$\to$data tensor (one sparse matmul per solve) is hard to beat.
The largest memory wins come from keeping constants sparse: eliminating an eager
$25\,000\times25\,000$ dense densification ($\approx 5$\,GB) on \texttt{FactorCovarianceModel}, and
shrinking the \texttt{ConvexPlasticity} Hessian block from $9$M to $51$k nonzeros by routing a
mostly-zero \texttt{quad\_form} matrix to the sparse binding.

parameterized problems---parametric least squares, a factor-covariance portfolio, and an
energy-storage scheduling model---and re-measure cold-start time, warm-restart time, and peak
memory as the size grows. All three are genuinely parametric, so the warm-restart curve measures
the engine's target regime: refilling values on a fixed sparsity pattern as the parameters change.
For each panel we plot \texttt{CPP} against the C engine on log--log axes.

\subsection{Parametric least squares}\label{sec:scaling-ls}
The bread-and-butter case: fit $x$ to noisy observations with the data matrix $A$ and right-hand
side $b$ supplied as parameters, so a re-solve only reassigns $A$ and $b$. The size knobs are the
number of observations $m$ and variables $n$.
\begin{lstlisting}[language=Python]
import cvxpy as cp

A = cp.Parameter((m, n))      # data matrix   (reassigned each solve)
b = cp.Parameter(m)           # observations  (reassigned each solve)

x = cp.Variable(n)
objective   = cp.Minimize(cp.sum_squares(A @ x - b))
constraints = [0 <= x, x <= 1]
prob = cp.Problem(objective, constraints)
\end{lstlisting}
We sweep $n \in \{250, 500, 1000, 2000, 4000\}$ with $m = 3n$ (overdetermined) and measure both
backends in the \emph{ignore-DPP} regime: the canonicalization is rebuilt from scratch whenever the
parameters change, which is the engine's intended use case. The C engine carries the parameters
natively and re-extracts values on a fixed sparsity pattern; the \texttt{CPP} baseline substitutes
the parameter values (the \texttt{EvalParams} reduction) and re-canonicalizes the resulting
constant-data problem. We deliberately avoid CPP's DPP parameter-tensor path here: because the data
matrix $A$ is itself an $m \times n$ parameter, that tensor has $\Theta(mn)$ entries and its
construction dominates everything else---tens of seconds and gigabytes already at $n = 500$---so it
is neither representative nor the comparison of interest. Cold-start and warm-restart times are
medians over three repetitions; peak memory is the process resident-set high-water mark
(\texttt{ru\_maxrss}), measured in a fresh subprocess per point so that, unlike Python-level
\texttt{tracemalloc}, it also captures the engine's C-side allocations.

Cold-start (Figure~\ref{fig:scaling-ls-cold}) favours the engine by roughly $4\times$ across the
range (ratio $0.21$--$0.27$), both backends scaling as $\sim n^{2.1}$. The gap widens on
warm-restart (Figure~\ref{fig:scaling-ls-warm}): \texttt{CPP} re-canonicalizes in essentially its
cold-start time ($9.1$\,s at $n = 4000$), whereas the engine re-extracts on the cached pattern in
$863$\,ms---a $10$--$12\times$ speed-up that is precisely the non-DPP re-solve regime the engine
targets. Peak memory (Figure~\ref{fig:scaling-ls-mem}) is comparable: both grow as $\sim n^{1.6}$
and are dominated by the dense $A$, with the engine $2$--$30\%$ heavier in resident set. Its own
internal accounting (the engine's \texttt{verbose} ``peak memory'') grows as $\sim n^{2.0}$, from
$14$\,MB at $n = 250$ to $3.7$\,GB at $n = 4000$, yet stays below the process RSS throughout.

\subsection{Factor-covariance portfolio}\label{sec:scaling-portfolio}
A Markowitz portfolio whose risk is expressed through a low-rank factor model: $n$ assets load on
$m \ll n$ factors with covariance $\Sigma$, plus idiosyncratic diagonal risk $D$. The risk-aversion
$\gamma$ and leverage limit $L_{\max}$ are parameters, so re-solving traces the efficient frontier
without rebuilding the problem. The size knobs are the number of assets $n$ and factors $m$.
\begin{lstlisting}[language=Python]
import cvxpy as cp
import numpy as np

# mu: expected returns, F: factor loadings (n x m),
# Sigma: factor covariance (m x m), D: idiosyncratic variances (diagonal).
w = cp.Variable(n)                  # portfolio weights
f = cp.Variable(m)                  # factor exposures
gamma = cp.Parameter(nonneg=True)   # risk aversion   (reassigned each solve)
Lmax  = cp.Parameter()              # leverage limit  (reassigned each solve)

ret  = mu.T @ w
risk = cp.quad_form(f, Sigma, assume_PSD=True) + cp.sum_squares(np.sqrt(D) @ w)
objective   = cp.Maximize(ret - gamma * risk)
constraints = [cp.sum(w) == 1, f == F.T @ w, cp.norm(w, 1) <= Lmax]
prob = cp.Problem(objective, constraints)
\end{lstlisting}
We hold the factor count fixed at $m = 100$ and sweep the assets
$n \in \{500, 1000, 2000, 4000, 8000\}$. As in the least-squares study, both backends run in the
\emph{ignore-DPP} rebuild regime---the engine carries $\gamma, L_{\max}$ natively and re-extracts on
a fixed sparsity pattern, while \texttt{CPP} substitutes their values and re-canonicalizes. (Here the
parameters are scalar, so CPP's DPP cache would in fact be feasible; we use the same rebuild regime
as before for a consistent comparison.) Times are medians over three repetitions; peak memory is the
process resident-set high-water mark measured in a fresh subprocess.

Cold-start (Figure~\ref{fig:scaling-portfolio-cold}) again favours the engine, but less decisively
than for least squares and with a narrowing margin: from $0.41\times$ at $n = 500$ to $0.88\times$
at $n = 8000$, as the engine's $\sim n^{1.2}$ cold cost catches CPP's $\sim n^{0.9}$. Warm-restart
(Figure~\ref{fig:scaling-portfolio-warm}) is where the engine dominates: \texttt{CPP} pays its full
cold-start cost on every re-solve ($144$\,ms at $n = 8000$), while the engine refills the cached
pattern in $10.7$\,ms---a steady $12$--$13\times$ advantage. Peak memory
(Figure~\ref{fig:scaling-portfolio-mem}) is close, the engine $4$--$16\%$ heavier in resident set;
both curves are nearly flat because the low-rank model keeps the operator small. The engine's own
internal peak (its \texttt{verbose} accounting) grows as $\sim n^{0.9}$, from $6$\,MB at $n = 500$
to $74$\,MB at $n = 8000$.

\subsection{Energy-storage scheduling}\label{sec:scaling-energy}
A simple energy problem: schedule a battery over a horizon of $T$ hours to minimize the cost of grid
energy, where the hourly price is the parameter that changes between solves. The state of charge is
the running sum of charge minus discharge, and the battery must end empty. The size knob is the
horizon $T$.
\begin{lstlisting}[language=Python]
import cvxpy as cp
import numpy as np

price = cp.Parameter(T)             # hourly price  (reassigned each solve)
load  = np.random.rand(T)           # fixed demand profile
Q, Pmax = 50.0, 20.0                # capacity and charge/discharge power limit

charge    = cp.Variable(T, nonneg=True)
discharge = cp.Variable(T, nonneg=True)
soc = cp.cumsum(charge - discharge)         # battery state of charge

constraints = [charge <= Pmax, discharge <= Pmax,
               soc >= 0, soc <= Q, soc[T - 1] == 0]
grid = load + charge - discharge            # net energy drawn from the grid
prob = cp.Problem(cp.Minimize(price @ grid), constraints)
\end{lstlisting}
