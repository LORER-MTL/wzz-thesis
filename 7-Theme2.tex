\Chapter{Benchmark results}\label{sec:Theme2}

This chapter presents benchmark results which compare the \texttt{diffengine} backend
(the CVXPY implementation based on \texttt{SparseDiffEngine}) with \texttt{cvxcore}
and CasADi.
All comparisons run on the $25$ problems of CVXPY's public benchmark suite
(\url{https://github.com/cvxpy/benchmarks}). These convex optimization problems cover many
fields, ranging from portfolio models, robust regression, and semidefinite programs to simple
LPs and QPs that are close to standard form.
The rest of the chapter first presents some technical details about the benchmark setup,
followed by the comparison results which are paired with commentary and observations.

\section{Benchmark Setup}

Every benchmark measures the construction of the problem data $(A,b,c,P)$; no solver is
invoked. For the two CVXPY backends this corresponds to a call to \texttt{get\_problem\_data}
with the target solver fixed to Clarabel~\cite{clarabel}: the \texttt{CPP} (\texttt{cvxcore})
baseline runs on the default DPP path, while \texttt{diffengine} is selected by passing
\texttt{ignore\_dpp=True}. For CasADi, we time the extraction of the same $(A,b,c,P)$ by
differentiation of an equivalent expression graph, following the conventions described in
Section~\ref{sec:bench-casadi}.

Every comparison reports up to two timings: a \emph{single} solve, where the problem
data are constructed once from scratch, and, on the subset of parametric problems, a
\emph{re-solve}, where the problem data are reconstructed after reassigning random parameter
values on a cached problem.

All measurements run single-threaded (BLAS thread pools pinned to one thread) on a 2018 MacBook
Pro with a 6-core Intel Core i7-8850H at \SI{2.6}{\giga\hertz} and \SI{16}{\giga\byte} of RAM.
The software versions are:
\begin{itemize}
  \item Python 3.14,
  \item CVXPY 1.10 (development version),
  \item \texttt{sparsediffpy} 0.6.1,
  \item NumPy 2.4~\cite{numpy} and SciPy 1.17~\cite{2020SciPy-NMeth},
  \item CasADi 3.7.2~\cite{andersson2019}.
\end{itemize}

Each reported time is the median of three new compilations; the re-solve columns are medians
of twenty re-evaluations. The scripts which run the benchmarks, the CasADi model for each
problem, and all recorded timings are available at
\url{https://github.com/SparseDifferentiation/Jacobian-accumulation} under the
\texttt{canonicalization/} directory.

\texttt{diffengine} is faster on the re-solve for six of the eight parametric problems, and on
the first solve for all but \textsc{ConvexPlasticity}. Its re-solves are fast because the
compiled program is cached, so only the parameter-dependent coefficient entries are
re-evaluated. The DPP baseline instead multiplies its cached parameter tensor by the new

across many coefficients (\textsc{SVM}'s regularization weight, \textsc{FactorCovariance}'s
risk aversion) is the ideal case for the tensor product.

\section{Comparison against CasADi}
\label{sec:bench-casadi}
CasADi~\cite{andersson2019} extracts problem data by algorithmic differentiation of a symbolic
expression graph. Since CasADi has no notion of disciplined convex programming, it cannot
canonicalize the high-level models; for a fair comparison we hand it the \emph{already-lowered}
formulation: the same epigraph variables and the same conic rows that CVXPY's canonicalization frontend
produces, written as CasADi \texttt{MX} expressions $f(z, \theta)$ (objective) and
$g(z, \theta) = b - Az$ (constraint slacks), where $z$ stacks the original and epigraph variables
and $\theta$ collects the parameters.

The problem data are recovered exactly the way CasADi's own quadratic-programming interface
\texttt{qpsol} does~\cite{casadidocs}, by differentiating the graph without invoking any
solver:
\[
c = \nabla_z f \,\big|_{z=0}, \qquad
P = \frac{\partial (\nabla_z f)}{\partial z}, \qquad
A = -\frac{\partial g}{\partial z}, \qquad
b = g \,\big|_{z=0}.
\]
These four quantities are wrapped in a \texttt{casadi.Function} which maps $\theta$ to
$(P, c, A, b)$. Computing $P$ as the Jacobian of the gradient is CasADi's fastest path on
these problems.

For CasADi, the single-solve timing covers differentiation, function construction, and the first
numeric evaluation on a freshly built graph, while a re-solve is one further evaluation of
the compiled function at the new parameter values. Graph construction itself is excluded,
mirroring the \texttt{diffengine} timing, which also starts from a built expression tree. We
verified on every benchmark that the two systems produce identical $(P, c, A, b)$ at full
benchmark size, so the tables below time the construction of the same matrices. All $25$
problems are compared, with \textsc{CVaR} reported as a did-not-finish.

These benchmarks are not the most favorable showcase for CasADi. It is built to differentiate
arbitrary programs, whose derivatives genuinely change with the evaluation point, and the
canonicalization of affine and quadratic problems, where every derivative is constant, is a
degenerate special case of that task. CasADi is also designed for workflows which construct a
function once and then evaluate it many times, so the one-time extraction cost measured here
is amortized away in its intended use.

\texttt{diffengine} is fastest where the lowered matrices contain large dense blocks: it knows
every atom's Jacobian block and its sparsity pattern in closed form, while CasADi must discover
the pattern and reconstruct the values through seeded derivative sweeps, whose number a dense
block forces to the full dimension. \textsc{CVaR} is the extreme case: its constraint matrix
contains a dense $131\,072 \times 768$ scenario block, which forces roughly $770$ derivative
sweeps during the Jacobian construction, and the extraction did not finish within
\SI{10}{\hour}.

The re-solve plays to CasADi's strengths. A re-solve only runs the compiled function: the
constant values are baked in at construction time, so only the entries which actually depend
on $\theta$ are recomputed, with no Python in the loop. This is about $2\times$ faster in
geometric mean than the \texttt{diffengine} re-solve, which still traverses CVXPY's solve
path, and dramatically faster when the parameters only touch $b$ (\textsc{ConvexPlasticity}).
\texttt{diffengine} remains faster when a parameter reshapes the quadratic itself
(\textsc{FactorCovarianceModel}), where CasADi must re-gather a large parameter-dependent $P$
on every evaluation.
